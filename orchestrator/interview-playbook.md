# 建议式深访手册

本手册定义跨阶段的访谈原则；执行由 `rp-interview-orchestration` 控制，具体触发项见其阶段覆盖地图。目标不是把问题变多，而是避免漏掉承重决策或把多个决定概括成一个答案，同时降低用户从零构思的负担。

## 核心合同

除工作目录、文件路径、是否启用某功能等纯操作事实外，每个有实质取舍的创作问题都应包含以下四部分：

1. **问题**：当前真正需要用户决定或校准的内容；
2. **建议**：Agent 基于现有材料给出的明确默认方案，必要时给 2–3 个方向，但必须指出首选；
3. **为什么这样建议**：说明建议如何承接已经确定的体验、人物、世界或运行约束；
4. **影响**：说明不同选择会怎样改变实际内容、后续阶段或玩家体验。

推荐的自然表达：

```text
问题：玩家第一次见到她时，最先感受到危险还是可靠？
建议：我建议先感到危险，再通过一个不张扬的保护动作露出可靠。
为什么：这样能同时保留距离感和继续接近她的理由，比直接写“外冷内热”更容易稳定表演。
影响：这会决定初见动作、对白强度、开场冲突，以及后续关系推进速度。
你可以直接说“按建议”、修改其中一项，或让我继续决定。
```

不要求机械使用固定标题；只要每个决策点的问题、建议、理由和影响清楚，可以自然表达。相邻问题可共享背景，但必须分别编号、分别可回答；不能用一个综合题或一次笼统的“按建议”关闭多个独立的高影响决定。每轮最多 3 个决策点，超出时分轮。

## 建议必须承担创作责任

前端建议必须让用户看见结构，按 `shared/frontend/layout-preview.md` 在对话主动画草图，展示当前标签/折叠/详情/步骤等关键状态；回答或改布局后同轮更新。已有明确决定或自由设计授权不反复求批，草图不替代完整访谈或真实视觉实现。已有 HTML 时提供当前内容的渲染预览，不仅列控件名称或让用户自己画。

- 不问空泛的“你想要什么”；先结合已有信息提出可采用的具体方向，再让用户确认或纠偏。
- 不用“都可以”“看你喜欢”冒充建议。存在明显更一致、更省成本或更可玩的方案时，明确推荐。
- 建议优先级依次是：用户已明确的事实与禁区 → 现有材料的强特征 → 核心体验与因果一致性 → 最简可运行路线。
- 用户说“按建议”只关闭紧邻、明确编号且已分别呈现的决策；“你定/整体放权”只覆盖语境中明确授权的范围。授权范围不清时先澄清；不把沉默、短答或“继续”解释成放权。
- 对用户不需要掌握的专业实现，由 Agent 自行完成；但**是否需要某项运行能力**不能被 Agent 私自吞掉。MVU、MVU_ZOD、EJS 以及用户要求的酒馆交互能力，都必须用普通语言说明用途、技术名称和取舍，让用户可以明确选择；变量作用域、Schema 写法、API、正则语法和具体文件组织仍由 Agent 负责。
- 用户明确选择启用的能力具有约束力。Agent 不得以“安全”“复杂”“省事”或“建议最小化”为理由静默关闭、降级、改名或用静态假实现替代；确实存在宿主阻碍时，先报告阻碍与损失，再请用户选择保留能力的实现路线或明确放弃。

## 创作归属模式与角色边界

在定位阶段必须单独关闭以下正式分流；默认选第一项：

1. **开放世界**：世界和 NPC 对外部主控保持中立，玩家可以创建一个或多个主控；
2. **固定主角**：所有固定身份、关系和共同经历都属于明确主角路线；
3. **开放世界＋可选主控预设**：世界核心保持中立，固定主控作为独立、可选的预设存在。

访谈中始终区分：

- creator 是使用 Agent 的创作者；
- 玩家是将来导入卡后进行游玩的人；
- 主控是当前聊天接入世界的外部角色；
- `<user>` 是外部角色资料的预留槽位。

开放世界默认不询问或代写玩家姓名、身份、过去、能力、立场和与 NPC 的私人关系。NPC 可以有自己的生活、目标以及与固定角色/势力的关系，也可以定义对陌生人和身份类型的通常反应，但不得默认把外部主控当作朋友、恋人、仇人、亲属或旧识。固定关系只能进入明确标记的主控预设或固定主角路线。


脑暴用于把未经整理的灵感整合为可游玩母纲，不是把世界、角色、系统和剧情栏目提前合并成一份大问卷。

- 第一轮先复述并解释现有碎片共同承诺的体验、冲突和开放可能，再展示一个首选整合方向；不能只回复“请补充更多信息”。
- 只询问会改变整体脊柱的事项，例如作品反复提供的体验、现实/架空程度、玩家怎样介入、世界怎样自行变化、怪异或冲突是否存在共同规律、最不希望滑向什么。
- 每轮回答后先展示母纲怎样被改写，再提出下一个最有价值缺口。场景、关系、世界动力和典型循环都属于真实推进。
- “完整母纲”是可持续产生选择与后果的开放结构，不是预先锁死所有路线的剧情梗概，也不是地点和设定名词的堆积。
- 用户只有一句基础想法时，Agent 负责提出第一版作品脊柱；用户可以只说“按建议”并继续，但只关闭当轮明确呈现的决策。
- 脑暴完成后，定位阶段消费结果并收束制作合同，不重新询问已经回答的同义问题。

## 深度动作

按当前缺口选择下列动作，不要求每阶段机械走完全部动作：

1. **锚定**：确认这一阶段最重要的体验、欲望、压力或用途。
2. **具体化**：把形容词和概念转成动作、对白、日常、环境或规则后果。
3. **对比与边界**：说明它与相近方向有什么不同，以及明确不希望出现什么。
4. **压力与因果**：询问在拒绝、失败、时间推进、利益冲突或无人介入时会怎样变化。
5. **场景证明**：写一个短场景、行为样例、规则演算或交互片段，验证设定是否真的成立。
6. **校准**：让用户针对已经写出的具体内容修正，而不是重新面对空白问题。

优先深入承重内容：会反复出现、会改变选择、会影响多个阶段，或一旦定错就需要大面积返工的事实。装饰性细节可以由 Agent 补全，不为“访谈完整”逐项询问。

## 回合组织

每轮最多 3 个独立决策，按依赖关系组织：先问会改变后续答案的核心项，再问同一主题下的具体表现。逐项读取当前阶段覆盖地图，先检查材料与既有回答；不为满足列表而问触发条件不成立的题。问题很多时：

- 对低风险、可逆项直接给默认建议；用户一句“按建议”只接受当前已单独编号且后果清楚的决定。
- 对有真实取舍的项分别说明影响；
- 不发送没有建议和解释的长问卷；
- 不要求用户一次完成整套世界、人物或系统设计；
- 用户回答一部分时，按题号/决策逐项关闭；先据此写出已确定内容，再只追问仍未解决的高影响缺口。

每次用户回答后至少完成一项真实推进：修改项目文件、写出可用内容、重写已有段落、生成一个场景证明或实现一个运行组件。随后只指出下一个最有价值的张力，不连续多轮纯收集信息。

## 深度档位

不在预检中强迫用户选择档位；根据项目规模、用户投入和返工风险自动调整，用户也可随时指定。

- **轻量**：抓住核心锚点，给出建议，并用一个具体片段校准；适合快速卡或定向修改。
- **标准（默认）**：完成锚定、具体化、至少一次压力/因果检查和一次具体内容校准。
- **深挖**：对承重内容增加对比边界、多情境压力、场景证明和连锁后果；适合群像、长期玩法或用户明确要求细做的部分。

深挖不等于询问更多专业字段。它要求同一个核心内容在更多真实情境中站得住，而不是扩大百科规模。

## 预检中的运行能力选项

能力选择必须透明、独立、可多选，但提问使用普通用户能理解的语言，并在括号中标出技术名称：

1. **让时间、地点、任务、关系、物品和角色状态跨消息记住并变化（MVU）**；
2. **检查变量类型、范围、必填字段和嵌套结构，减少更新错误（MVU_ZOD）**；它依赖 MVU，但不能被悄悄合并或悄悄省略；
3. **让 Prompt、世界书内容或页面根据当前上下文自动变化（EJS）**；
4. **让玩家点击界面执行行动、查看详情或调用酒馆能力（Tavern Helper 等）**，仅在项目确实需要交互时询问。

每项分别维护 `enabled`、`disabled`、`unresolved`。用户只选择 MVU，不代表选择或拒绝 MVU_ZOD/EJS；用户只选择 EJS，不代表生成 MVU；沉默不等于关闭。用户明确启用后不得静默降级。先分别解决 MVU 与 EJS，再在两者都启用且确有数据依赖时判断 MVU→EJS bridge；bridge 不是用来替代用户能力选择的隐藏开关。

## 各阶段的非专业抓手

| 阶段 | 优先询问的玩家语言 | Agent 自行处理的专业问题 |
|---|---|---|
| 脑暴 | 哪些画面最舍不得丢、想反复获得什么感觉、人物之间最有意思的拉扯是什么、最不想做成什么 | 灵感归类、主题提炼、矛盾整合、可玩脊柱与场景压力检验 |
| 定位 | 最想反复获得什么感觉、最不想变成什么、典型一轮怎么玩；这是开放世界、固定主角，还是开放世界＋可选主控预设 | 卡格式和组件拆分、世界核心与主控预设的技术分层 |
| 材料 | 最想保留的体验、最不满意的表现、哪些内容不能失真 | 字段迁移和格式兼容 |
| 世界 | 普通人怎样生活、谁得利谁受损、无人介入会发生什么；外部主控不介入时世界如何自行运行 | 世界书切片与调度、世界核心与外部主控的边界 |
| 角色 | 想要什么、压力下怎么做、公开与私下有什么差别；与哪些固定角色/势力有确定关系，哪些关系必须留给当前主控决定 | 条目结构和字段归位、关系作用域 |
| 系统 | 哪些选择需要长期后果、失败意味着什么、玩家看到什么反馈 | 数值形态和持久化方案 |
| 场景 | 谁在这里做什么、玩家能怎样介入、离开或失败会留下什么 | 拓扑表达和条目组织 |
| MVU 状态 | 哪些变化必须跨消息记住、谁可修改、玩家何时看到 | 状态根、Schema、更新、楼层和持久化 |
| EJS 模板 | 哪些 Prompt/页面内容需要随上下文动态变化、失败时显示什么 | 执行阶段、作用域、输出通道和安全设置 |
| MVU→EJS bridge | 动态模板是否真的必须读取持久状态、是否只读 | 数据方向、完整快照、生命周期和回退 |
| 叙事与开场（可选） | 只对已选择新增的叙事规则/开场访谈，不强迫另一项或重写已有素材 | 实际 greeting 内容、已有文本与叙事规则检查 |
| 开场前端 | 进入游戏前必须理解什么、哪些主控资料必须先准备、复制后怎样维护/导入 `<user>` 或主控条目、怎样切 Greeting | 表单、剪贴板回退、静态 Greeting 映射和当前活动主控读取合同 |
| 持续消息前端 | 每轮一眼要知道什么、看完要做什么、什么必须随 Swipe 更新 | 当前楼层、数据源、正则和消息生命周期 |
| QA | 默认复用已确定关键路径与失败行为，不单独请示；仅新的承重取舍返回其创作阶段 | 自动语法/契约/交付检查，实机证据和用户验收分开 |

## 玩家中立性完成门

定位、世界、角色、场景、叙事和开场阶段完成前，至少检查：无 `<user>` 时世界能否运行；是否把 creator/玩家/主控偷换成同一人；NPC 是否默认绑定了外部主控关系；主控 A→B 切换后旧资料是否泄漏；固定关系是否被隔离在明确的可选预设中。若任一项失败，阶段不能以“默认合理”关闭，必须回到拥有该语义的阶段修复。

## 完成标准

一个阶段不是因为“问过足够多问题”而完成，而是当前覆盖地图中所有已触发的承重决策已由材料明确、用户确认、用户明确授权代定或明确跳过；`tentative` 只支持可逆草稿，不能关闭阶段。并且：

- 承重内容已有明确选择与理由；
- 关键抽象至少有一个可观察的具体表现；
- 重要选择的后果能传递到下游内容；
- 至少一个高风险点经过场景、边界或失败压力检查；
- 用户可以针对已经写出的内容继续修改，而不是仍面对一片空白。
