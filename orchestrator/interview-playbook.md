# 建议式深访手册

本手册定义所有创作阶段共用的访谈方式。目标不是把问题变多，而是降低用户从零构思的负担，同时让每个答案都产生更具体、更可行动、更有后果的内容。

## 核心合同

除工作目录、文件路径、是否启用某功能等纯操作事实外，每个有实质取舍的创作问题都应包含以下四部分：

1. **问题**：当前真正需要用户决定或校准的内容；
2. **建议**：Agent 基于现有材料给出的明确默认方案，必要时给 2–3 个方向，但必须指出首选；
3. **为什么这样建议**：说明建议如何承接已经确定的体验、人物、世界或运行约束；
4. **影响**：说明不同选择会怎样改变实际内容、后续阶段或玩家体验。

推荐的自然表达：

```text
问题：玩家第一次见到她时，最先感受到危险还是可靠？
建议：我建议先感到危险，再通过一个不张扬的保护动作露出可靠。
为什么：这样能同时保留距离感和继续接近她的理由，比直接写“外冷内热”更容易稳定表演。
影响：这会决定初见动作、对白强度、开场冲突，以及后续关系推进速度。
你可以直接说“按建议”、修改其中一项，或让我继续决定。
```

不要求机械使用固定标题；只要问题、建议、理由和影响都清楚，可以写成自然段。多个紧密相关的问题可以共用一段建议、理由和影响，但不能只扔出一串无解释的问题。

## 建议必须承担创作责任

- 不问空泛的“你想要什么”；先结合已有信息提出可采用的具体方向，再让用户确认或纠偏。
- 不用“都可以”“看你喜欢”冒充建议。存在明显更一致、更省成本或更可玩的方案时，明确推荐。
- 建议优先级依次是：用户已明确的事实与禁区 → 现有材料的强特征 → 核心体验与因果一致性 → 最简可运行路线。
- 用户说“你定”“按建议”或整体放权后，直接作出一致决定并写入内容；不要把同一决定换个说法继续追问。
- 对用户不需要掌握的专业实现，由 Agent 自行判断。把技术分歧翻译成玩家能观察到的差别，例如“这条手记只属于当前楼，还是整个聊天长期保留”，不要先问变量作用域、Schema 或 API。

## 深度动作

按当前缺口选择下列动作，不要求每阶段机械走完全部动作：

1. **锚定**：确认这一阶段最重要的体验、欲望、压力或用途。
2. **具体化**：把形容词和概念转成动作、对白、日常、环境或规则后果。
3. **对比与边界**：说明它与相近方向有什么不同，以及明确不希望出现什么。
4. **压力与因果**：询问在拒绝、失败、时间推进、利益冲突或无人介入时会怎样变化。
5. **场景证明**：写一个短场景、行为样例、规则演算或交互片段，验证设定是否真的成立。
6. **校准**：让用户针对已经写出的具体内容修正，而不是重新面对空白问题。

优先深入承重内容：会反复出现、会改变选择、会影响多个阶段，或一旦定错就需要大面积返工的事实。装饰性细节可以由 Agent 补全，不为“访谈完整”逐项询问。

## 回合组织

一轮可以有多个问题，但按依赖关系组织：先问会改变后续答案的核心问题，再问同一主题下的具体表现。问题很多时：

- 对低风险项直接给默认建议，用户一句“按建议”即可接受；
- 对有真实取舍的项分别说明影响；
- 不发送没有建议和解释的长问卷；
- 不要求用户一次完成整套世界、人物或系统设计；
- 用户回答一部分时，先据此写出实际内容，再继续剩余缺口。

每次用户回答后至少完成一项真实推进：修改项目文件、写出可用内容、重写已有段落、生成一个场景证明或实现一个运行组件。随后只指出下一个最有价值的张力，不连续多轮纯收集信息。

## 深度档位

不在预检中强迫用户选择档位；根据项目规模、用户投入和返工风险自动调整，用户也可随时指定。

- **轻量**：抓住核心锚点，给出建议，并用一个具体片段校准；适合快速卡或定向修改。
- **标准（默认）**：完成锚定、具体化、至少一次压力/因果检查和一次具体内容校准。
- **深挖**：对承重内容增加对比边界、多情境压力、场景证明和连锁后果；适合群像、长期玩法或用户明确要求细做的部分。

深挖不等于询问更多专业字段。它要求同一个核心内容在更多真实情境中站得住，而不是扩大百科规模。

## 各阶段的非专业抓手

| 阶段 | 优先询问的玩家语言 | Agent 自行处理的专业问题 |
|---|---|---|
| 定位 | 最想反复获得什么感觉、最不想变成什么、典型一轮怎么玩 | 卡格式和组件拆分 |
| 材料 | 最想保留的体验、最不满意的表现、哪些内容不能失真 | 字段迁移和格式兼容 |
| 世界 | 普通人怎样生活、谁得利谁受损、无人介入会发生什么 | 世界书切片与调度 |
| 角色 | 想要什么、压力下怎么做、公开与私下有什么差别 | 条目结构和字段归位 |
| 系统 | 哪些选择需要长期后果、失败意味着什么、玩家看到什么反馈 | 数值形态和持久化方案 |
| 场景 | 谁在这里做什么、玩家能怎样介入、离开或失败会留下什么 | 拓扑表达和条目组织 |
| 运行时 | 哪些变化必须记住、谁能看见、何时反馈、失败时怎样表现 | MVU/EJS/Schema/API 路线 |
| 开场 | 玩家为何此刻在这里、角色正在做什么、前三轮怎样接住 | greeting 字段和初始化接线 |
| UI | 玩家一眼要知道什么、看完要做什么、手机上最重要什么 | iframe、数据源和生命周期 |
| QA | 导入后的关键路径是什么、哪个功能绝不能坏、可接受怎样降级 | 语法、契约和宿主证据 |

## 完成标准

一个阶段不是因为“问过足够多问题”而完成，而是因为：

- 承重内容已有明确选择与理由；
- 关键抽象至少有一个可观察的具体表现；
- 重要选择的后果能传递到下游内容；
- 至少一个高风险点经过场景、边界或失败压力检查；
- 用户可以针对已经写出的内容继续修改，而不是仍面对一片空白。
