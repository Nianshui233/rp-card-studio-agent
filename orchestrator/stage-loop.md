# 固定创作阶段状态机

状态机只用于当前对话中的创作导航，不写入文件，不建立账本、阶段/进度记录、决定锁/日志、访谈表、需求/盘点清单、交接/恢复文件或 QA 过程日志。所有需用户做创作决定的阶段都按 routing 加载 `rp-interview-orchestration`；共用原则见 `orchestrator/interview-playbook.md`，逐阶段触发项见 `internal-skills/rp-interview-orchestration/references/stage-coverage.json`。

## 固定顺序

```text
preflight
→ brainstorm（预检启用时）
→ positioning
→ materials（有材料、旧卡或转换时）
→ worldbuilding
→ character
→ systems（预检启用时）
→ scenes（预检启用时）
→ mvu（需要跨消息持久状态或明确要求 MVU 时）
→ ejs（需要动态模板/Prompt 或明确要求 EJS 时）
→ runtime_bridge（MVU 与 EJS 都已启用且确实需要交换数据时）
→ narrative_opening
→ opening_frontend（需要介绍/路线/创角页面时）
→ message_frontend（需要持续消息 UI 时）
→ qa_delivery
```

MVU、EJS 和二者的 bridge 是三个不同阶段：

- `mvu` 只决定 MagVarUpdate 状态、Schema、更新、快照和持久化；
- `ejs` 只决定 ST-Prompt-Template 模板、执行阶段、作用域和输出；
- `runtime_bridge` 只在两者分别成立后定义显式数据交换，默认 MVU → EJS 单向只读；
- 启用其中一个不会自动启用另一个，也不会自动创建 bridge。

`qa_delivery` 必走。定向修改、审查或只处理某一组件时可以直接进入相应阶段，再做相关 QA，不强迫经过无关阶段。

## 预检

一次收集：工作目录、NSFW、操作类型、材料位置、脑暴建议与是否启用，以及本次需要的可选内容。

运行能力用玩家语言分开确认，不把 MVU 与 EJS 捆绑成一个选项。只要向用户展示阶段/功能选项，就使用下面两个独立、可多选的项目；不能只显示第一项：

1. **跨消息持久状态（MVU）**：是否需要让任务、关系、物品、时间地点等在后续消息中持续变化并被状态栏读取？
2. **动态模板（EJS）**：是否需要让 Prompt、世界书内容或 STPT 页面根据当前上下文自动变化？

不要把 bridge 当成第三个常规初始选项。先分别解决 MVU 与 EJS，再在两者都启用时判断“EJS 是否必须读取 MVU 状态”。

每项在当前对话中独立维护三态：`enabled`、`disabled`、`unresolved`。

- 用户只回答“要 MVU”：MVU=`enabled`，EJS 仍为 `unresolved`；进入后续前必须从材料明确解决，或补问一次 EJS 需求。用户明确说“只做 MVU/不要 EJS”时，才把 EJS 设为 `disabled`。
- 用户只选择 EJS：EJS=`enabled`，MVU 仍为 `unresolved`；不得因此生成状态树。
- 用户没有回答某项：保持 `unresolved`，不因沉默、“继续”或选择另一项而关闭。
- 材料已有 `.ejs`、STPT 特殊指令、动态模板要求或同类旧实现：EJS=`enabled/source_resolved`。
- 材料明确只有静态内容且没有动态模板用途：Agent 可建议 EJS=`disabled`，但在阶段摘要中说明理由。
- 只有 MVU=`enabled`、EJS=`enabled` 且存在真实数据依赖时，bridge=`enabled`；否则为 `disabled` 或 `not_applicable`。

## 脑暴启用规则

- 只有零散画面、互相冲突的方向或整体重构需求时建议启用；已有清晰企划、定向修改、纯审查或纯技术任务时建议跳过。
- 启用后先加载 `rp-concept-brainstorm`，允许用户直接倾倒未经整理的灵感。第一轮必须先展示暂定整合方向，再询问少量承重选择，不以长问卷或专业字段开场。
- 每次用户回答后立即改写母纲、补出可玩动力或写场景证明；用户只对明确授权范围放权时，直接决定并完成该范围；仍未关闭的高影响项继续逐项追问。
- 母纲默认只在当前对话中形成。用户明确要求时可以保存单一当前版 `创作总纲.md`，但不得保存脑暴过程、完成状态、问题答案或修改历史。
- 脑暴足以支撑下游时进入 `positioning`。定位直接继承核心体验、世界动力、关系张力、典型循环与防偏移边界，只补真实缺口，不重复从零发问。

## 阶段内部循环

```text
读取当前阶段覆盖地图并识别已知/未知/不适用项
→ 将未知承重事项拆成独立决策（每轮最多 3 项）
→ 逐项给出问题、建议、理由和影响
→ 用户确认、修正、明确授权代定或明确跳过
→ 立即写出或修改真实内容/代码
→ 对承重内容做具体化、压力/因果或场景证明
→ 让用户校准已经写出的内容
→ 若仍有实质缺口，继续下一轮
→ 内容足以支持后续时给出阶段总结报告
→ 进入下一个启用阶段
```

- 纯路径、开关、文件位置等操作事实可以直接询问；创作取舍必须由 Agent 先承担分析并提出明确推荐。
- 每轮最多 3 个独立决策点；可以共享背景说明，但必须分别编号、分别可回答，禁止用一个综合题压扁多个选择。
- 用户不需要从零构思：每项先给首选建议，再让用户确认、局部修改或对清楚标出的范围明确授权代定。
- 用户部分回答时逐项映射；已回答的项写入内容，未回答的高影响项保留开放，不因“继续”或沉默自动关闭。
- 每次回答后都应产生实际内容或修改；不要连续数轮只收集信息。
- 标准模式默认完成锚定、具体化、至少一次压力/因果检查和一次内容校准；轻量或深挖按项目风险自动调整。
- 深挖优先作用于会反复出现、会改变选择或会造成大面积返工的承重内容，不为了显得详细增加百科、字段或专业术语。

阶段总结报告包含：

1. 本阶段实际完成的内容；
2. 已确定的关键事实与规则；
3. 采用这些方向的主要理由及其对后续的影响；
4. 仍存在但不阻断后续的薄弱点或可选增强；
5. 下一启用阶段及其目标。

总结应基于已经写出的内容，不复述完整访谈，不制作决定账本。

## 后续阶段变更与局部回退

后续阶段提出的新展示、交互或运行需求若改变前面已确认的游戏事实，不得把它当成纯 UI 补丁，也不得要求用户重做整张卡。先经过访谈控制器分类为已有状态直读、已确认规则的确定性派生、临时 UI 状态或新持久状态/玩法；新状态/玩法回到覆盖地图标明的 owning stage 重新确认受影响的语义，再返回 `mvu` 定义持久状态合同。只有动态模板需求才返回 `ejs`；只有二者需要交换数据才返回 `runtime_bridge`。不允许 UI 或 EJS 暗中创建 MVU 状态。

## 进入与返回

- 新建完整项目在预检启用脑暴时从 `brainstorm` 开始，否则从 `positioning` 开始。
- 旧卡修改、审查或转换在定位后先经过 `materials`。
- 继续项目时读取现有文件，判断当前尚未完成的最早相关阶段；不创建恢复状态文件。
- 用户明确只修改某个组件、只审查或只处理 UI 时，可以直接进入该组件所属阶段；完成后只执行相关 QA 与交付，不强迫补做无关阶段。
- 后续实现发现前置内容确实不足时，临时返回拥有该内容的阶段，补完后回到原阶段；不重跑其他已完成内容。

## 阶段完成标准

脑暴阶段完成不是因为灵感数量足够，而是零散构想已经成为可供定位直接消费的可游玩母纲：有统一核心、反复体验、自主变化、关系或利益张力、典型循环、开局与升级方向，并至少经过一次具体场景、失败或无人介入检验。

其他阶段的真实内容已经足以供下游使用：覆盖地图中已触发的承重决策均已由明确材料解决、用户确认、用户明确授权代定或明确跳过；临时假设不能关闭承重项。关键抽象已有可观察表现，至少一个高风险点经过场景、边界或失败压力检查。若用户要先看草稿，可交可逆草稿并指出未定事项；不要因为还能扩写或模板还有字段而无限延长访谈。
