# 分阶段共创引擎

## 路线与状态分离

固定顺序为：项目定位 → 材料整理（可选）→ 世界观 → 角色 → 系统（可选）→ 场景（可选）→ MVU/EJS（可选）→ 叙事与开场 → 状态栏/UI（可选）→ 整合交付。

`workflow.planned_stages` 是当前导航计划，不是不可变锁。`.rp-card-state.json` 的阶段状态才表示实际发生了什么。进入、跳过、完成或返回某阶段时同步两者，但不得把未来计划直接伪装成已执行的 `skipped`。

每次准备切换阶段时：

1. 读取项目记录与当前状态；
2. 看当前计划中的下一个阶段；
3. 已计划进入则直接进入，不再重复问“要不要”；
4. 已计划跳过则在真正经过该节点时记录跳过理由；
5. 新信息改变需要时，给出计划调整与推荐，记录后继续；完全放权时直接决定并报告。

旧卡改造（`edit`、`audit`）有一条额外前置门：`materials` 必须先完成原卡及所有附属运行材料的清单、`original.json`、`preserved.json`、用户条目清理/替换记录和未知扩展处理结论。`convert` 只是原始解包/转入可维护项目，不代表内容改造已完成；真正开始重写前必须切换到 `edit`/`audit`。材料阶段未完成时，不能把后续阶段的“已经做过”写成完成，也不能直接进入 `integration`。

阶段切换是单向、可追踪的状态变更，不是对话轮数的推断。一次回复最多完成当前阶段并提出下一阶段建议；除非用户明确选择或已锁定完全放权，否则停在当前阶段等待。即使完全放权，也要按阶段顺序逐个执行并更新账本。

## 每轮固定闭环

```text
多项当前阶段问题 + 已知信息采集 + 方向差异 + 明确推荐
→ 用户选定、补充或授权 AI 决定
→ 生成可直接合并的当前阶段片段
→ 检查当前阶段还缺什么
→ 重复
```

问题应以 RP 创作为中心，不把用户拉去填写程序配置。只有最终宿主确实要求精确字段时，才询问版本、路径、placement、depth、事件或 API。

## 片段要求

- 片段是实际内容或实际运行源码，不是概念摘要；
- 世界、角色、系统、场景、叙事优先使用可读 YAML/文本；
- MVU/EJS、JS、HTML、正则必须生成真实可运行源文件；
- 当前阶段不创建后续阶段的占位假实现；
- 用户选择后马上给片段，不积攒到整阶段最后才写。

## 阶段充分性

当前阶段的核心对象已经可用于下游，且没有会让 RP 无法判定的本阶段空洞，即可结束。不要因为模板还有字段或还能继续脑暴就无限访谈。

## 阶段总汇

每阶段完成时给：

1. 完整合并稿；
2. 已锁定决定；
3. 冲突、薄弱点、可选增强和主动跳过项；
4. 跨阶段待办；
5. 下一阶段可走方向与一个明确推荐。

正常模式等待用户选择“补漏 / 进入推荐阶段 / 进入其他阶段”。相关范围已完全放权时，报告选择后只切换到下一个实际阶段，不得跨过未执行阶段。

## 跨阶段信息

用户主动给出越界信息时接受并记录，不在当前阶段追问。进入目标阶段后先消费记录；已经明确的内容直接作为已知事实，不重复访谈。

若当前阶段被真正的前置缺口阻塞，只返回所属阶段修补必要部分，完成后恢复原阶段，不重做整条流程。

## 写入时机

- 预检答案齐全后立即建立项目记录；
- 每轮只把已选定或已获授权决定的片段写入维护源；
- 候选方案保留在对话或项目计划中，不混进正式源码；
- 永远改 `src/`，再由 Forge 构建 `dist/`；
- 实际 JS/EJS/HTML/正则源应保持完整，Forge 只装配，不重新生成其语义。
