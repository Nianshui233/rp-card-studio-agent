# 固定创作阶段状态机

状态机由 `rp-project-continuation` 维护项目权威，并在当前对话展示实时进度画板。`制作文件/项目记录/authority.md` 保存已确认、待决定、暂缓和风险；`制作文件/项目记录/NEXT.md` 保存当前续接指针；材料与验收分别进入对应 JSON 文件。它们不保存完整聊天过程，也不进入最终导入包。所有需用户做创作决定的阶段都按 routing 加载 `rp-interview-orchestration`；共用原则见 `orchestrator/interview-playbook.md`，逐阶段触发项见 `internal-skills/rp-interview-orchestration/references/stage-coverage.json`。

## 阶段授权与交接

必须同时遵守 `orchestrator/stage-authorization.md`。routing 的 next 不是授权；制作进度、用户接受和代定权限分开。authority 的全阶段账本是唯一状态源，NEXT/画板不得自行制造确认。

## 固定顺序

```text
preflight
→ continuation（读取/初始化项目权威、NEXT、材料和验收文件，并展示当前对话进度画板）
→ materials（有任何用户资料，或检测到外部事实/作品/版本研究需求时；资料规模只影响分批方式）
→ brainstorm（预检启用时）
→ positioning（先关闭创作归属模式分流）
→ worldbuilding
→ character
→ systems（预检启用时）
→ scenes（预检启用时）
→ mvu（需要跨消息持久状态或明确要求 MVU 时）
→ ejs（需要动态模板/Prompt 或明确要求 EJS 时）
→ runtime_bridge（MVU 与 EJS 都已启用且确实需要交换数据时）
→ narrative_opening（需要新设叙事规则或新写开场时；可只做其中一项）
→ opening_frontend（需要介绍/路线/创角页面时）
→ message_frontend（需要持续消息 UI 时）
→ qa_delivery
```

MVU、EJS 和二者的 bridge 是三个不同阶段：

- `mvu` 只决定 MagVarUpdate 状态、Schema、更新、快照和持久化；
- `ejs` 只决定 ST-Prompt-Template 模板、执行阶段、作用域和输出；
- `runtime_bridge` 只在两者分别成立后定义显式数据交换，默认 MVU → EJS 单向只读；
- 启用其中一个不会自动启用另一个，也不会自动创建 bridge。

`qa_delivery` 必走且默认自动执行，无需单独报备；按 `orchestrator/automatic-work.md` 区分本次范围收尾和用户验收，不自动开启下一创作阶段。定向修改、审查或只处理某一组件时可以直接进入相应阶段，再做相关 QA，不强迫经过无关阶段。

## 预检

默认主动发现当前可访问的酒馆安装与运行实例，按 `orchestrator/automatic-work.md` 执行只读探测。叙事规则与开场分别作为可选项展示，沿用已明确素材时不重复访谈，未回答不得静默跳过。

一次收集：工作目录、NSFW、操作类型、材料位置、脑暴建议与是否启用，以及本次需要的可选内容。预检不要求用户填写项目管理字段，但必须在进入世界/角色创作前关闭两个不同性质的选择：创作归属模式，以及运行能力。

### 创作归属模式（正式分流）

用普通语言单独询问：

1. **开放世界**（默认推荐）：玩家自己创建一个或多个主控，世界和 NPC 不预绑定外部主控关系；
2. **固定主角**：作品围绕一个明确主角展开，主角身份、关系和经历可以成为硬设定；
3. **开放世界＋可选主控预设**：世界核心保持玩家中立，同时提供几个可以主动启用的固定主控路线。

用户没有明确选择时，默认使用开放世界。该选择必须在定位阶段确认；未确认前不得把“玩家”“主控”或“user”写成世界内固定人物。

### 运行能力（透明、独立、可多选）

必须用普通语言说明用途，并在括号中保留技术名称；不能因为 Agent 想省事、担心出错或追求“安全”就替用户关闭。询问示例是“是否需要让任务、关系、物品、时间地点等在后续消息中持续变化并被状态栏读取”，以及“是否需要让 Prompt、世界书内容或 STPT 页面根据当前上下文自动变化”：

1. **跨消息记住并更新状态（MVU）**：时间、地点、任务、关系、物品和角色状态是否要在下一轮继续保留和变化；
2. **检查变量结构（MVU_ZOD）**：是否要检查类型、范围、必填字段和嵌套对象，减少 AI 把数字写成文字、漏字段或破坏结构；只有 MVU 启用时才有实际作用，但必须单独说明；MVU_ZOD 与 MVU 仍是独立选择，不能用“已选 MVU”替代确认；
3. **根据上下文动态改变 Prompt/世界书/页面（EJS）**：是否需要动态模板、条件内容或 STPT 页面输出；
4. **界面点击后执行酒馆动作（Tavern Helper 等）**：只在用户要求交互按钮、写入状态、发送行动或调用宿主能力时询问。

MVU、MVU_ZOD、EJS 分别维护 `enabled`、`disabled`、`unresolved`；用户的明确选择具有约束力。用户只回答“要 MVU”：MVU=`enabled`，EJS 仍为 `unresolved`；用户只选择 EJS：EJS=`enabled`，MVU 仍为 `unresolved`。用户只选择一项时只改变那一项；沉默、“继续”或选择另一项都不能把未回答能力改成 `disabled`。用户明确启用后不得静默降级或改名；若环境不支持，先说明阻碍、损失和可选替代路线。

不要把 bridge 当成常规首轮选项。先分别确认 MVU 与 EJS，再在两者都启用且 EJS 确实需要读取 MVU 状态时判断 bridge；bridge 不会因为两者同时启用就自动成立。

## 创作归属模式的内容合同

- **开放世界**：世界核心、NPC 核心、固定角色、势力、场景和无人介入时的事件必须独立成立；外部主控只在运行时接入。NPC 对外部主控的朋友、恋人、仇人、亲属或旧识关系默认未定义。
- **固定主角**：可以写入指定主角的身份、过去、关系和专属开场，但这些事实属于固定主角路线，不得伪装成所有玩家都会拥有的世界事实。
- **开放世界＋可选主控预设**：世界核心与每个主控预设分开维护。预设可引用世界核心，世界核心不得依赖某个预设才能成立；必须保留“从零创建/不启用预设”的入口。
- 多个主控的个人资料、知识、物品、关系和状态必须有清楚作用域。关闭主控 A、启用主控 B 时，不得把 A 的内容写回 B 或世界核心。
- `<user>` 是外部角色接入槽，不是唯一主角。creator、未来玩家、当前主控和 `<user>` 不得在问题、内容或变量中混称。


## 脑暴启用规则

- 只有零散画面、互相冲突的方向或整体重构需求时建议启用；已有清晰企划、定向修改、纯审查或纯技术任务时建议跳过。
- 启用后先加载 `rp-concept-brainstorm`，允许用户直接倾倒未经整理的灵感。第一轮必须先展示暂定整合方向，再询问少量承重选择，不以长问卷或专业字段开场。
- 每次用户回答后立即改写母纲、补出可玩动力或写场景证明；用户只对明确授权范围放权时，直接决定并完成该范围；仍未关闭的高影响项继续逐项追问。
- 母纲内容写入项目权威的当前范围和创作事实；需要完整参考文本时保存 `制作文件/创作源/创作总纲.md`。authority 只记录确认状态、待决定、当前阶段和下一道门，不保存完整问答历史。
- 脑暴足以支撑下游时进入 `positioning`。定位直接继承核心体验、世界动力、关系张力、典型循环与防偏移边界，只补真实缺口，不重复从零发问。

## 阶段内部循环

```text
读取项目权威、NEXT、材料和验收状态
→ 在当前对话展示进度画板
→ 读取当前阶段覆盖地图，并先检查创作归属模式、运行能力选择和主控边界是否已解决
→ 将未知承重事项拆成独立决策（每轮最多 3 项）
→ 逐项给出问题、建议、理由和影响
→ 用户确认、修正、明确授权代定或明确跳过
→ 立即写出或修改真实内容/代码
→ 更新 authority.md、NEXT.md 和必要证据
→ 刷新当前对话进度画板
→ 对承重内容做具体化、压力/因果或场景证明
→ 让用户校准已经写出的内容
→ 若仍有实质缺口，继续下一轮
→ 内容足以支持后续时给出阶段总结并更新下一道门
→ 标记 awaiting_handoff（待交接），本阶段授权到期
→ 创作等待用户审阅；本次制作已到收尾条件时自动 QA/交付，不开启下一创作阶段
→ 核对新的接受/进入依据后，关闭本阶段或继续修正
```

- 纯路径、开关、文件位置等操作事实可以直接询问；创作归属模式和运行能力是否启用属于用户可见的高影响决定，必须用普通语言提出明确推荐并让用户确认；具体文件、API、变量路径和实现细节由 Agent 负责。
- 每轮最多 3 个独立决策点；可以共享背景说明，但必须分别编号、分别可回答，禁止用一个综合题压扁多个选择。
- 用户不需要从零构思：每项先给首选建议，再让用户确认、局部修改或对清楚标出的范围明确授权代定。
- 用户部分回答时逐项映射；已回答的项写入 authority，未回答的高影响项保留开放，不因“继续”或沉默自动关闭。
- 每次回答后至少完成一项真实推进：修改项目文件、写出可用内容、重写已有段落、生成一个场景证明或实现一个运行组件。随后更新 NEXT 和画板，不连续多轮纯收集信息。
- 标准模式默认完成锚定、具体化、至少一次压力/因果检查和一次具体内容校准；轻量或深挖按项目风险自动调整。
- 深挖优先作用于会反复出现、会改变选择或会造成大面积返工的承重内容，不为了显得详细增加百科、字段或专业术语。

阶段总结报告包含：

1. 本阶段实际完成的内容；
2. 已确定的关键事实与规则；
3. 采用这些方向的主要理由及其对后续的影响；
4. 仍存在但不阻断后续的薄弱点或可选增强；
5. 下一启用阶段及其目标。

阶段总结应基于已经写出的内容，不复述完整访谈；列出用户确认、材料事实、受权代定和未接受提案，以及新增/删除/体验变化与验证限制。总结后更新 authority.md、NEXT.md 和当前对话进度画板，创作标为待交接；不自行开启后续创作阶段。本次制作已到收尾条件时自动进入 QA 与交付，旧创作成果保持 authored/pending，最终一次性报告，不让用户再批准技术收尾。

## 后续阶段变更与局部回退

后续阶段提出的新展示、交互或运行需求若改变前面已确认的游戏事实，不得把它当成纯 UI 补丁，也不得要求用户重做整张卡。先经过访谈控制器分类为已有状态直读、已确认规则的确定性派生、临时 UI 状态或新持久状态/玩法；新状态/玩法回到覆盖地图标明的 owning stage 重新确认受影响的语义，再返回 `mvu` 定义持久状态合同。只有动态模板需求才返回 `ejs`；只有二者需要交换数据才返回 `runtime_bridge`。不允许 UI 或 EJS 暗中创建 MVU 状态。

## 进入与返回

- 新建完整项目在预检检测到用户资料或外部研究需求时先进入 `materials`，否则跳过该阶段；脑暴是否启用再按预检决定。
- 旧卡修改、审查或转换在 `materials` 中先保留原始副本、整理来源并盘点组件，再进入定位。
- 继续项目时读取 `制作文件/项目记录/authority.md`、`制作文件/项目记录/NEXT.md`、材料索引、验收记录、现有文件和 Git/worktree，先检查材料处理/研究状态，再判断当前尚未完成的最早相关阶段；不重新询问已经确认的设置。
- 用户明确只修改某个组件、只审查或只处理 UI 时，可以直接进入该组件所属阶段；完成后更新受影响的权威、验收和 NEXT，只执行相关 QA 与交付，不强迫补做无关阶段。
- 后续实现发现前置内容确实不足时，临时返回拥有该内容的阶段，补完后回到原阶段；不重跑其他已完成内容。

## 玩家中立性与主控切换 QA

在进入 QA 与交付前，至少执行以下内容检查，并将结果、证据或待实测状态写入 `制作文件/项目记录/acceptance.json`；当前对话同步展示画板：

1. **无主控测试**：不加载任何 `<user>` 或主控资料时，世界、NPC、势力和场景仍能运行并产生后果；
2. **关系切换测试**：准备“主控 A 是 NPC 朋友、主控 B 是 NPC 仇人”，切换 A→B，确认当前关系、提示、状态栏和剧情均跟随 B；
3. **污染测试**：关闭 A、启用 B，确认 A 的物品、知识、经历、关系和状态不会泄漏到 B 或世界核心；
4. **预设隔离测试**：固定主控关系只在明确可选的预设中出现，未启用预设时不被世界和 NPC 采用；
5. **身份边界检查**：creator、未来玩家、当前主控和 `<user>` 没有被偷换；开场不强迫玩家接受 Agent 擅自编造的身份。

发现内容归属错误时，回到定位、世界、角色或场景阶段修复；不要用正则、前端、EJS 或变量显示掩盖它。

## 阶段完成标准

脑暴阶段完成不是因为灵感数量足够，而是零散构想已经成为可供定位直接消费的可游玩母纲：有统一核心、反复体验、自主变化、关系或利益张力、典型循环、开局与升级方向，并至少经过一次具体场景、失败或无人介入检验。

以下是阶段内容就绪标准，不是用户接受或进入下一阶段的授权。其他阶段的真实内容已经足以供下游使用：覆盖地图中已触发的承重决策均已由明确材料解决、用户确认、用户明确授权代定或明确跳过；临时假设不能关闭承重项。关键抽象已有可观察表现，至少一个高风险点经过场景、边界或失败压力检查。若用户要先看草稿，可交可逆草稿并指出未定事项；不要因为还能扩写或模板还有字段而无限延长访谈。

阶段内容就绪后提交创作交接；自动 QA 可以承接本次制作范围，不能代替用户接受，已关闭必须有用户对实际交接的接受依据。授权引用缺失、跨阶段或与真实消息冲突时阻断提升，不以 Agent 自己的账本循环证明确认。

## 运行组件的最终检查

按 `orchestrator/production-verification.md` 维护具体页面取舍、精确导入 bindings、统一检查结果与浏览器操作用例。production.activeStage 必须跟随现有阶段账本，不滞留旧阶段绕过门禁；未进入的可选阶段不提前要求实现。qa_delivery 复核所有已启用组件，最终运行 production-check validate --final。
