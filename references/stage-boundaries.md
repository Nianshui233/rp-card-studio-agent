# 阶段边界

阶段边界的目的不是把创作割裂，而是防止用户在同一轮同时处理世界规则、人物心理、数值公式和界面实现。一次只解决一种层级的问题，用户更容易判断取舍，锁定内容也更稳定。

## 边界判定方法

准备提出问题前，先判断该问题最终会修改哪个源文件或哪类决定：

- 修改项目环境或交付范围：项目预检。
- 修改项目的一句话方向与核心体验：项目定位。
- 修改输入材料的来源、权重或保留方式：材料整理。
- 修改世界层面的事实、通用规则与稳定内容 ID：世界观。
- 修改某个角色的内在逻辑与表现：角色。
- 修改玩法变量、业务状态机及其语义规则：系统。
- 修改地点、空间、通路与局部事件：场景。
- 修改 storage、运行时路径、版本化更新协议、初始化 profile、opening binding 或 EJS 工程映射：MVU/EJS。
- 修改叙述方式、扮演指令、开场正文或同一开场的呈现变体：叙事与开场。
- 修改展示字段、布局、视觉、交互、降级或 UI 生命周期规格：状态栏/UI。
- 修改世界书激活/插入/概率、媒体文件与预加载、适配器生成、构建、打包、校验和交付清单：整合交付。

一个问题同时会改动两类决定时，应拆成两个阶段问题。先处理作为前置依赖的阶段，再把另一个决定放入跨阶段待办。

## 容易混淆的分界

### 项目定位与世界观

- “故事希望让用户体验被监视下的逃亡”属于项目定位。
- “监视机构如何发现违规者、权限有哪些边界”属于世界观。

定位只决定方向和规模，不提前把方向写成世界规则。

### 世界观与角色

- “所有列车长受誓约约束，不能主动伤害乘客”属于世界观。
- “某位列车长如何理解誓约、何时会钻漏洞”属于角色。

若角色能力需要一个尚不存在的通用规则，先登记世界观缺口，不在角色阶段现场发明。

### 角色与系统

- “角色会因欺骗而更警惕”属于角色行为倾向。
- “欺骗被识破时怀疑值增加 12，达到 70 后拒绝合作”属于系统。

角色阶段可以记录“需要追踪怀疑变化”，但不询问数值范围和公式。

### 系统与 MVU/EJS

- “信任取值 0 到 100，泄密会降低 15”属于系统语义。
- “警戒状态从观察转为调查需要哪些事实，转换后限制哪些行动”属于系统语义。
- “字段路径为 `relationship.trust`，用哪种更新命令写入”属于 MVU/EJS。
- “状态保存在哪个 scope、使用哪个协议版本、开场绑定哪个初始化 profile”属于 MVU/EJS。

系统阶段必须先把业务语义说清，MVU/EJS 才负责可靠实现。

### 世界观与整合交付

- “调度静默是仅 GM 知道的历史事实，稳定 ID 为 `dispatch_silence`”属于世界观。
- “该事实以关键词还是常驻方式激活、插入深度和概率是多少”属于整合交付。

世界观只定义可引用内容，不按宿主参数反向改写世界事实。

### 系统与状态栏/UI

- “怀疑值是否对玩家可见”是系统的信息规则。
- “怀疑值显示成数字、进度条还是文字等级”是状态栏/UI。

系统阶段可以决定可见性，不讨论排版。

状态栏/UI 阶段只能消费已经锁定的可见性、字段语义与数据来源。若某个想展示的字段尚无系统定义，将它记录到系统阶段待办；不要在 UI 阶段现场发明含义、初值、阈值、更新公式或写入者。

### 进入状态栏/UI 与首批问题

- 前一阶段只能问“进入还是跳过状态栏/UI”，不能提前问等级、颜色、组件或交互。
- 真正进入后，第一批必须询问配套 UI 希望是轻型、中型还是重型，说明实际体验差异并给出基于已锁定项目规模的推荐。
- `basic_status` 是旧项目兼容或用户明确只要简单只读状态条时的选项，不应与完整轻型 UI 混为一谈。
- 用户把本阶段完全交给 AI 时，AI 直接选择等级、报告理由并锁定，不再回头重复询问。
- 后续批次依次只处理视觉系统、信息架构与组件、表现与绑定、交互/运行/安全/性能、代表性片段与审查；不得借 UI 讨论重新打开角色、世界、剧情或系统语义。

### 场景与叙事

- “车长室有两处出口，警报后侧门锁死”属于场景。
- “开场是否从用户撬开侧门的动作写起”属于叙事与开场。

场景可以声明“这里需要背景图或警报音效”这一叙事槽位；具体文件、URL、预加载和资源回退属于整合交付。

### 叙事与角色

- “角色说话简短、回避直呼用户姓名”属于角色语言习惯。
- “回复使用第三人称过去时，动作与对白如何排版”属于叙事规则。

### 叙事呈现与状态栏/UI

- “同一开场需要纯文本、聊天记录和 Galgame 三种正文变体”属于叙事与开场。
- “消息内 Galgame 呈现如何布局、更新和清理，以及解析失败显示什么内容”属于状态栏/UI。

呈现变体可以声明能力需求和纯文本 fallback，但不决定消息内组件布局、消息级生命周期或构建入口。

## 跨阶段待办

用户主动提供越界信息时保留它，不追问。建议的数据结构：

<!-- validate: project.schema.json; merge: assets/templates/project.yaml -->
```yaml
cross_stage_backlog:
  - id: backlog_character_conductor_fire_fear
    source_stage: worldbuilding
    target_stage: character
    summary: "列车长害怕明火；在角色阶段决定成因、强度与行为表现。"
    status: open # open | blocking | deferred | resolved
```

记录规则：

- 尽量保留用户原意，不在记录时扩写。
- 一个待办只指定一个主要目标阶段；确实影响多个阶段时拆成多条并标明同一来源。
- 当前阶段只报告“已记录到角色阶段”，不要立刻问“为什么怕火”。
- 进入目标阶段时，把待办作为已知信息或本阶段问题素材。
- 处理完成后标记 `resolved`，避免在后续阶段重复追问。

## 前置缺口与返回

发现当前阶段依赖未满足时，按影响处理：

- **不阻塞**：记录到对应阶段待办，继续当前阶段。
- **重要但可暂定**：给出当前阶段可继续的临时假设，但不锁定；推荐本阶段结束后回补。
- **阻塞**：停止当前阶段的新问题，说明缺少的前置决定及其实际影响，推荐返回对应阶段。

返回时只打开必要字段：

```text
角色阶段发现“角色的复生能力”没有世界通用代价
-> 暂停角色阶段
-> 返回世界观，仅解决复生规则的能力、代价、上限和例外
-> 生成世界观补丁并锁定
-> 恢复角色阶段
```

不要把“返回阶段”变成重做整个阶段。

## 用户主动越级

当用户要求直接讨论未来阶段：

1. 说明当前阶段尚缺哪些门槛。
2. 判断这些缺口是否会使未来阶段无法可靠工作。
3. 可以延后时，记录当前阶段状态并按用户要求切换。
4. 不可延后时，给出最小补齐方案与推荐；不要用一长串问题阻止用户。
5. 用户明确承担风险并坚持跳过时，将阶段记为 `skipped`；风险会阻塞交付则新增 `blocking` 待办，否则新增 `deferred` 待办，并在整合交付前重新检查。

## NSFW 的跨阶段例外

NSFW 只在项目预检确定一次开关，此后不再作为问题主题：

- 启用时，相关信息自然并入角色与状态栏/UI 的既有结构，不创建单独阶段、单独边界问卷或反复确认。
- 不启用时，所有阶段都不得出现对应问题、字段、标题或占位符。
- 这一例外不改变平台硬性安全约束。

## 提问前自检

每次发出问题前快速检查：

1. 这个答案会修改哪个阶段的源文件？
2. 它是否直接服务于当前阶段的充分性门槛？
3. 用户是否已经给过答案或已锁定？
4. 是否可以改成跨阶段待办，而不是现在追问？
5. 问题中的推荐是否真的说明了方向差异和影响？

任一问题不属于当前阶段，就移除或登记待办。
