# 状态栏/UI 阶段

本阶段把已经锁定的玩家可见信息设计成与 RP 项目配套的消息前端系统。它拥有 UI 体验等级、视觉系统、信息架构、组件、数据绑定、消息内交互、降级和运行验收；不拥有世界事实、人物动机、玩法公式或变量业务语义。

角色卡是完整 RP 项目容器，UI 也不应被缩减成一块通用状态框。默认母型直接采用成熟卡的实际成品形态：一条稳定开场标记替换成一份完整入口 HTML，在同一个应用里连续完成版本与依赖、世界介绍、更新信息、游玩指南、开场选择、角色创建、实时预览、保存/重置/复制和确认入局；另一份完整状态 HTML 负责解析模型状态块或读取 MVU 状态，并在页内容纳任务、物品、关系、情报、调查、地图等功能。只有检定、选项、通知或世界更新等输出时机明显不同的内容才拆成独立正则。

## 进入条件

- `workflow.selected_stages` 已在项目预检中选择进入状态栏/UI；前一阶段不得重复询问路线，进入后才询问 UI 内部设计。
- 叙事与开场已经锁定；本阶段可以为开场绑定 UI 标记和导航，但不能改写开场共享语义、剧情事实或玩家交接。
- 需要展示的状态已有玩家可见的语义来源。使用 MVU 时，变量类型、默认值、`source_path`、`runtime_path`、writer、reader 和初始化已经锁定。
- 缺少 UI 所需变量时，只登记跨阶段待办并返回系统或 MVU/EJS 做最小补丁；不得在 UI 阶段现场发明变量语义。

## UI 等级

进入本阶段后的第一批必须询问：

> 与本角色卡/RP 项目配套的 UI，希望做到轻型、轻中型、中型、重型还是超重型？

助手结合题材、审美和期望交互给出推荐，不能只列选项。等级只描述完整 HTML 的前端表现 ambition：够不够华丽、炫酷、好看，主题贴合度如何，动效、交互、JavaScript 联动、便利性和趣味性做到什么程度。它不决定页面数、模块数、字段数、功能数、导航结构、adapter 或代码量。`basic_status` 仅作为用户明确要求的极简兼容路线。

| 等级 | 设计倾向 | 常见形态 | 适用方向 |
| --- | --- | --- | --- |
| `basic_status` | 最少信息与依赖 | 一个简单状态投影或少量文本/HTML | 老项目、字段很少、只求稳定展示 |
| `light` 轻型 | 成熟完整、表现克制 | 完整入口、完整状态、统一主题、成熟排版、必要数据绑定与宿主联动；少量但精细的动效和实用交互 | 希望清楚、顺手、稳定，同时拒绝简陋模板 |
| `light_medium` 轻中型 | 题材拟物与行动联动明显增强 | 页面开始像题材中的档案、终端、手册或操作台；直接行动按钮、反馈与宿主输入/命令联动更丰富 | 希望保留轻快体验，但明显更有代入感和可操作性 |
| `medium` 中型 | 产品级、层次丰富 | 成熟主题系统、切换、筛选、搜索、弹窗、反馈、快捷操作、语义化数据视图和连贯动效 | 希望界面成为完整的游戏伴随系统 |
| `heavy` 重型 | 华丽、沉浸、强主题化 | 多层空间、复杂动效、趣味交互、可视化、深度 JS 联动、宿主协作与氛围演出 | 希望消息内综合应用达到高完成度、高沉浸 |
| `super_heavy` 超重型 | 独立前端 / 0层游玩卡 | 消息 HTML 成为主要游玩界面，具备应用级状态仓库、路由/多视图、弹窗体系、持久化、全屏、观察器、资源管理和深度宿主 API | 希望主要在前端内游玩，聊天层退为叙事与数据通道 |

同一套字段、功能和入口/状态信息架构可以做成轻型、轻中型、中型或重型；差别在前端表现、交互实现和运行时深度，不在功能删减。超重型则发生结构跃迁：它把消息 UI 提升为主要游玩应用，但仍不以源码行数作为门槛。所有等级都没有最低页面数、最低独立正则数、最低代码行数或最低模块数。不要为了等级凑页数，也不要为了“安全”压低创意或技术方案。

“独立前端 / 0层游玩卡”不是让技能修改 SillyTavern 本体，也不是页面级常驻面板。它仍由角色卡携带并在合法消息载体中启动，只是将框架、集中状态、路由、弹窗、持久化、全屏、多视图与宿主桥接整合为一个应用级运行时。选择这一档后，必须把启动、重挂载、消息编辑、聊天切换隔离、状态同步、宿主调用、存储、卸载清理和资源失败纳入真实宿主验收。

成熟的一体化 RP 卡采用“完整核心描述 + 完整入口 HTML + 状态块正则美化”的运行形态。学习并内化稳定字面标记触发整页、完整 HTML 文档、页内多步骤导航、实时预览、本地保存、宿主输入框/消息 API 联动、模型状态块捕获与解析，以及隐藏原始数据后的 HTML 渲染；最终技能与产物不得依赖任何参考文件、参考仓库或外部样本继续存在。视觉正常也不能自动视为交互正确，所有脚本仍需在目标 Blob iframe、Tavern Helper 与当前 SillyTavern 中实际点击验证。

## 玩家端产品原则

消息 UI 是面向玩家的 RP 伴随界面，不是后台 Dashboard、数据库查看器、MVU 调试器或变量 JSON 浏览器。设计顺序必须是“玩家此刻要理解和行动什么”，而不是“变量表里有哪些字段”。首屏应让玩家快速回答：

1. 现在在哪里、什么时间。
2. 正在发生什么。
3. 哪些人物、关系、事务或线索值得注意。
4. 下一步可以做什么。

信息架构遵守以下规则：

- 玩家一级入口通常宜保持精炼；5 个是常见参考，不是硬上限。内部能力数量也不由 UI 等级固定，复杂内容可通过二级册签、分区、折叠、摘要和上下文入口承载。开放世界可采用“概览 / 人物 / 行旅 / 事务 / 案牍”这类玩家任务模型，但名称按项目重写。
- 不把 Schema 分组直接变成导航，不把任意对象递归渲染成键值卡片。当前地点、人物、到访地点、情报、事务、物品、关系和证据应使用各自的语义视图。
- 可见层优先简体中文。稳定英文 ID、变量路径和枚举可以保留在内部，但不得直接显示 `scene_id`、`scene_ref`、`display_name`、`setup_status`、`phase_id`、`current_branch_status`、`baseline_unmodified`、`awaiting_player_declaration` 等开发字段。可靠中文映射不存在时，隐藏该值或显示“状态已记录”，不要把未知英文枚举交给玩家。
- 空数组、空对象、空字符串和 `uninitialized` 不生成空卡。玩家尚未声明的信息应给出说明用途和下一步的引导空状态；普通无内容区域直接省略。
- 长列表按在场/相关性/时间或玩法优先级排序，并使用分组、折叠、限制和渐进披露。不得一次展开几十名人物、几百个字段或整棵变量树。
- 检查重复日期、地点和旅行状态；检查同一 Grid 中长卡是否把其他卡拉出巨大空白。内容顶对齐、避免横向溢出、移动端优先当前行动、44×44px 触控目标和清晰键盘焦点是推荐基线，可按实际玩家设备与美术方向调整。

## 本阶段边界

### 允许询问

- UI 等级：轻型、轻中型、中型、重型、超重型；用户明确只要极简时可选择 `basic_status`。
- UI 服务的主要目标、主要设备、使用频率和可接受的 Tavern Helper 宿主依赖。
- 项目专属的视觉方向、主题媒介、配色、字体策略、布局、纹理、动效和唯一视觉签名。
- 完整页面、页内模块和独立剧情组件清单，导航、一级与二级信息以及移动端重排。
- 已存在玩家可见字段使用什么组件呈现，如何处理空值、集合、大数据量和优先级。
- 标签、折叠、表单、选项、消息写入、Slash 命令、开场 swipe 和运行失败时的降级。
- HTML/CSS/JS 维护源、受管正则、性能预算、安全边界和真实宿主验收。

### 禁止询问

- 不询问新剧情、人物动机、世界秘密、场景结构或玩法公式。
- 不新增变量、writer、阈值含义或状态转换；只绑定已有 `source_path`。
- 不修改开场的共享事实、初始状态、钩子和玩家交接。
- 不把 GM 专用或玩家不可见字段绑定到 UI。
- 不要求修改 SillyTavern、Tavern Helper 或其他插件本体。
- 不把参考卡、远程页面或外部仓库原样复制成项目 UI。
- 允许按功能需要访问 `window.parent`、`parent.document`、`#send_textarea`、`#send_but` 或插件宿主 DOM，不要求先证明公开 API 不可用，也不得仅因版本敏感就删减用户要求的功能。
- 默认不加载 Google Fonts、远程图标库、远程脚本或远程 UI。
- 不把模型维护的字符串直接写入 `innerHTML`；动态值使用 `textContent` 或受控 DOM 节点。

## 六批工作循环

每批都必须遵循：

```text
多项问题 + 已知信息采集 + 2~3 个针对性方向和推荐
→ 用户选定或 AI 在授权范围内决定并报告理由
→ 生成可合并片段
→ 检查本批充分性
→ 只进入下一批 UI 问题
```

### 第一批：体验等级与目标

必须询问：

1. 希望 UI 是轻型、轻中型、中型、重型还是超重型？若用户只想要几个状态值，说明 `basic_status` 的取舍；若希望主要在 UI 内游玩，解释“独立前端 / 0层游玩卡”的代价与收益。
2. 是否需要一份完整项目介绍页，集中承载项目名、版本、依赖、世界导语、更新信息、作者留言、游玩指南与必要内容提示？
3. 是否需要自定义角色创建/开局配置页？入口采用预制开场、自由创角还是两者并存？
4. 用户角色定义采用世界书模板、创角 UI、两者任选还是显式合并？世界书模板默认关闭，填写后再启用。
5. UI 最主要服务于什么：快速状态、世界沉浸、复杂信息管理、开场引导、任务、调查、战斗、选项还是完整游戏式体验？
6. 哪些内容必须成为独立界面，不能只塞进综合状态终端？
7. 是否接受 Tavern Helper 消息 iframe 与公开接口作为完整前端依赖？
8. 桌面、移动端或同等优先？

推荐逻辑：

- 少量字段、无主要玩法模块：建议 `basic_status`，但明确它不是完整轻型 UI。
- 需要完整入口应用、聚合状态应用与成熟但克制的主题表现：建议 `light`。
- 希望界面像题材内真实工具，并有更多直接行动按钮、反馈和宿主输入/命令联动：建议 `light_medium`。
- 希望形成产品级伴随系统，包含丰富层次、语义化视图、搜索筛选、弹窗和连贯反馈：建议 `medium`。
- 希望高度华丽、沉浸、强主题化，并采用复杂动效、可视化和深度宿主协作：建议 `heavy`。
- 希望消息 HTML 成为主要游玩界面，采用集中状态、路由/多视图、复杂弹窗、持久化、全屏与应用级生命周期：建议 `super_heavy`。

用户完全放权时，AI按上述规则选择等级，报告决定与理由后立即锁定，不再重复询问。

片段写入 `src/ui/ui.yaml`，使用 `ui-experience.schema.json`。

### 第二批：视觉系统

助手先从项目自身的时代、材料、器物、组织、技术和叙事媒介推导至少三个方向。每个方向必须说明：

- 4~6 个核心颜色及其用途。
- display/body/utility 三类字体策略；默认使用系统字体或随卡嵌入资源。
- 布局概念与简短 ASCII 线框。
- 边框、圆角、阴影、纹理和动效。
- 一个能代表项目、且只在关键位置使用的视觉签名。
- 可读性、移动端和减少动画模式。

避免把“黑底 + 酸绿色霓虹终端”“暖米色 + 高对比衬线”“通用报纸排版”当作默认答案。只有项目本身真正要求时才使用。

选定后，进行一次自我批评：指出哪个选择仍像通用模板，修改后再锁定。片段写入 `src/ui/theme.yaml`，使用 `ui-theme.schema.json`。

### 第三批：信息架构、完整页面与页内模块

只决定：

- 入口流程：完整项目介绍、预制开场选择、自定义创角/开局配置，以及它们之间的返回与开始路径。介绍页至少可容纳项目名、版本、依赖、世界导语、更新信息、作者留言、游玩指南和必要内容提示；作者留言与内容提示可按项目省略。
- 主要完整页面：哪些功能共享同一触发时机、数据源和导航壳，应合并到同一个 HTML 页面。
- 页内模块：状态、任务、物品、关系、情报、调查、地图、战斗等如何成为同一综合工作区里的标签、分区、抽屉或折叠模块。
- 剧情组件：变量报告、检定、选项、通知等。
- 一级导航、二级折叠、页面之间的路由和移动端顺序。
- 哪些组件由 opening、model 或 runtime 产生。
- 创角字段与 assets/templates/user-character.yaml 的兼容关系：世界书、UI 任一入口都能独立使用；选择 merge 时才定义冲突优先级。

页面引用使用 `ui_component:<id>`，触发标记使用稳定英文机器协议，正则名称使用中文。一个完整页面必须有闭合的 CSS、`body` 结构、JavaScript、数据层和交互层。不要把不同触发时机的内容硬塞进一个无结构巨页；也不要把同一状态工作区里的任务、物品、关系、地图等拆成许多重复外壳的独立正则。判断标准是“是否共享触发、生命周期、导航和数据快照”，不是功能名是否不同。

片段写入：

```text
src/ui/ui.yaml
src/ui/components/*.yaml
```

页面使用 `ui-component.schema.json`。`layout.groups` 表示玩家看见的一级入口或主要分区，通常宜保持精炼；每个 group 可容纳多个具有真实绑定的内部模块。Forge 检查页面完整性、绑定闭合、运行能力和项目专属源码，不用页面数、标签数或模块数推断档位。不得用 8 或 12 个一级标签冒充中型、重型或超重型能力，也不要求为每个功能创建独立正则。

### 第四批：页内模块表现与数据绑定

对每个需要状态的数据槽决定：

- 已锁定的语义 `source_path`。
- 合适的表现组件：文本、数值、进度条、徽章、标签、列表、对象卡、时间线、装备网格、关系卡、任务列表、调查板、地图节点或资源表。
- 标签、缺失值、优先级、范围、色调规则。
- 数组、Record 和大集合的空状态、排序、限制和折叠策略。
- 数据的语义视图：地点只显示名称和当前语境；人物显示姓名、身份、状态和是否在场；到访地点显示首次、最近和次数；情报显示内容、来源和可信度；事务显示义务、后果和待查方向。
- 内部枚举到中文文案的映射，以及无法可靠翻译时的隐藏或中性回退。

禁止使用一个“通用对象递归器”把任意 Record/对象展开成键值卡。

维护源只写语义 `source_path`。Forge 会通过 MVU 账本映射到真实 `runtime_path`，并且只读取 `stat_data`。不得绑定 `display_data` 或 `delta_data`。

片段写入 `src/ui/bindings.yaml`，使用 `ui-bindings.schema.json`。

若发现缺少状态路径，记录跨阶段待办，不在本轮追问变量公式或 writer。

### 第五批：交互、运行与安全

为每个交互分级：

| 等级 | 含义 |
| --- | --- |
| `static` | 纯展示 |
| `local_interaction` | 只操作当前消息 iframe 内部，如标签和折叠 |
| `message_read` | 通过酒馆助手公开 API 读取当前楼原始消息 |
| `message_write` | 通过公开消息 API 写入用户消息 |
| `slash_command` | 通过 `triggerSlash` 调用命令 |
| `opening_swipe` | 通过 `setChatMessages` 切换明确的首消息 swipe |
| `host_bridge` | 通过父页面、输入框、发送按钮或插件 DOM 与 SillyTavern 联动；正常可用，需目标宿主实测 |
| `host_fragile` | 旧项目兼容名称；按 `host_bridge` 处理，不再需要额外授权 |

内置完整 UI 基线使用 `tavern_helper_message + host_required`，但项目可选择 SillyTavern 正则、其他插件接口或自定义 adapter。每个编译页面可以是自包含 fenced HTML，也可以按已登记依赖加载资源。采用 Tavern Helper 消息页时：

- 状态/工作区页面先 `await waitGlobalInitialized('Mvu')`，再用 `getAllVariables()` 读取该消息 iframe 可见的全局→角色→聊天→截至当前楼的合并快照，并从 `stat_data` 取值。
- 绑定读取优先使用有意义的 `runtime_path`；导入或旧项目的 runtime alias 仍为 `uninitialized` 时，允许回退到同一账本声明的语义 `source_path`，不得因此显示空壳。
- 订阅 `Mvu.events.VARIABLE_UPDATE_ENDED` 刷新状态，并在卸载时移除同一事件与 handler。
- 模型输出的 block 组件由 Forge 在宿主正则中建立受控捕获组，把 `$1` 直接送入 iframe；不要在替换后再调用 `getChatMessages()` 重读已经被替换的标记。
- Forge 生成的捕获槽允许使用 `$1`；用户提供的 inline HTML/CSS/JS 仍不得自行写 `$&`、`$1` 等替换令牌。JSON 负载中的 `<`、`>`、`&` 使用 Unicode 转义，避免终止捕获容器。
- 选择提交优先使用 `createChatMessages` 与 `triggerSlash('/trigger')`。
- 开场导航使用明确的 `setChatMessages([{message_id, swipe_id}])`。
- 输入框预填、聚焦、发送按钮或插件功能联动可以直接使用父页面/宿主 DOM；无需为了规避 `parent.document` 改写为复杂替代路线。
- 注册到父页面或插件的监听器、观察器和临时节点必须有稳定所有权并在卸载、切聊或重建时清理。消息 iframe 可能因编辑、重新生成、历史加载或 opening swipe 多次执行；每次执行先替换或清理自己上一次拥有的运行实例，再确定性重绑现有静态节点。
- 静态标签、折叠和按钮优先使用覆盖式 `onclick`，或使用可完整重建的绑定注册表。不得把页面内按钮和导航监听绑定到 `pagehide` 的 `AbortSignal`；opening swipe 可能触发 `pagehide` 而页面随后仍继续使用。MVU 与宿主全局监听仍需在运行实例被替换或真正卸载时显式清理。
- inline JavaScript 中 `&&`、`||` 后必须留空格。Forge 至少扫描 `&&[A-Za-z_$]` 与 `\|\|[A-Za-z_$]`；类似 `current&&current.cleanup` 的源码会因 HTML 命名实体解析被破坏。检查对象是最终正则替换后的脚本，而不只是 YAML 原文，并执行脚本语法检查。
- 动态数据可使用 `textContent`、模板 HTML、`innerHTML`、`insertAdjacentHTML` 或框架渲染；根据数据可信度与目标效果处理转义，最终以实际正确性为准。
- `eval`、`new Function`、浏览器存储、网络请求、WebSocket、CDN 与远程 UI/资源均可按项目需要使用。登记来源、版本、入口、失败表现和生命周期；只有确认会破坏产物或功能时才阻断。
- 所有显示正则 `runOnEdit: true`。
- 提供加载、空、错误、降级和纯文本 fallback。
- 在真实宿主验证前保持 `runtime: not_run`。

片段写入 `ui.yaml` 的 `host_policy/performance/acceptance` 与各组件的 `interactions/delivery/acceptance`。

### 第六批：代表性片段、审查和总汇

在锁定阶段前，至少展示：

1. 一个入口组件片段。
2. 一个主要状态/工作区片段。
3. 一个剧情组件片段。
4. 主题 token 和唯一视觉签名。
5. 桌面与窄屏布局说明。
6. 交互链和纯文本降级。

进行两次自我审查：

- 设计审查：是否仍像对任何项目都会生成的通用模板？主题、字体、结构和文案是否来自本项目？
- 工程审查：绑定、API、安全、性能、`runOnEdit`、降级和宿主证据是否完整？

然后输出阶段总汇、查缺补漏和进入整合阶段的推荐。完全放权时直接锁定并进入下一阶段，不再请求确认。

## 维护源码与编译

完整 UI 使用：

```text
src/ui/ui.yaml
src/ui/theme.yaml
src/ui/bindings.yaml
src/ui/components/*.yaml  # 默认 project_portal + status_terminal；其余只为真正独立的触发块
```

页面可以直接提供 `source.mode: inline` 的完整 HTML/CSS/JS，也可以使用生成页面、页内模块和项目 token。根据效果和维护成本选择；项目专属源码、远程资源、浏览器存储、宿主联动或动态渲染不需要额外许可，只需把依赖和兼容性写清楚。任务中心、物资中心、关系中心等模板只作为页内设计素材，默认吸收到综合状态应用；启动页、介绍页、开场选择和创角页也默认吸收到 `project_portal`，只有确实需要不同触发或独立生命周期时才拆开。

Forge 将这些源编译为：

```text
UI 体验 + 主题 + 绑定 + 组件
→ 跨源与变量引用检查
→ 正确性与兼容性扫描
→ 自包含 fenced HTML/CSS/JS
→ 少量中文命名完整页面正则 + 必要的剧情块正则
→ CharacterBook 模型输出组件协议
→ 最终单一角色卡 JSON
```

组件正则使用由组件 ID 稳定生成的 UUID，带受管追踪信息；重复构建必须幂等。用户正则和未知扩展不被覆盖。

## `basic_status` 兼容路线

旧 `status-ui.schema.json 1.x` 与 `src/ui/status-ui.yaml` 继续可读。它适合少量只读字段和最小依赖：

- `embedded + sillytavern_regex`：简单静态文字/HTML，使用 Tavern Helper 宏，不能实现可靠逐楼快照、条件状态或复杂交互。
- `tavern_helper_message + host_required`：旧单状态栏消息 iframe 候选，仍需真实宿主验收。

旧项目不会自动升级成 UI 2.0。用户要求升级时，应重新进入本阶段，从等级和目标开始设计；保留未知和用户自写正则，只替换技能可识别的受管规则。

## MVU 与占位符

- 完整入口应用优先使用稳定字面标记，例如 `Create_character`，让开场白保持极简且正则只替换一次。完整状态应用通常使用 `<StatusPlaceHolderImpl/>` 或捕获式状态块。
- 非 MVU 路线：用一条常驻 CharacterBook 合同要求模型在每次助手回复末尾输出稳定状态代码块；一条正则隐藏或捕获原始块；一条完整 HTML 正则解析捕获内容并渲染。不要把每个状态字段拆成一条正则。
- MVU 路线：初始化块、更新块隐藏、变量提交、状态占位符和 HTML 读取必须形成闭环；状态 HTML优先读当前楼变量，必要时兼容捕获文本回退。
- 默认与备选开场由 Forge 幂等保留唯一状态占位符。
- 启用 MVU 后，后续状态占位符由 MVU 自动追加，模型不得输出。
- 未启用 MVU但启用状态终端时，才生成模型末尾输出唯一占位符的 CharacterBook 合同。
- 由模型产生的检定、选项、通知等组件，Forge 自动生成中文 CharacterBook 协议条目，规定标记、负载格式、顺序和降级。
- 模型组件标记位于叙事之后、变量更新块之前；同一组件在一条回复中最多输出一次。

## 完成门槛

- UI 等级、目标、设备优先级、完整项目介绍页、创角/开局配置路线、预制/自由开场关系、用户角色模板策略和所选宿主能力已经锁定；等级没有被误用为固定页数或固定 adapter。
- 玩家能快速理解当前处境、重要信息和可执行动作；中文玩家体验、术语、布局和视觉层级符合项目目标。英文机器键、技术 ID 与枚举若有意展示，应有明确用途或可理解映射。
- HTML、CSS、JavaScript、JSON 和正则可解析；SillyTavern 替换令牌、HTML 实体碰撞与转义不会破坏最终代码。
- 所有实际使用的组件、路由、绑定、变量、脚本入口和模型输出协议引用闭合；数据能读到，按钮与宿主联动能执行预期动作。
- 远程资源、网络接口、浏览器存储、父页面 DOM、插件内部 API、动态代码或自定义 adapter 如被采用，已记录 URL/版本/入口、依赖、失败表现、生命周期清理和已知维护后果；它们本身不是阻断项。
- 页面级常驻状态栏/面板没有被创建；状态和功能位于聊天消息或用户明确选择的其他合法载体中。
- 不要求修改 SillyTavern、Tavern Helper 或其他插件本体。
- 响应式、触控尺寸、键盘、色彩、减少动画、一级入口数量、空状态和性能预算按目标玩家与项目场景验收。375px、44px、五个入口等是常用检查基线，不是普遍硬门槛。
- 没有真实宿主证据时仍可完成设计、构建和候选交付，但必须保持 `runtime: not_run`，不能把离线成功冒充实机通过。
