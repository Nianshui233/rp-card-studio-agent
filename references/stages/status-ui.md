# 状态栏/UI 阶段

本阶段把已经锁定的玩家可见信息设计成与 RP 项目配套的消息前端系统。它拥有 UI 体验等级、视觉系统、信息架构、组件、数据绑定、消息内交互、降级和运行验收；不拥有世界事实、人物动机、玩法公式或变量业务语义。

角色卡是完整 RP 项目容器，UI 也不应被缩减成一块通用状态框。完整 UI 采用“少量完整消息页面 + 页内多个功能模块 + 少量独立剧情块”的结构：启动/介绍/创建可以形成入口流程，综合状态终端在一份完整 HTML 中容纳任务、物品、关系、情报、调查、地图等页签或分区；只有变量报告、检定、选项、通知等具有不同输出时机的内容才拆成独立正则组件。

## 进入条件

- 用户已经确认进入状态栏/UI 阶段；在前一阶段结束时只能问“进入还是跳过”，不能提前询问 UI 内部设计。
- 叙事与开场已经锁定；本阶段可以为开场绑定 UI 标记和导航，但不能改写开场共享语义、剧情事实或玩家交接。
- 需要展示的状态已有玩家可见的语义来源。使用 MVU 时，变量类型、默认值、`source_path`、`runtime_path`、writer、reader 和初始化已经锁定。
- 缺少 UI 所需变量时，只登记跨阶段待办并返回系统或 MVU/EJS 做最小补丁；不得在 UI 阶段现场发明变量语义。

## UI 等级

进入本阶段后的第一批必须询问：

> 与本角色卡/RP 项目配套的 UI，希望做到轻型、中型还是重型？

助手必须结合项目规模给出推荐和实际影响，不能只列选项。`basic_status` 仅作为兼容或用户明确要求的极简路线，不属于完整 UI 的轻型等级。

| 等级 | 最低规模 | 能力门槛 | 典型适用项目 |
| --- | ---: | --- | --- |
| `basic_status` | 1 个状态投影 | 少量字段、无复杂交互、稳定优先 | 老项目、三五个字段、明确只要简单状态条 |
| `light` 轻型 | 至少 3 个完整页面；主工作区至少 4 个模块 | 至少一个入口、一个综合状态终端、一个剧情组件；完整项目主题、响应式、空/错/降级态 | 以社区“轻度前端”规模为校准的单一主体验 |
| `medium` 中型 | 至少 4 个完整页面；主工作区至少 8 个模块 | 轻型全部能力，加玩家设置和至少两类剧情组件；任务、物品、关系、情报等优先并入综合工作区 | 多角色、开放世界、多个长期玩法模块 |
| `heavy` 重型 | 至少 5 个完整页面；主工作区至少 12 个模块 | 中型全部能力，加至少三类剧情组件、hub/mixed 导航、复杂集合和性能策略 | 将角色卡作为完整 RP 应用的复杂模拟项目 |

“尸变纪元”只用作轻型规模与页面组织方法的校准参考：它的状态终端是一份完整 HTML，内部用多个导航页承载宏观态势、个人、小队、庇护所、载具、装备、联系人、情报和扫描；变量报告、检定和选项则按不同触发时机独立。不得复制其代码、主题、中文标记、远程字体或具体世界内容；父页面/宿主 DOM 联动可以按本项目需求重新设计。

代码行数不是等级标准。组件覆盖、视觉完成度、数据绑定、交互、响应式、安全和宿主验收才是等级标准。

## 玩家端产品原则

消息 UI 是面向玩家的 RP 伴随界面，不是后台 Dashboard、数据库查看器、MVU 调试器或变量 JSON 浏览器。设计顺序必须是“玩家此刻要理解和行动什么”，而不是“变量表里有哪些字段”。首屏应让玩家快速回答：

1. 现在在哪里、什么时间。
2. 正在发生什么。
3. 哪些人物、关系、事务或线索值得注意。
4. 下一步可以做什么。

信息架构遵守以下规则：

- 玩家一级入口通常不超过 5 个。内部 4/8/12 个能力模块不等于 4/8/12 个一级标签；多余能力通过二级册签、分区、折叠、摘要和上下文入口承载。开放世界可采用“概览 / 人物 / 行旅 / 事务 / 案牍”这类玩家任务模型，但名称必须按项目重写。
- 不把 Schema 分组直接变成导航，不把任意对象递归渲染成键值卡片。当前地点、人物、玩家档案、到访地点、情报、事务、物品、关系和证据应使用各自的语义视图。
- 可见层优先简体中文。稳定英文 ID、变量路径和枚举可以保留在内部，但不得直接显示 `scene_id`、`scene_ref`、`display_name`、`setup_status`、`phase_id`、`current_branch_status`、`baseline_unmodified`、`awaiting_player_declaration` 等开发字段。可靠中文映射不存在时，隐藏该值或显示“状态已记录”，不要把未知英文枚举交给玩家。
- 空数组、空对象、空字符串和 `uninitialized` 不生成空卡。玩家尚未声明的信息应给出说明用途和下一步的引导空状态；普通无内容区域直接省略。
- 长列表按在场/相关性/时间或玩法优先级排序，并使用分组、折叠、限制和渐进披露。不得一次展开几十名人物、几百个字段或整棵变量树。
- 检查重复日期、地点和旅行状态；检查同一 Grid 中长卡是否把其他卡拉出巨大空白；卡片网格使用内容顶对齐，页面不得横向溢出。移动端把当前行动信息置前，所有可点击目标至少 44×44px，并提供清晰的键盘焦点。

## 本阶段边界

### 允许询问

- UI 等级：轻型、中型、重型；用户明确只要极简时可选择 `basic_status`。
- UI 服务的主要目标、主要设备、使用频率和可接受的 Tavern Helper 宿主依赖。
- 项目专属的视觉方向、主题媒介、配色、字体策略、布局、纹理、动效和唯一视觉签名。
- 完整页面、页内模块和独立剧情组件清单，导航、一级与二级信息以及移动端重排。
- 已存在玩家可见字段使用什么组件呈现，如何处理空值、集合、大数据量和优先级。
- 标签、折叠、表单、选项、消息写入、Slash 命令、开场 swipe 和运行失败时的降级。
- HTML/CSS/JS 维护源、受管正则、性能预算、安全边界和真实宿主验收。

### 禁止询问

- 不询问新剧情、人物动机、世界秘密、场景结构或玩法公式。
- 不新增变量、writer、阈值含义或状态转换；只绑定已有 `source_path`。
- 不修改开场的共享事实、初始状态、钩子和玩家交接。
- 不把 GM 专用或玩家不可见字段绑定到 UI。
- 不要求修改 SillyTavern、Tavern Helper 或其他插件本体。
- 不把参考卡、远程页面或外部仓库原样复制成项目 UI。
- 允许按功能需要访问 `window.parent`、`parent.document`、`#send_textarea`、`#send_but` 或插件宿主 DOM，不要求先证明公开 API 不可用，也不得仅因版本敏感就删减用户要求的功能。
- 默认不加载 Google Fonts、远程图标库、远程脚本或远程 UI。
- 不把模型维护的字符串直接写入 `innerHTML`；动态值使用 `textContent` 或受控 DOM 节点。

## 六批工作循环

每批都必须遵循：

```text
多项问题 + 已知信息采集 + 2~3 个针对性方向和推荐
→ 用户选定或 AI 在授权范围内决定并报告理由
→ 生成可合并片段
→ 检查本批充分性
→ 只进入下一批 UI 问题
```

### 第一批：体验等级与目标

必须询问：

1. 希望 UI 是轻型、中型还是重型？若用户只想要几个状态值，说明 `basic_status` 的取舍。
2. UI 最主要服务于什么：快速状态、世界沉浸、复杂信息管理、开场引导、玩家创建、任务、调查、战斗、选项还是完整游戏式体验？
3. 哪些内容必须成为独立界面，不能只塞进综合状态终端？
4. 是否接受 Tavern Helper 消息 iframe 与公开接口作为完整前端依赖？
5. 桌面、移动端或同等优先？

推荐逻辑：

- 少量字段、无主要玩法模块：建议 `basic_status`，但明确它不是完整轻型 UI。
- 需要启动/介绍、综合终端和少量剧情组件：建议 `light`。
- 任务、物品、NPC/关系、势力、情报、调查中有三类以上主要模块：建议 `medium`。
- 多流程、复杂导航、地图/调查板/关系网、搜索筛选、批量数据或多数玩法都需要 UI：建议 `heavy`。

用户完全放权时，AI按上述规则选择等级，报告决定与理由后立即锁定，不再重复询问。

片段写入 `src/ui/ui.yaml`，使用 `ui-experience.schema.json`。

### 第二批：视觉系统

助手先从项目自身的时代、材料、器物、组织、技术和叙事媒介推导至少三个方向。每个方向必须说明：

- 4~6 个核心颜色及其用途。
- display/body/utility 三类字体策略；默认使用系统字体或随卡嵌入资源。
- 布局概念与简短 ASCII 线框。
- 边框、圆角、阴影、纹理和动效。
- 一个能代表项目、且只在关键位置使用的视觉签名。
- 可读性、移动端和减少动画模式。

避免把“黑底 + 酸绿色霓虹终端”“暖米色 + 高对比衬线”“通用报纸排版”当作默认答案。只有项目本身真正要求时才使用。

选定后，进行一次自我批评：指出哪个选择仍像通用模板，修改后再锁定。片段写入 `src/ui/theme.yaml`，使用 `ui-theme.schema.json`。

### 第三批：信息架构、完整页面与页内模块

只决定：

- 入口流程：启动、介绍、开场选择、玩家创建。
- 主要完整页面：哪些功能共享同一触发时机、数据源和导航壳，应合并到同一个 HTML 页面。
- 页内模块：状态、任务、物品、关系、情报、调查、地图、战斗等如何成为同一综合工作区里的标签、分区、抽屉或折叠模块。
- 剧情组件：变量报告、检定、选项、通知等。
- 一级导航、二级折叠、页面之间的路由和移动端顺序。
- 哪些组件由 opening、model 或 runtime 产生。

页面引用使用 `ui_component:<id>`，触发标记使用稳定英文机器协议，正则名称使用中文。一个完整页面必须有闭合的 CSS、`body` 结构、JavaScript、数据层和交互层。不要把不同触发时机的内容硬塞进一个无结构巨页；也不要把同一状态工作区里的任务、物品、关系、地图等拆成许多重复外壳的独立正则。判断标准是“是否共享触发、生命周期、导航和数据快照”，不是功能名是否不同。

片段写入：

```text
src/ui/ui.yaml
src/ui/components/*.yaml
```

页面使用 `ui-component.schema.json`。`layout.groups` 表示玩家看见的一级入口或主要分区，通常不得超过 5 个；每个 group 可容纳多个具有真实绑定的内部模块。轻中重能力门槛由 Forge 检查完整页面数、入口/设置/剧情覆盖，以及综合工作区内具有真实绑定的内部模块数；不得用 8 或 12 个一级标签冒充中型或重型能力，也不要求为每个功能创建独立正则。

### 第四批：页内模块表现与数据绑定

对每个需要状态的数据槽决定：

- 已锁定的语义 `source_path`。
- 合适的表现组件：文本、数值、进度条、徽章、标签、列表、对象卡、时间线、装备网格、关系卡、任务列表、调查板、地图节点或资源表。
- 标签、缺失值、优先级、范围、色调规则。
- 数组、Record 和大集合的空状态、排序、限制和折叠策略。
- 数据的玩家语义视图：地点只显示名称和当前语境；人物显示姓名、身份、状态和是否在场；到访地点显示首次、最近和次数；情报显示内容、来源和可信度；事务显示义务、后果和待查方向；玩家档案只显示用户已经声明的字段。
- 内部枚举到中文文案的映射，以及无法可靠翻译时的隐藏或中性回退。

禁止使用一个“通用对象递归器”把任意 Record/对象展开成键值卡。

维护源只写语义 `source_path`。Forge 会通过 MVU 账本映射到真实 `runtime_path`，并且只读取 `stat_data`。不得绑定 `display_data` 或 `delta_data`。

片段写入 `src/ui/bindings.yaml`，使用 `ui-bindings.schema.json`。

若发现缺少状态路径，记录跨阶段待办，不在本轮追问变量公式或 writer。

### 第五批：交互、运行与安全

为每个交互分级：

| 等级 | 含义 |
| --- | --- |
| `static` | 纯展示 |
| `local_interaction` | 只操作当前消息 iframe 内部，如标签和折叠 |
| `message_read` | 通过酒馆助手公开 API 读取当前楼原始消息 |
| `message_write` | 通过公开消息 API 写入用户消息 |
| `slash_command` | 通过 `triggerSlash` 调用命令 |
| `opening_swipe` | 通过 `setChatMessages` 切换明确的首消息 swipe |
| `host_bridge` | 通过父页面、输入框、发送按钮或插件 DOM 与 SillyTavern 联动；正常可用，需目标宿主实测 |
| `host_fragile` | 旧项目兼容名称；按 `host_bridge` 处理，不再需要额外授权 |

默认完整 UI 使用 `tavern_helper_message + host_required`。每个编译页面都是自包含 fenced HTML，包含 CSS、主体结构和 JS。生成代码必须：

- 状态/工作区页面先 `await waitGlobalInitialized('Mvu')`，再用 `getAllVariables()` 读取该消息 iframe 可见的全局→角色→聊天→截至当前楼的合并快照，并从 `stat_data` 取值。
- 绑定读取优先使用有意义的 `runtime_path`；导入或旧项目的 runtime alias 仍为 `uninitialized` 时，允许回退到同一账本声明的语义 `source_path`，不得因此显示空壳。
- 订阅 `Mvu.events.VARIABLE_UPDATE_ENDED` 刷新状态，并在卸载时移除同一事件与 handler。
- 模型输出的 block 组件由 Forge 在宿主正则中建立受控捕获组，把 `$1` 直接送入 iframe；不要在替换后再调用 `getChatMessages()` 重读已经被替换的标记。
- Forge 生成的捕获槽允许使用 `$1`；用户提供的 inline HTML/CSS/JS 仍不得自行写 `$&`、`$1` 等替换令牌。JSON 负载中的 `<`、`>`、`&` 使用 Unicode 转义，避免终止捕获容器。
- 选择提交优先使用 `createChatMessages` 与 `triggerSlash('/trigger')`。
- 开场导航使用明确的 `setChatMessages([{message_id, swipe_id}])`。
- 输入框预填、聚焦、发送按钮或插件功能联动可以直接使用父页面/宿主 DOM；无需为了规避 `parent.document` 改写为复杂替代路线。
- 注册到父页面或插件的监听器、观察器和临时节点必须有稳定所有权并在卸载、切聊或重建时清理。消息 iframe 可能因编辑、重新生成、历史加载或 opening swipe 多次执行；每次执行先替换或清理自己上一次拥有的运行实例，再确定性重绑现有静态节点。
- 静态标签、折叠和按钮优先使用覆盖式 `onclick`，或使用可完整重建的绑定注册表。不得把页面内按钮和导航监听绑定到 `pagehide` 的 `AbortSignal`；opening swipe 可能触发 `pagehide` 而页面随后仍继续使用。MVU 与宿主全局监听仍需在运行实例被替换或真正卸载时显式清理。
- inline JavaScript 中 `&&`、`||` 后必须留空格。Forge 至少扫描 `&&[A-Za-z_$]` 与 `\|\|[A-Za-z_$]`；类似 `current&&current.cleanup` 的源码会因 HTML 命名实体解析被破坏。检查对象是最终正则替换后的脚本，而不只是 YAML 原文，并执行脚本语法检查。
- 动态数据使用 `textContent` 或受控 DOM 节点。
- 禁止 `eval`、`new Function`、未登记存储、网络请求和远程 UI。
- 所有显示正则 `runOnEdit: true`。
- 提供加载、空、错误、降级和纯文本 fallback。
- 在真实宿主验证前保持 `runtime: not_run`。

片段写入 `ui.yaml` 的 `host_policy/performance/acceptance` 与各组件的 `interactions/delivery/acceptance`。

### 第六批：代表性片段、审查和总汇

在锁定阶段前，至少展示：

1. 一个入口组件片段。
2. 一个主要状态/工作区片段。
3. 一个剧情组件片段。
4. 主题 token 和唯一视觉签名。
5. 桌面与窄屏布局说明。
6. 交互链和纯文本降级。

进行两次自我审查：

- 设计审查：是否仍像对任何项目都会生成的通用模板？主题、字体、结构和文案是否来自本项目？
- 工程审查：绑定、API、安全、性能、`runOnEdit`、降级和宿主证据是否完整？

然后输出阶段总汇、查缺补漏和进入整合阶段的推荐。完全放权时直接锁定并进入下一阶段，不再请求确认。

## 维护源码与编译

完整 UI 使用：

```text
src/ui/ui.yaml
src/ui/theme.yaml
src/ui/bindings.yaml
src/ui/components/*.yaml  # 每个文件代表一个完整消息页面或真正独立的触发块
```

页面也可以提供经过安全扫描的 `source.mode: inline` HTML/CSS/JS。默认优先使用生成页面、页内模块和项目 token；只有生成结构不足以表达项目独特体验时才写项目专属源码。任务中心、物资中心、关系中心等模板仍可作为设计素材，但默认应吸收到综合工作区的内部模块，只有确实需要不同触发或独立生命周期时才成为单独页面。

Forge 将这些源编译为：

```text
UI 体验 + 主题 + 绑定 + 组件
→ 跨源与变量引用检查
→ 安全扫描
→ 自包含 fenced HTML/CSS/JS
→ 少量中文命名完整页面正则 + 必要的剧情块正则
→ CharacterBook 模型输出组件协议
→ 最终单一角色卡 JSON
```

组件正则使用由组件 ID 稳定生成的 UUID，带受管追踪信息；重复构建必须幂等。用户正则和未知扩展不被覆盖。

## `basic_status` 兼容路线

旧 `status-ui.schema.json 1.x` 与 `src/ui/status-ui.yaml` 继续可读。它适合少量只读字段和最小依赖：

- `embedded + sillytavern_regex`：简单静态文字/HTML，使用 Tavern Helper 宏，不能实现可靠逐楼快照、条件状态或复杂交互。
- `tavern_helper_message + host_required`：旧单状态栏消息 iframe 候选，仍需真实宿主验收。

旧项目不会自动升级成 UI 2.0。用户要求升级时，应重新进入本阶段，从等级和目标开始设计；保留未知和用户自写正则，只替换技能可识别的受管规则。

## MVU 与占位符

- 完整 UI 的状态终端通常使用 `<StatusPlaceHolderImpl/>`；其他组件使用自己的稳定标记。
- 默认与备选开场由 Forge 幂等保留唯一状态占位符。
- 启用 MVU 后，后续状态占位符由 MVU 自动追加，模型不得输出。
- 未启用 MVU但启用状态终端时，才生成模型末尾输出唯一占位符的 CharacterBook 合同。
- 由模型产生的检定、选项、通知等组件，Forge 自动生成中文 CharacterBook 协议条目，规定标记、负载格式、顺序和降级。
- 模型组件标记位于叙事之后、变量更新块之前；同一组件在一条回复中最多输出一次。

## 完成门槛

- UI 等级、目标、设备优先级和宿主依赖已经锁定。
- 主题不是占位或通用模板；存在项目专属的颜色、字体策略、布局概念和唯一视觉签名。
- 完整页面数、页内有效模块数和剧情触发覆盖符合等级门槛；不是复制外壳或空标签凑数。
- 所有组件引用、导航路由和绑定闭合。
- 每个绑定都引用已声明、玩家可见且允许 `status_ui` 读取的变量；Forge 能映射到 `stat_data` 真实运行路径。
- 入口、主要工作区和剧情组件都有纯文本 fallback。
- 所有模型输出组件都有 CharacterBook 协议。
- 交互符合项目需要；父页面/宿主 DOM 联动允许使用，常驻状态栏/面板仍禁止；没有失控网络、远程 UI、动态代码和危险 HTML sink。
- 桌面、375px 窄屏、键盘、至少 44px 触控目标、色彩独立和减少动画策略完整。卡片内容顶对齐，无横向溢出、巨大空白或固定元素遮挡。
- 一级入口不超过 5 个；内部模块按玩家任务组织并使用二级结构承载，不直接照搬 Schema。
- 玩家可见文案为自然中文，无开发字段、技术 ID、未知英文枚举、重复事实或递归对象转储。
- 性能预算、集合策略、引导性空状态、错误与降级状态完整。
- 组件正则名称使用中文，机器 ID 和标记使用稳定英文。
- `runtime: not_run` 与真实宿主证据严格区分，没有把离线成功冒充实机通过。真实验收同时覆盖未初始化开场与已有真实数据的开场，并覆盖 opening swipe、消息编辑、重新生成、iframe 二次执行、切聊和刷新后导航与按钮仍可用且不重复触发。
