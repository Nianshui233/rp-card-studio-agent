# 状态栏 / UI 阶段（可选）

本阶段只创作进入RP后的持续消息前端：状态、物品、关系、任务、地图、线索、调查、通知和交互工具。首条消息的项目介绍、路线选择和创角前端已经属于“叙事与开场”阶段，不在这里重复设计。

## 第一批必须问

> 进入游戏后的持续状态/功能 UI 希望做到轻型、轻中型、中型、重型还是超重型？

同时询问题材视觉方向、主要设备、最常查看/操作的状态与功能。不要在本阶段重新询问开场介绍页或创角前端；它们由上一阶段独立决定。

等级衡量的是玩家实际得到的完成度、华丽度、主题沉浸、交互与 JS 深度。技能内置的 `assets/examples/self-contained-rp/src/runtime/ui/潮痕状态栏.html` 所代表的规模与体验是“轻型”的基准，不是重型示例：

| 等级 | 含义 |
| --- | --- |
| 轻型 | 一份完整、成熟、主题统一的持续状态应用。至少具备清晰内部导航、多类数据视图、搜索/筛选/折叠/详情等真实信息操作、至少一种真实宿主行动、确认或空/错/加载等反馈、响应式适配、真实数据绑定与完整主题视觉。交互可以克制，但不能只是几项数值加进度条的小面板。 |
| 轻中型 | 完整保留轻型基线，并明显增加操作便利、信息组织、行动按钮、宿主联动、反馈、动效或趣味交互中的多个方面。 |
| 中型 | 在轻型基线上形成产品级信息架构和复合操作：更多主要功能区、组合搜索/筛选、详情与编辑流程、任务/物品/地图/关系等真实操作，以及更可靠的 UI 状态保持。 |
| 重型 | 在中型基础上加入强主题演出、复杂功能联动、大量可直接发起的游戏行为、丰富趣味交互、深度宿主协作和可靠生命周期。 |
| 超重型 | 独立前端/0层游玩应用；完整继承前述能力，消息 HTML 成为主要游玩表面，并具备应用级路由、状态管理、持久化、复杂宿主协作与完整生命周期。 |

等级不规定页数、字段数、正则数、文件字节或代码行数。技能内置样本只是帮助理解其成熟规模，不是生成配额；轻型不能用短代码和静态假数据降级，超重型也不能用堆代码冒充体验。后续每一档都必须说明相对轻型基线真正新增了哪些玩家功能、交互、便利性、视觉演出或宿主联动。

## 体验证据用于复盘，不是填表门禁

在 `status-ui.yaml#/status_ui/experience_evidence` 中记录玩家可验证的事实：

- `baseline.navigation`：页签、分区导航、抽屉或等价的信息路径；
- `baseline.data_views`：状态、环境、物品、关系、任务、日志等实际数据视图；
- `baseline.information_tools`：搜索、筛选、折叠、详情、排序等真实信息操作；
- `baseline.host_actions`：填充/发送输入、slash command、变量写入、消息操作等真实联动；
- `baseline.feedback_states`：确认、加载、空态、成功、失败、回退或重复点击处理；
- `baseline.responsive_checks`：窄屏、触控、中文长文本、软键盘、减少动画等实测/待测项；
- `baseline.theme_features`：与题材绑定的颜色、材质、图形、动效和信息语言；
- `baseline.data_binding`：每类核心数据从何处读取、何时刷新、缺失时如何处理；
- `level_advancements`：高于轻型时，按便利性、信息架构、交互深度、视觉表现、宿主联动、持久化/生命周期记录实际增量；
- `primary_play_surface`：仅超重型/0层游玩时为 `true`。

这些字段用于阶段总结与玩家验收，不按非空项目数量决定等级。不适用的维度可以留空并说明理由；已经填写的证据应尽量指向 HTML/JS、正则、脚本、变量协议或真实宿主验收，避免只写“高级交互”“丰富功能”。

## 渲染路线按项目选择

`regex_replace` 是常见默认路线，但不是唯一合法答案。每个 surface 可以选择 `regex_replace`、`helper_script`、`ejs`、`inline_html`、`framework` 或 `existing`。校验只检查所选路线的真实承重组件，不要求其他路线的文件和正则。

开场与持续 UI 默认职责分离，但可以通过 `opening_relationship: shared_source / opening_to_runtime / unified_zero_layer` 明确共享源码、开场转运行或0层统一应用。

## 先定功能面，不拆碎组件

通常优先形成一份完整的持续状态应用：在一个统一界面内承载本项目需要的状态、任务、物品、关系、情报、地图、调查、事件等内部页面。检定结果、临时选项、通知等仅在生命周期不同且独立出现时再拆成单独正则。

不要把一个功能页里的每张卡片、标签或按钮各自做成独立 HTML/正则，也不要把首楼介绍/创角应用作为一个 `status_ui.surface` 混进来。

## 维护源码

推荐：

```text
src/runtime/ui/
  状态界面.html
  检定结果.html          # 仅按需
```

每份是完整 HTML 文档或可构建为完整文档的小项目，通常包含：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width,initial-scale=1">
  <style>/* 项目专属完整样式 */</style>
</head>
<body>
  <!-- 一个功能面内的全部页面与组件 -->
  <script type="module">/* 真实交互、数据读取和宿主联动 */</script>
</body>
</html>
```

不要把 HTML 重新拆成 `ui.yaml + theme.yaml + components/*.yaml` 再由通用代码合成。确有现成前端工程时可以编译，但构建产物必须是项目专属完整 HTML，而不是通用模板。

## 数据与运行链

设计前明确：

```text
原始数据来自哪里
→ 当前楼层如何读取
→ 哪些值是持久状态、草稿、UI 状态或派生显示
→ 何时刷新
→ 用户动作写到哪里
→ 失败、空值、加载与降级怎样显示
```

MVU 状态栏通常等待 `Mvu` 就绪，再用 `Mvu.getMvuData({ type: 'message', message_id: getCurrentMessageId() })` 读取当前楼层 `stat_data`，并监听目标版本的实际更新事件。`display_data` / `delta_data` 在当前 MVU 源码中已标为 deprecated，不作为新 UI 的唯一数据源。非 MVU 状态栏可捕获模型输出的稳定状态块。不要让正则凭空“把变量变成 HTML”，也不要把示例初值硬编码成运行数据。

## 标记生产链

每个 `status_ui.surfaces[]` 不仅要记录 `marker` 和 HTML 文件，还要说明谁负责在真实消息中生产这个标记：

```yaml
emission:
  producer: model_output        # opening_message / framework / helper_script / user_action / existing
  cadence: every_assistant_message
  source_ref: wb_status_output_contract
  evidence: []
```

- 每轮消息状态栏若由模型生产，默认建立一个独立、常驻、模型可见的中文 CharacterBook 输出契约条目，明确命令模型在每次回复末尾输出同一个标记，并用 `source_ref` 指向该条目。
- MVU 只负责变量并不等于它会输出项目自定义标记。只有目标框架确实追加与正则相同的标记时，才能选择 `framework` 并记录证据。
- Tavern Helper 脚本、按钮或成熟既有实现也可以作为生产者，但必须记录实际脚本/行为与证据，不能只写“应该会输出”。
- 非 MVU 卡通常让模型输出完整、稳定的 XML 状态块，例如 `<我非我状态>...</我非我状态>`；专门的世界书输出契约应说明字段、顺序、缺省值、禁止正文外泄和每轮输出位置，正则再捕获整个块并渲染 HTML。

Forge 会检查生产者、标记和正则消费者是否闭合。只有 HTML 和捕获正则、却没有任何消息生产者的状态栏属于确定断链。

按钮可以读取/写入消息或变量、调用 slash command、填充/发送 SillyTavern 输入框、打开弹窗、操作世界书或调用宿主 API。使用父页面 DOM 和私有 API是允许的；记录版本耦合和失败表现并真机验证即可。

## 中文玩家体验

- 玩家可见标题、标签、空状态、错误与按钮默认使用自然中文；
- 不直接暴露 `runtime_path`、snake_case、内部 ID 或英文枚举；
- 中文字体、行高、字重、标点、换行与长文本经过实际检查；
- 主要信息优先，次要信息用标签页、折叠、抽屉或详情层渐进展示；
- 触控区域、键盘焦点、反馈、滚动、窄屏、软键盘和减少动画均按实际功能处理；
- 视觉主题来自世界本身，而不是默认蓝色仪表盘或代码工程风。

## 生命周期与验证

检查真实消息渲染、iframe/Blob URL 模式、脚本重复注册、楼层身份、编辑、Swipe、重载、聊天切换、窄屏、长中文文本、空数据、错误数据、按钮重复点击和控制台首个因果错误。

页面级常驻状态栏/面板仍不创建；本阶段所有常规 UI 位于聊天消息或用户明确选择的合法卡内载体。超重型同层前端也必须由角色卡携带，不能修改宿主本体。

## 完成门槛

- UI 等级与主题选择有明确理由；
- 轻型以内置原创样本所代表的完整持续状态应用为质量基准；证据用于复盘，不以填写数量阻断；
- 轻中型及以上明确记录了相对轻型新增的功能、交互和体验；超重型明确把持续消息 HTML 作为主要游玩表面；
- 持续状态功能面、内部导航和进入RP后的用户旅程清楚；
- 没有把首条介绍、路线选择或创角前端混进 `status_ui.surfaces`；
- 实际 HTML/CSS/JS 已生成，而非只有组件配置；
- 所有可见字段都有真实数据来源和中文显示映射；
- 所有按钮有真实处理、反馈和失败状态；
- 正则触发标记、提示词分离和宿主依赖明确；
- 每个 UI 标记都有真实生产者；每轮模型输出标记有独立、常驻、模型可见的世界书输出契约，或有已验证的框架/脚本替代；
- 没有真实宿主证据时标记 `runtime: not_run`，但仍可构建候选交付物。
