# 分阶段共创引擎

本文件定义所有项目阶段共用的对话状态机。具体阶段的问题范围、充分性门槛和片段结构由 `references/stages/` 下的对应文件补充；两者冲突时，优先遵守更严格的阶段边界。

## 标准路线

按以下顺序组织新项目：

1. 项目预检
2. 项目定位
3. 材料整理（可选）
4. 世界观
5. 角色
6. 系统（可选）
7. 场景（可选）
8. MVU/EJS（可选）
9. 叙事与开场
10. 状态栏/UI（可选）
11. 整合交付

可选阶段可以跳过。角色阶段不是可选阶段，而是一次角色资产盘点关口：定位允许零固定角色时，可以锁定空角色清单并当轮完成，不创建占位角色或假主角。修改、转换或审查已有项目时，可以从最相关的阶段切入，但仍需先完成项目预检并检查前置依赖。

### MVU/EJS 可选路由

前一阶段收尾时只决定“进入或跳过” `mvu_ejs`，并给出结合已锁定需求的推荐；MVU、EJS 或组合的能力选择属于该阶段本身，不得提前询问。普通模式由用户确认路线；AI 只在覆盖该路线或后续阶段的明确授权内代为决定，报告理由后锁定且不再追问。

- 进入：激活 `mvu_ejs` 后再处理能力组合、运行时契约和实现细节；进入前无需把任一 feature 预先设为 `true`。
- 新建且无既有实现时跳过：保持 `features.mvu: false` 与 `features.ejs: false`，在 `.rp-card-state.json` 写入 `stages.mvu_ejs.status: skipped` 和简短理由，不开始访谈，不生成禁用片段、依赖说明或阶段总汇，直接把 `narrative_opening` 作为下一阶段。
- 非新建项目本轮跳过：保留既有 feature、源码、依赖和未知字段，并继续校验实际交付物。既有状态为 `complete` 时不要降级为 `skipped`；尚未处理时可记 `skipped`，但摘要必须说明“本轮未修改、既有实现保留”。修改、禁用或移除既有实现不属于跳过，必须进入 `mvu_ejs` 完成迁移、清理和验证。

## 五条不变规则

1. **一次只处理一个阶段。** 只询问当前激活阶段允许的问题，不因“顺便确认”而借用其他阶段的问题。
2. **每轮形成闭环。** 使用“多项问题与信息采集 + 方向与推荐 -> 用户选定 -> 生成可合并片段”的循环，直到当前阶段达到充分性门槛。
3. **决定先于成稿。** 未经选择的互斥方向保持为候选，不偷偷写进正式片段；用户明确放权的项目除外。
4. **确认即锁定。** 已锁定内容不会在后续轮次被静默改写，也不会重新作为问题出现。
5. **阶段结束必须总汇。** 先给用户一份可查缺补漏的完整合并稿，再给下一阶段的可选方向和明确推荐。

## 持久化状态映射

项目只使用两份状态真源，不创建第三种 `workflow` 包装结构。对话中的流程概念按下表落到现有字段：

| 对话语义 | 语义真源 `project.yaml` | 技术真源 `.rp-card-state.json` |
| --- | --- | --- |
| 固定阶段路线 | `workflow.stage_order`、`workflow.optional_stages` | 不重复保存路线 |
| 当前阶段 | 不保存临时游标 | `active_stage` |
| 各阶段进度与轮次 | 不保存工具进度 | `stages.<stage>.status`、`round`、`summary` |
| 已锁定决定及最终值 | `decisions[]` 的 `value`、`decided_by`、`locked`、`status`、`rationale`、`history` | `decision_locks[]` 仅保存 ID、值哈希、锁定来源和时间 |
| AI 放权范围 | 决定结果通过 `decisions[].decided_by: ai_delegation` 留痕 | `delegations[]` 保存授权范围、授予时间和是否仍有效 |
| 跨阶段待办正文 | `cross_stage_backlog[]` | 同名数组只保存 `project_decision_id` 与技术处理状态 |
| 当前阶段未决缺口 | 保留在阶段总汇；若会影响其他阶段，再写入 `cross_stage_backlog[]` | 用当前阶段的 `status: blocked` 或 `awaiting_user` 与 `summary` 表达 |

`phase`、`stage_route`、`locks`、`open_gaps` 和单数 `delegation` 只是便于讨论的概念名，不是可写入文件的字段。落盘前必须分别读取 `assets/schemas/project.schema.json` 与 `assets/schemas/state.schema.json`；创作语义以 `project.yaml` 为准，Forge 只从它生成技术锁，不能从技术状态反向发明或修改决定。

## 进入一个阶段

进入阶段时依次执行：

1. 读取项目状态、当前阶段文件和已确认源码。
2. 汇总会约束本阶段的前置硬设定，但不要把它们改写成新问题。
3. 从本阶段充分性门槛反推缺口，区分 `blocking`、`important`、`optional`。
4. 只选择当前最有信息增益的一组问题，通常每轮 3 到 6 项。收尾只剩一个主缺口时，仍从该缺口的选择、边界或例外、验收影响中提取至少两项真实信息并在同一轮询问；若这些信息已经锁定，则不再提问，直接进入阶段总汇。不得降为单项问答，也不得为凑数量制造无关问题。
5. 若当前阶段已经充分，直接进入阶段总汇，不重复访谈。

进入阶段的首次回复使用：

```markdown
## 本阶段目标
[一句话说明本阶段最终要锁定什么]

## 已知信息
- [只列会影响本阶段的已确认事实]

## 本轮问题
### 1. [问题]
- 方向 A：[内容]；影响：[对 RP 或工程的影响]
- 方向 B：[内容]；影响：[对 RP 或工程的影响]
- 推荐：[方向]，因为[结合现有信息的理由]
- 也可以：[说明用户可自定义或混合，但要指出需明确的差异]
```

不要在首次回复里预写一份看似已经定稿的完整方案。推荐用于帮助选择，不等于替用户锁定。

## 问题设计契约

每个问题都应做到：

- 直接对应一个尚未满足的充分性条件。
- 给出 2 到 4 个真正有差异的方向，而不是同义改写。
- 解释每个方向会怎样改变 RP 体验、维护成本或后续设计。
- 明确给出一个结合当前项目的推荐及理由。
- 允许用户自定义、组合或拒绝所有候选。
- 避免把多个独立决定塞进同一道问题；如果用户无法分别选择，就应拆开。
- 不重复询问已经明确提供或已经锁定的信息。

问题应优先解决高影响、高依赖的缺口，再处理装饰性细节。不要一次抛出几十个问题，也不要使用只有“是/否”而没有影响说明的问卷。

## 用户回答后的固定循环

收到选择后，按以下顺序回复并更新状态：

### 1. 本轮已锁定

逐条报告刚刚确定的决定。对于 AI 获得授权后代为决定的内容，同时说明“如何决定”和“为什么这样决定”，随后立即写入 `project.yaml.decisions[]`，设置 `decided_by: ai_delegation`、`locked: true` 与 `status: active`，并由 Forge 同步技术锁。

### 2. 本轮生成片段

生成能够直接合并进该阶段源文件的片段，而不是只复述选项。片段应：

- 使用本项目约定的结构和稳定 ID。
- 只包含本阶段内容。
- 把必要的因果、例外和判定口径写完整。
- 与既有锁定项合并，不覆盖无关字段。
- 明确区分玩家可见信息与 GM/秘密信息（若该阶段涉及信息分层）。

### 3. 本阶段检查

报告本阶段的完成状态：

- 已满足的充分性条件。
- 仍存在的 `blocking` 或 `important` 缺口。
- 新发现的冲突、规则真空或跨阶段待办。
- 不用虚假的百分比包装进度；优先列“已满足 X/Y 项”。

### 4. 下一步

- 仍不充分：提出下一组且仅属于当前阶段的问题，继续同一循环。
- 已充分：输出阶段总汇，不再继续挖掘可有可无的细节。

标准回复骨架：

````markdown
## 本轮已锁定
- [决定 + 来源]

## 本轮生成片段
```text
[按当前阶段 Schema 生成并验证的可合并片段]
```

## 本阶段检查
- 已满足：[条件]
- 仍缺少：[条件]
- 跨阶段待办：[只记录，不在本阶段追问]

## 下一批问题
[仍不充分时使用本阶段问题格式]
````

## 跨阶段信息

用户可能主动说出不属于当前阶段的重要信息。此时：

1. 接受并简短复述，避免让用户觉得被忽略。
2. 原意记录进 `cross_stage_backlog`，标明来源阶段和目标阶段。
3. 不在当前轮追问该信息的细节，也不提前生成目标阶段内容。
4. 进入目标阶段时先消费待办；若它已经足够明确，直接锁定或作为已有信息，不重复问。

如果当前阶段被前置缺口真正阻塞，不要越界补问。报告缺少哪项、为什么会阻塞，然后推荐暂时返回对应阶段。完成补丁后恢复原阶段。

## 阶段充分性

“充分”不等于“写得最多”。满足以下条件即可进入总汇：

- 本阶段文件列出的必需门槛全部满足。
- 不存在会让核心 RP 无法判定的本阶段规则真空。
- 不存在未裁决的本阶段致命冲突。
- 所有关键决定已经由用户或获授权的 AI 锁定。
- 可选细节若跳过，不会阻止下游阶段；跳过项已明确记录。

不要因为还能继续扩写，就无限延长访谈。

## 阶段总汇

达到充分性门槛后，输出：

1. **阶段合并稿**：把所有已确认片段整合成一份无重复、无冲突的当前版本。
2. **锁定决定**：列出用户锁定项及尚未报告过的硬决定。AI 放权决定在代选时已经报告过，后续总汇只把结果自然并入合并稿，不重复解释或重新确认；其来源保留在技术状态中。
3. **查缺补漏**：分别列出冲突、薄弱点、可选增强项和用户主动跳过项；没有则明确写“无”。
4. **跨阶段待办**：按目标阶段归档，不在这里展开。
5. **下一阶段方向**：给出可走的下个阶段、跳过条件和一个明确推荐。
6. **切换动作**：正常模式下请用户选择“补漏 / 确认并进入推荐阶段 / 确认并选择其他阶段”。

示例结尾：

```markdown
## 下一阶段建议
- 方向 A：进入角色阶段。适合当前世界规则已经稳定的情况。
- 方向 B：补充一轮世界观边界案例。适合希望强调规则推演的项目。
- 推荐：进入角色阶段，因为核心规则、社会后果和信息分层均已可判定。

请选择补漏，或确认本阶段并指定下一阶段。
```

如果用户已把相应范围完全交给 AI，则仍输出总汇和推荐，但不要再请求确认；报告选择后直接切换并锁定。

## 写入时机

- 项目预检期间只做对话确认和只读检查，不创建项目目录、不修改材料。
- 新建项目在项目定位总汇被锁定后，才初始化工作区并开始保存阶段片段。正常模式由用户确认锁定；覆盖该范围的完全放权则由 AI 报告方案与理由后锁定。
- 每轮只写入已经锁定的片段；候选方案和未确认猜测不进入正式源码。
- 所有写入先更新维护源码与状态账本，不直接修补 `dist/` 产物。
- 对已有项目的修改应保留未知字段和原始输入，具体事务规则由 Forge 文档与脚本执行。

## 异常处理

- **回答不完整**：锁定已明确项，只继续询问缺失项。
- **回答互相冲突**：指出冲突的实际后果，给 2 到 3 个修复方向和推荐；仍只处理当前阶段。
- **用户修改已锁定项**：按 `references/delegation-and-locking.md` 执行定点解锁和影响传播。
- **用户要求跳阶段**：检查依赖。可安全延后则记录并切换；会导致当前产物不可判定则说明阻塞项。
- **用户改变任务目标**：返回项目预检更新任务类型或交付目标，再重新计算路线，不把工程变更伪装成创作问题。
