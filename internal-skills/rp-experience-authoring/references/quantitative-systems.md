# 数值系统专科

只在系统已经被判断为数值型或混合型时读取。这里设计的是与运行框架无关的 RP 数值逻辑；MVU、EJS、Schema、消息变量和 UI 路径仍留到后续技术阶段。

数值存在的意义，是让持续变化能够被稳定裁决并产生可观察后果。不要为“显得完整”添加无人读取、不会改变行为、也不会影响选择的轴。

## 访谈问题

使用普通玩家能理解的表达进行多轮、多问题访谈，不设固定题数；每次回答后立即更新数值规则，并给方向与推荐。需要确认的内容包括：

1. 这个数值在游玩中代表什么，达到高低两端时会发生什么实际变化；
2. 它作用于谁，是每个角色独立、某个势力共享，还是整个世界只有一份；
3. 它可以升降、只能上升、只能下降，还是会自然回到某个基准；
4. 哪些事件会明显改变它，同类行为反复发生时是否衰减或冷却；
5. 玩家是否应直接看到数值，还是只通过行为、叙事和 UI 档位感知；
6. 多个事件同一轮发生、触顶、触底或信息不足时，希望怎样裁决。

不要要求用户直接写公式。先收集想要的体验，再由 Agent 提出 2–3 套计算轮廓并明确推荐。

## 每个数值轴的闭环

每个承重轴至少具备：

- 稳定机器名和自然中文含义；
- 作用对象与独立/共享范围；
- 下限、上限、初值和变化方向；
- 正面与负面事件的基础变化范围；
- 完整覆盖范围、无空档和无重叠的阈值；
- 每个阈值至少两种能被玩家或其他角色察觉的表现；
- 单次变化、单场景或单会话变化边界；
- 触顶、触底、恢复、自然衰减和重置条件；
- 重复行为的衰减、冷却或明确“不防刷”的设计理由；
- 数值改变后对行为、关系、资源、权限、事件或叙事造成的实际后果。

只升轴不得通过普通负向事件下降，只降轴同理；如果存在逆转机制，把它写成明确例外，而不是让方向字段失去意义。

## 计算与多事件

公式应使用纯数值和清晰运算符，修正系数 `1.0` 表示不修正。推荐基础形式：

```text
delta = round(base * threshold_mod * context_mod * repetition_mod)
```

- `base`：事件本身的基础强度；
- `threshold_mod`：当前位置对正负变化的敏感度；
- `context_mod`：公开/私下、证据强弱、关系或环境等情境修正；
- `repetition_mod`：同类意图在当前结算周期内重复出现时的衰减。

同一轮出现多个事件时，必须声明合并方式。可以使用“主事件全额、次要同向事件折算、正负分别合并后再相加”，也可以设计其他规则；关键是不能由游玩模型每次临时任选算法。

## 多轴联动

多个数值轴同时存在时，检查：

- 是否真的需要独立，还是同一概念换了名字；
- 一个轴是否修改另一个轴的增减速度、阈值表现或可用行动；
- 两个轴给出相反行为指令时按什么优先级裁决；
- 联动是否形成永远无法脱离的正反馈或负反馈死循环；
- UI 展示的派生值是否只读，避免模型和脚本重复写入。

## 运行示例与压力测试

数值系统定稿前至少演算：

1. 一次明确正向事件；
2. 一次明确负向事件；
3. 一次同类事件重复触发；
4. 一次正负事件同轮发生；
5. 一次跨越阈值；
6. 一次触顶或触底；
7. 一次模糊事件或信息不足。

每个示例写出旧值、事件、各修正、原始变化、边界裁剪、新值和可观察后果。示例算不通，说明规则还没有完成，不能把问题推给 MVU 阶段。

## 推荐源码

把 `assets/templates/quantitative-system.mixin.yaml` 合并到对应系统源码。混合型只填写实际数值化的轴，叙事部分继续保留在系统主结构中。

## 完成门槛

- 范围、初值、方向和阈值互相一致；
- 阈值完整覆盖范围且没有空档、重叠或反向区间；
- 相邻阈值在行为或玩法上可辨认，不只是换标签；
- 公式所有输入都有来源，所有输出都有后果；
- 重复、多事件、边界、衰减和多轴冲突有稳定裁决；
- 正面、负面和边界演算均能得到合理结果；
- 技术阶段只需实现这套规则，不需要重新发明系统语义。
