# 系统阶段（可选）

系统是 RP 中可反复发生、可被理解和裁决的玩法规则。它首先是叙事与行为规则，不默认等于数值表、状态机或程序配置。

## 先判断系统形态

不要因为最终可能使用 MVU，就提前把所有玩法改造成数字。先根据实际体验选择：

- **叙事型**：主要依靠事实、标签、阶段、资源状态、事件时钟和因果裁决；继续使用本文件。
- **数值型**：数值大小、增减幅度、阈值或公式本身会持续影响选择与表现；继续读取 `quantitative-systems.md`，并合并 `assets/templates/quantitative-system.mixin.yaml`。
- **混合型**：少数承重维度需要精确数值，其余仍用叙事状态；只把承重维度交给数值专科，不把整个世界数字化。

判断依据是“玩家是否会因为数值差异作出不同选择，以及游玩模型是否必须稳定复算”，不是“状态栏想显示很多东西”。如果标签、档位或事件时钟已经足够，就不增加公式。

## 何时需要

调查进度、资源消耗、战斗、经营、声望、感染、任务、时间推进、事件演化等需要跨回合保持一致时进入。纯关系或短场景只靠角色与叙事即可成立时可以跳过。

## 允许讨论

- 系统要让 RP 多出什么选择、压力、反馈和后果；
- 谁能触发、何时结算、世界和 NPC 如何响应；
- 规则的例外、失败、恢复、重复利用和长期变化；
- 是否需要数值、档位、标签、列表、时钟或纯叙事判断；
- 信息对玩家、NPC、叙事模型分别可见多少；
- 哪些内容值得跨回合保存，哪些只需当场叙述。

不在这里决定 MVU 路径、Zod、EJS、正则或 UI 画法。只有系统语义稳定后，MVU/EJS 阶段才选择如何实现。

## 每轮推荐结构

先问系统目的与游玩感觉，再问判定与后果，然后判断叙事/数值/混合形态，最后用边界案例检验。问题使用普通玩家能理解的语言，例如“同一件事连续做三次，效果应该越来越弱吗”，不要一上来要求填写公式、`writer/readers/cleanup/migration`。

## 叙事系统最低合同

叙事型和混合型的非数值部分不能只列概念名。每个承重系统至少明确：

- **作用对象与触发**：谁能触发，事实、行动、时间或资源满足什么条件；
- **可用选择**：系统让玩家、NPC 或势力多出哪些真实行动，而不是只增加旁白描述；
- **正常结果**：准备充分或条件满足时怎样成功；
- **部分成功**：目标推进但付出时间、资源、暴露、关系或长期风险；
- **失败路线**：失败是否终止、转向补救、升级威胁或留下可继续处理的痕迹；
- **信息不足**：无法确定时保持什么状态，怎样在正文中表现不确定性；
- **重复处理**：同一事实是否只结算一次，同类行为重复是否衰减、冷却或触发反制；
- **冲突优先级**：多个规则、角色义务或事件同时要求不同结果时怎样裁决；
- **恢复与退出**：状态如何缓解、逆转、收束或永久留下；
- **结算顺序**：需要顺序时明确“识别事实 → 裁决结果 → 施加后果 → 推进世界/NPC → 写入需记忆状态”。

系统不必机械使用“成功/部分成功/失败”三段式；若采用其他结构，必须提供同等清晰的行动、代价和信息不足裁决。

## 推荐源码

```yaml
名称: "夜班事件推进"
目的: "让港口即使无人介入也持续发生变化，并为调查、交易和结盟制造窗口。"

核心规则:
  - "每经过一个重要行动或一段明显时间，检查当前进行中的事件。"
  - "事件由参与势力、当前地点、已暴露线索和资源状况共同推进。"
  - "没有角色参与的事件仍会发生，但结果通过传闻、环境变化或人物行动被看见。"

事件结构:
  状态: [潜伏, 发酵, 爆发, 收束, 留痕]
  推进来源:
    - "时间自然流逝"
    - "相关势力主动行动"
    - "关键资源被夺走或补足"
    - "秘密被公开"
  收束后果:
    - "改变地点状态"
    - "改变 NPC 日程与关系"
    - "生成新的传闻、机会或威胁"

裁决原则:
  正常推进: "满足阶段条件时进入下一阶段，并先表现可观察迹象。"
  部分成功: "玩家阻止直接损失，但暴露身份或消耗关键资源。"
  失败路线: "事件升级并留下新的补救入口，不为制造戏剧直接结束所有路线。"
  信息不足: "保持当前阶段，用传闻、异常或人物谨慎表现不确定性。"
  重复处理: "同一事实只结算一次，不因复述重复推进。"
  冲突优先: "已发生事实与世界硬规则优先，不为让事件靠近当前视角改写因果。"
  结算顺序: "识别触发 → 裁决本次结果 → 留下后果 → 推进场外行动 → 记录承重状态。"

示例:
  - 条件: "走私团在两次夜班内未得到燃料，且港务处已提高检查"
    结果: "事件从发酵进入爆发；走私团改为劫掠民用仓库"
```

只有系统确实需要精确数值时才进入 `quantitative-systems.md`。不要在本文件里用几行含糊的“初值、阈值”假装数值系统已经设计完成，也不要为了 MVU 方便把本可用自然规则表达的系统全部数字化。

## 系统质量审计

定稿前检查：

- **选择闭环**：系统是否真的让参与者作出选择，而不是自动播放事件；
- **触发闭环**：触发条件是否可观察、可区分、不会因同一事实被重复结算；
- **后果闭环**：成功、部分成功、失败和拒绝都有可继续处理的结果；
- **时间闭环**：延迟、等待、错过窗口和无人介入会真实推进；
- **角色闭环**：NPC 与势力按目标、资源和义务响应，不因系统需要变成无条件工具人；
- **恢复闭环**：损失、警报、感染、声望、资源或事件有明确恢复、转移、收束或不可逆说明；
- **状态闭环**：只有后续需要读取的事实进入持久状态；一次性描写不伪装成变量；
- **实现中立**：系统语义不依赖尚未决定的 MVU、EJS 或 UI 才能理解；
- **反利用**：重复刷取、故意拖延、复述事实、拆分同一行为或多事件叠加有稳定处理；
- **跨阶段一致**：系统能力、代价、数值与世界规则、角色行为、场景资源和开场初态一致。

## 完成门槛

- 规则能指导实际 RP 行为，不只有概念名；
- 触发、成功/部分成功/失败、信息不足、例外与重复处理明确；
- 世界/NPC 在无人介入时仍有推进逻辑；
- 需要持久化的内容与只需叙述的内容已经区分；
- 已明确属于叙事型、数值型或混合型，选择理由与实际游玩需求一致；
- 数值型或混合型已经通过数值专科的范围、阈值、计算、边界与示例检查；
- 若计划进入 MVU/EJS，已留下“需要实现什么”的语义清单，而不是提前设计代码。

## 建议式系统访谈

每个系统问题都先给推荐规则：它要增加什么选择或压力、哪些后果值得长期保留、失败是终止还是转入代价路线、玩家应看到怎样的反馈。解释为什么建议叙事型、数值型或混合型，并说明选择会增加哪些运行组件与维护成本。

不要问“要不要 MVU”或要求用户写公式。可以问：“我建议把调查进度做成阶段时钟而不是 0–100 数字，因为玩家更关心线索是否足以推动行动；这样规则更稳、UI 更轻，但无法显示精确百分比。是否按这个方向？”定稿前至少演算一个正常选择、一个部分成功或失败/拒绝，以及一个无人介入的推进。
