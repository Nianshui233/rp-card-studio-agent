# SillyTavern Message Frontend Authoring

只接受主 Agent 调度。这个 Skill 负责正式游玩中的消息内前端家族，不把所有项目压缩成一个通用状态栏。

按需读取：

- 持续状态、交互与消息生命周期：`references/message-ui.md`
- 非 MVU 消息快照与正则载体：`references/non-variable-regex-ui.md`
- 字体、图标、SVG 图形与资源策略：`shared/frontend/ui-assets.md`；选用图形化表达时读取该参考中的实现与验收合同

不要处理一次性开场/创角页面；但要消费它已经由用户维护/导入的主控资料，不得重新创建第二套主控档案或默认玩家。

## 来源优先级：不要把样本 HUD 当成产品需求

持续消息前端必须从当前项目的原始卡、已确认体验和真实状态合同推导信息架构。`full-mvu-rp`、HUD 样本矩阵和其他示例均标为 `reference_only`，只能提供技术参考，不能直接决定本项目展示哪些卡片、字段、标签、图表、路线或操作。若原始卡已有消息界面，先盘点其保留、迁移、重写、删除和待确认项；新增展示项必须说明对应的本项目事实或玩法后果。

## 设计起点：玩家在当前消息里要做什么

前端不是“MVU 数据 → 卡片列表”的自动映射。开始设计前先用用户能回答的语言确认：

- 玩家在每轮最需要理解什么；
- 玩家看完界面后要做什么：继续阅读、选择行动、查看人物、调查线索、处理资源、阅读日志、进行检定、查看地图或别的动作；
- 这个界面在作品里像什么：战术终端、档案、地图、报纸、卷轴、办公桌、商城、医疗记录、控制台、通讯频道或其他媒介；
- 哪些信息常驻、哪些折叠、哪些只在发生变化时出现；
- 哪些操作会改变下一轮剧情，哪些只是本地查看；
- 哪些信息更适合用文字/列表，哪些更适合用地图、路线图、徽章、仪表、关系图、资源流向或其他作品专属图形表达。

如果用户没有概念，给出 2–3 个差异明显、可用日常语言理解的方案并明确首选。图形化问题要问“希望玩家看见什么、怎样理解或操作”，不要问 SVG、`viewBox`、DOM 或路径代码。不要先问 CSS、框架、DOM、API、iframe、正则 placement 或变量路径；这些属于实现层。技术能力需要单独透明确认：

- **MVU**：是否需要跨消息保存并更新时间、地点、关系、任务、物品或主控状态；
- **mvu.zod**：是否需要对变量类型、范围、对象和数组结构做校验与归一化；
- **EJS**：是否需要根据当前上下文改变 Prompt、世界书内容或页面输出；
- **酒馆助手交互**：是否需要点击界面向聊天输入行动、执行用户明确授权的资料维护或写回状态。

这些是独立能力。用户开启哪项，执行 Agent 就必须实现和验证哪项；不得为了“安全”“复杂”或省事静默降级，不能把 EJS 当成 MVU，也不能把 mvu.zod 当成可有可无的装饰层。

## 前端家族，而不是两个万能页面

根据实际玩法按需选择一个或多个消息表面：

- **状态/现场摘要**：当前时间、地点、环境、主控状态和玩家此刻必须知道的事实；
- **选项/行动**：玩家能选择的行动、交谈、观察、移动、交易或确认；
- **检定/结果**：骰点、风险、判定结果、代价和后果；
- **情报/线索**：调查资料、新闻、档案、地图、关系证据或可用于决策的证据；
- **日志/记录**：事件、变化、发现和历史摘要；
- **人物/关系**：只有作品确实以人物关系为玩法时才提供；
- **物品/资源/商城**：只有物资管理、交易或经济是实际玩法时才提供；
- **转场/序章/特殊事件**：需要独立叙事媒介时提供。

项目可以只有一个静态摘要，也可以有一组互相配合的界面。不得默认生成“一个开场页 + 一个状态栏”，也不得因为字段多就无限复制正则和标签。每个额外表面都必须回答：玩家为什么需要它、它从哪条真实协议读取、点击后产生什么结果、失败时怎样退回。

前端家族共享同一套运行合同和状态权威，但不共享第二套持久状态树。每个表面可以有自己的视觉媒介和信息层级；不能把所有变量原样倾倒给用户，也不能用通用 Dashboard 卡片替代作品专属结构。

## 图形化表达与真实数据

地图、路线、关系图、设备仪表、资源流向和主题徽章可以是消息前端的一等表现方式，但必须先证明玩家为什么需要它，以及它读取哪条真实协议。

- 静态图形只表达已经确定的作品内容；动态位置、路线、数值、连接和状态必须来自唯一真实数据源；
- 图形化表达不能凭空创建地点、关系、可前往地点、状态或第二套变量；
- SVG 是可选的一等表达能力，可用于自包含地图、路径、徽章、刻度和专属符号；HTML/CSS、SVG 或其他实现由 Agent 按体验选择，不为“使用 SVG”而强行复杂化页面；
- 交互图形必须有文字、键盘和可访问入口，状态不能只靠颜色；
- 默认优先内联、自包含和离线回退；Agent 编写并检查的 SVG/JavaScript 是维护源码，运行时模型文本必须作为数据解析、校验再绑定，不直接变成执行代码；
- 图形失败、数据为空或宿主不可用时提供文字/列表和明确错误态；回退是异常路径，不得把用户已选定的图形和交互因“安全”“省事”静默降级。

## 主控中立与当前活动主控

世界核心、NPC 本体和消息前端默认不绑定单一玩家。除非用户明确选择固定主控预设：

- 不把“玩家”“user”“主控”当成同一个固定人物；
- 不在前端静默创建姓名、过去、身份或与 NPC 的朋友/仇人/恋人关系；
- 不把某个主控的资料、物品、知识、关系或历史写回世界核心或其他主控；
- 不因状态栏存在就假设一定有主控。

状态/人物面板读取**用户已经维护/导入且当前活动的主控**，而不是自己创建或猜测：

- 有活动主控：显示该主控的资料和当前状态；
- 没有主控：照常显示世界、现场、事件和其他固定角色，主控区显示“未登记/未选择”；
- 多份主控但没有活动标记：显示“未选择当前主控”，不合并；
- 切换主控：以新的当前活动资料重新读数，旧主控的私人状态不残留；
- 主控与 NPC 的私人关系属于当前主控/当前情境，不改写 NPC 的基础关系。

固定主控预设可以有专属页面和专属关系，但必须被标记为可选预设，并与开放世界核心隔离。

## 接口

输入来自已经完成的内容和运行合同：

- 系统、场景和角色阶段提供玩家需要观察和操作的事实；
- `st-mvu-authoring` 在启用 MVU 时提供唯一状态根、路径、作用域、读写权、保存方式和事件时序；
- mvu.zod 合同提供 Schema、范围、归一化和失败行为；
- `st-ejs-authoring` 在启用 EJS 时提供模板执行阶段、作用域、输出边界和失败回退；
- `st-worldbook-regex` / `st-render-regex` 提供 marker、载荷、prompt/display 分工和完整/流式路由；
- 宿主支援 Skill 提供当前楼层、Swipe、iframe、父页能力和清理事实；
- 开场阶段提供用户维护/导入的主控资料入口，不提供默认主控。

本 Skill 输出：

- 一个或多个与作品体验匹配、完整自包含的消息 HTML 表面；
- 每个表面的真实用途、载体、marker、数据源、producer/parser/schema 与正则/EJS 配对；
- 当前数值楼层与 Swipe 对应的数据读取；
- 编辑、Swipe、消息更新、重载、切聊和重复挂载行为；
- 玩家动作、真实写入、保存、同存储面读回、反馈和失败回退；
- 加载、空态、无主控、损坏、宿主不可用和 `pagehide` 清理；
- 键盘、焦点、ARIA、触控、长列表、性能和调试降级；若使用图形化表达，还要检查 SVG/图形的真实数据绑定、文字回退、响应式和交互等价入口。

## 后续新增展示项与状态归属

用户新增展示/操作要求时，先区分：已有状态直读、已有规则的确定性派生、临时 UI 状态、用户主控资料、固定预设内容，或新的持久化状态/玩法。

- 已有字段：沿用原路径和唯一权威来源；
- 可推导项：仅在确定性、不需保存且不改变模型决策时在视图层派生；
- 临时 UI 项：折叠、当前标签页、筛选、动画进度不写入 MVU；
- 用户主控资料：读取用户维护/导入的当前活动资料，不复制到世界核心；
- 新持久状态或新玩法：回 systems/scenes/character 确认语义，再回 MVU/mvu.zod 定义路径、初值、范围、唯一写者、可见性、保存和旧聊天处理；
- 只有动态 Prompt/世界书/页面输出才回 EJS；EJS 不得暗中创建 MVU 状态。

状态栏或其他消息前端不得为“显示完整”创建影子状态、假值、默认玩家或第二套持久化。语义未定时可以搭可逆视觉草稿，但必须标出未接通。

## 读取器最低合同

前端渲染只依赖真实的状态载荷：如果 provider 已返回当前消息的 `stat_data`，`schema` 即使存在也可能是对象或字符串，不能用 `typeof schema === "object"` 作为唯一可用性门禁。完整 MvuData/桥接校验与玩家界面渲染是两件事；provider 报告没有快照时显示干净空态，不伪造数据，也不把内部 API 错误直接展示给玩家。

## 持续生命周期

```text
消息表面建立
→ 通过 provider 专用 adapter 取得数值楼层与 Swipe
→ 读取真实状态或消息载荷
→ 渲染对应的消息表面
→ 监听宿主编辑/Swipe 与项目自有 post-write 信号
→ 玩家执行被授权的动作
→ 写入明确数值楼层或生成明确的下一轮行动输入
→ 等待必要保存并同面读回
→ 刷新当前表面
→ 编辑/Swipe/重载时重新读取
→ 页面销毁时清理
```

MVU 的 `VARIABLE_INITIALIZED/VARIABLE_UPDATE_ENDED` 是内存变换事件，不等同于消息变量持久化完成。不要在事件中立即重读 `Mvu.getMvuData()`；按实际 provider 等待保存/重渲染信号。用户主控资料的导入、启用和切换也必须有真实的宿主证据，不能只靠页面按钮文字判断。

## Provider adapter

- TH fenced iframe：使用 `getCurrentMessageId()`、裸 TH API 与裸事件清理；
- STPT `@@iframe`：由 EJS render context 写入 `message_id/swipe_id`，显式探测 `window.parent` 能力，所有 namespace 事件句柄主动 stop；
- 纯 SillyTavern：只做受限静态展示，不承诺按钮、变量或脚本；捕获值进入 HTML 时必须有字符边界或明确净化；
- 其他 provider：先写明如何获得 message ID、如何读写、如何保存、如何清理，再实现页面。

不能把 TH 专用 `getCurrentMessageId/eventOn` 合同泛化到所有 iframe。

## 访谈方式

持续消息前端是玩家反复看见的产品界面。视觉风格、排版偏好、要展示的信息和交互感受是第一优先级，但用户不需要会设计网页。除非已有完整设计简报或明确授权自由设计，至少用以下问题访谈：

1. **玩家此刻最想知道什么？** 例如“我在哪、身上有什么、谁在附近、现在能做什么”；
2. **看完后最想做什么？** 例如“点一个 NPC 交谈、调查线索、选择路线、处理物品”；
3. **界面在作品里像什么？** 例如档案、终端、地图、报纸、战术台或日志；
4. **哪些内容常驻、折叠或只在变化时提醒？**
5. **图形化表达**：哪些信息希望看成地图、路线图、徽章、仪表、关系图或其他作品专属图形？图形是否可操作另放在交互问题中确认。
6. **状态变化希望怎样被感知？** 颜色、文字、警报、日志、动画或其他自然方式。

Agent 先给首选方案和真实示例，再让用户确认；不以“默认 HUD 更易读”为理由覆盖主题。按已有回答、材料和授权跳过已解决项，每轮最多 3 个独立决策；纯文字项目不强问图形，已授权自由设计时由 Agent 选择。不要问 CSS、框架、DOM、API、iframe 或正则实现。每次用户回答后立即修改真实 HTML，并用加载、无主控、空态、错误楼层、保存失败、窄屏、长文本、编辑或 Swipe 中至少一个情境校准。

## 边界

- 不制作项目介绍、完整创角、开局路线选择或 Greeting 跳转；
- 不初始化第二套玩家档案或状态树；开场存在时只消费用户已维护/导入的主控资料；
- 不把状态栏变成隐藏的创角流程；
- 不因为有一个 `<user>` 条目就假设它永远存在或只有一份；
- 不生成 UI 需求表、数据路径清单、生命周期账本、中间 YAML、manifest、mock 或构建器；直接维护实际 HTML 与真实运行组件。

## 交付

每个页面含完整 body、CSS 和 JavaScript，并明确 Tavern Helper fenced HTML、ST-Prompt-Template `@@iframe`、纯静态 SillyTavern 或其他已验证载体。交付说明列出前端家族中实际启用的表面及其用途，不为未启用的表面制造文件。没有真实宿主证据时写 `runtime: not_run`。
