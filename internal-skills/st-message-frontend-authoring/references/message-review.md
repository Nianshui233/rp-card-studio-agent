# 持续游玩：从反复使用复核

这是一遍面向长期游玩的复核，不以开场的视觉冲击、章节节奏或创角流程评分。实现后从实际数据与操作检查，而非仅依据源码和测试绿灯；没有另一模型参与时不声称独立模型审查。

## 看什么，怎样判定

| 观察对象 | 需要回答的具体问题 | 对应证据 |
|---|---|---|
| 高频任务 | 当前最重要的信息能否扫读？低频细节能否找到？ | 实际首层、按需视图和重复操作。 |
| 语义表达 | 地图、关系、槽位、数量或进度是否有真实意义？何时文字更清楚？ | 真实字段映射、图例、详情；未知/零值也要看。 |
| 动作结果 | 查看、拟定行动、发送、写入与保存是否明确分开？ | 实际点击后的 DOM、输入框、状态与读回。 |
| 内容增长 | 长中文、大量对象和增长数值是否挤掉操作或造成无法回查的截断？ | 长内容与大量对象的项目用例，不拿空态代表完成。 |
| 连续使用 | 刷新会不会抢焦点、跳回顶部、重复闪动、丢失筛选？ | 刷新、展开、筛选、再刷新后的观察。 |
| 消息语境 | 当前楼层、Swipe、主控与聊天是否正确？旧信息有没有残留？ | 各对应生命周期和实际数据范围；模拟不能代替酒馆。 |
| 窄屏舒适度 | 是否重新组织结构，而不是缩小桌面页？触控是否能访问所有详情？ | 窄消息容器、短屏、放大文字、键盘与触控路径。 |
| 视觉执行 | 文字、图形、色彩与状态反馈是否支持任务，而非通用仪表盘皮肤？ | 当前宽窄屏、关键视图及动作后的画面。 |

密度不是字号越小越好，复杂不是功能越多越好。不能为满足检查删掉已承诺操作；发现新的玩法或持久状态需求，回 owning stage 定语义，不由 UI 私自扩展。

## 有问题怎样写

以“当前什么地方有问题 → 具体证据 → 对玩家观察/判断/行动的影响 → 修改 → 相同状态复测”组织。没有证据的审美猜测保持待核对。方向失效要改变信息组织或表达，而非继续堆边框、发光和字段。

当前结论写回 `frontends.message_frontend.designReview` 的 readingPriority、actionClarity、longSessionComfort、visualExecution，不另设审美账本或保存旧实现。已解决问题只保留当前必要依据。机器检查不等于好看、用户满意或真实酒馆通过；临时调参截图不能计入正式复核。
