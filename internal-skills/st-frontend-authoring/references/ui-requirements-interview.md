# UI 需求访谈与产品定义合同

这份合同负责把用户能感知的 UI 需求问清楚，再交给前端、运行时和整合模块实现。它不是代码配置表，也不是让用户填写正则、变量路径或 API 的问卷。

## 1. 适用范围

把两种前端分开访谈：

1. **开场介绍/创角前端**：版本、世界介绍、作者留言、游玩指南、路线选择、主控设定填写、预览、提交和进入开局。
2. **持续消息前端**：状态、人物、物品、任务、地图、关系、事件、行动、反馈和长期游玩功能。

叙事与开场阶段只访谈第一类；状态栏/UI阶段只访谈第二类。用户主动提供另一类信息时记录到跨阶段待办，不借机追问或接管另一个表面。

## 2. 每轮固定形式

每轮最多询问 3–4 个当前阶段关键问题。问题必须使用普通玩家能理解的语言，并遵循：

```text
已知信息与本轮缺口
→ 3–4 个当前阶段问题
→ 2–3 个方向差异与一个明确推荐
→ 用户选定、补充或授权 AI 决定
→ 生成当前阶段可直接合并的片段/方案
→ 本阶段查漏补缺与下一轮建议
```

只在信息缺失、冲突或会改变设计方向时提问。已有世界观、角色、系统、MVU/EJS、开场和样本信息必须先自动整理，不能让用户重复填写。

不把所有问题一次性抛出；一个项目可以分多轮完成。每轮结束都说明已锁定什么、还缺什么、哪些只是 Agent 的技术实现决定。

## 3. 问题池不是固定问卷

下列维度都要覆盖，但只在当前缺失时询问，按项目复杂度和已知信息分批使用：

### A. 用途与玩家旅程

- 这个界面主要帮助玩家看什么、做什么？
- 玩家最常见的一次使用路径是什么？例如“查看状态 → 打开人物 → 查看关系 → 发起行动”。
- 哪些内容需要一眼看到，哪些可以进入标签页、折叠、抽屉或详情页？
- 这是辅助信息面、操作面，还是项目的主要游玩表面？

不要直接问“页面类型”这种工程词。可以给出贴合项目的选项：状态总览、人物与关系、背包/商店、任务与事件、地图与地点、战斗/判定、时间线、日志、创角导览、世界百科或 Agent 推荐组合。

### B. 信息与数据规模

- 必须展示哪些信息？允许用户自然语言列举，Agent 负责整理成单值、多值、列表、详情和派生字段。
- 哪些字段可能为空、未知、隐藏、过期或暂时不可用？
- 列表通常只有几项，还是可能出现几十项、上百项？
- 数据是每轮刷新、状态变化时刷新、打开页面时读取，还是用户点击才读取？

先由 Agent 输出“字段候选表 + 优先级 + 空态/错误态建议”，用户只需要改动不符合直觉的部分。

### C. 交互与宿主动作

可以用自然语言描述想做的事，不要求用户知道 API：

- 是否需要折叠、标签页、搜索、筛选、排序、分页、详情弹窗、复制、收藏、标记已读或历史回看？
- 点击按钮后是展开信息、改变卡内状态、写入 MVU、生成一段可发送文本、填入 SillyTavern 输入框，还是直接触发生成？
- 操作成功、失败、处理中、重复点击和宿主不可用时，玩家应看到什么反馈？
- 哪些动作可以撤销、重试或复制回退？

按钮是否能访问父页面、Tavern Helper、MVU 或其他插件由 Agent 根据项目需要和宿主能力决定。用户只确认“希望按钮完成什么事”。

### D. 视觉方向与信息密度

不要只问“你喜欢什么风格”，而是结合 RP 主题给出 2–4 个可感知的方向，每个方向说明颜色、材质、字体气质、图形、动效和信息层级。例如：

- 旧港档案：煤油灯、旧纸、铜锈、深海蓝、档案章和手写批注；
- 都市异闻：冷灰玻璃、警示红、监控噪点、窄栏和告警闪烁；
- 诡谲梦境：低饱和紫、半透明层叠、漂浮文字和柔和模糊；
- 军事终端：深色金属、荧光绿、网格、状态警示和紧凑数据排布。

只在需要时询问：

- 主色或禁用颜色；
- 紧凑、舒适或沉浸式信息密度；
- 单主题，还是明暗/昼夜/阵营主题切换；
- 动效偏好、减少动画、声音或震动反馈；
- 中文字体气质、长文本阅读和排版偏好。

如果项目需要特殊中文字体或功能图标，在视觉方向锁定后再补问“更重视主题字体、阅读舒适还是完全离线”“功能图标希望简洁、机械、手绘还是项目专属”。不要求用户知道字体文件、SVG、CDN 或图标包名称；资产来源和实现路线由 Agent 负责。

如果用户说“你决定”，Agent 根据世界、玩法和玩家旅程直接选择并锁定，报告理由，不再反复提供视觉选项。

### E. 设备、载体与可达性

用玩家语言询问：

- 手机优先、电脑优先，还是两边同等？
- 是否需要单手操作、触控大按钮、横屏、窄屏和软键盘友好？
- 是否有需要特别照顾的长中文、低对比度、减少动画或键盘操作场景？

“消息内、独立文档、沉浸式 0 层”是实现结果，不作为默认技术选项强迫用户选择。应询问体验目标，再由 Agent 选择 `message_surface`、`standalone_document` 或 `zero_layer`。普通持续状态 UI 默认优先消息内生命周期；只有用户明确要求或需求本身已经成为主要游玩表面时，才采用 0 层路线。

## 4. 字段到组件的主动建议

Agent 应主动给出建议并让用户确认观看方式，而不是让用户选择 HTML 标签：

| 字段语义 | 默认建议 | 可能的替代 |
| --- | --- | --- |
| 血量、体力、好感、进度、完成度 | 进度条、环形指标 | 数值徽章、趋势条 |
| 状态、在线、库存、任务态 | 中文状态徽章 | 色带、图标+文字 |
| 标签、属性、关键词 | 标签组、分组标签 | 可筛选芯片 |
| 多项数值对比 | 条形图、对照表 | 雷达图、紧凑指标卡 |
| 事件、历史、日程 | 时间线、事件卡 | 按日期折叠列表 |
| 人物关系 | 关系卡、分组网络 | 邻接列表、关系矩阵 |
| 物品、技能、任务 | 卡片列表、网格 | 可筛选表格、详情抽屉 |
| 地点、地图、区域 | 地点卡、分区导航 | 简化地图、路线列表 |
| 长文本、档案、说明 | 可读正文、折叠详情 | 分页、目录、抽屉 |

建议必须说明理由、优先级和移动端退化方式。不要因为有字段就机械地增加组件；组件数量服从玩家旅程和信息层级。

## 5. 标记、正则与技术决定

- 用户已经提供标记时，尊重并记录它；用户没有提供时，Agent 可以自行生成稳定、中文、唯一的 XML/短标记。
- 不要求用户自行发明触发词、正则、变量路径、placement、depth、事件名或 API。
- 由 Agent 闭合“生产者 → 模型提示词处理 → 玩家显示替换 → HTML 数据读取”链，并在整合阶段验证。
- MVU 只负责变量并不等于它会生产 UI 标记；非 MVU 卡需要独立的模型输出契约或已验证的脚本/框架生产者。
- 触发标记是运行实现，不是视觉需求本身；不要在视觉需求阶段把技术标记问题伪装成用户偏好问题。

## 6. 完全放权与方案推荐

区分三种用户表达：

- “我不懂，给我推荐”：给 2–3 个普通语言方案，让用户选。
- “你看着办”：结合项目事实给出推荐；如果授权范围不清，只问最小缺口。
- “完全交给你/你决定”：直接选择、说明取舍、锁定并执行，不再重复询问，也不把已决定项重新列成待确认。

无论哪种情况，Agent 都要报告：选择了什么、为什么、对玩家体验有什么影响、哪些技术细节由 Agent 自行承担。

## 7. 需求记录结构

开场和持续状态前端都可以在对应源文件中保留以下 `ui_requirements`，用于跨轮次恢复和查缺补漏。它是设计账本，不是新的强制字段合同：

```yaml
ui_requirements:
  interview_status: draft
  purpose: ""
  primary_journey: ""
  player_tasks: []
  information:
    must_show: []
    useful: []
    detail_only: []
    may_be_empty: []
    data_scale: "unknown"
    update_cadence: "unknown"
  interactions:
    desired: []
    host_actions: []
    feedback: []
    avoid: []
  visual:
    direction: ""
    palette: ""
    font_direction: ""
    icon_direction: ""
    density: comfortable
    theme_mode: single
    motion: project_matched
  device:
    priority: equal
    touch: true
    narrow_screen: true
    long_chinese_text: true
  carrier:
    user_facing_goal: ""
    agent_choice: "message_surface"
  assets:
    font_strategy: system_stack
    icon_strategy: project_svg
    remote_dependencies: []
  recommendations: []
  open_questions: []
  locked_decisions: []
```

未确认的字段保持 `unknown`、空数组或空字符串；不要为了让模板“看起来完整”虚构用户偏好。

## 8. 完成判定

UI 需求阶段在以下内容足够明确时结束：

- 玩家知道这个界面用来做什么、最常走哪条路径；
- 核心信息和信息优先级清楚，已考虑空态、错误态、长列表和长中文；
- 主要交互和宿主动作清楚，按钮不只是装饰；
- 视觉方向、信息密度、设备优先级和载体方向已有选择或 AI 锁定；
- 开场与持续前端边界清楚；
- 技术链仍可由 Agent 自行完成，不把用户拖去填写代码配置。

不要因为还有更多可选字段、组件或视觉细节就无限访谈。需求完整后立即给出产品方案和第一批真实 HTML/CSS/JS 片段。
