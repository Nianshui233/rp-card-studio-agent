# 持续消息 UI

本参考只服务进入 RP 后的持续消息前端：状态、物品、关系、任务、地图、线索、调查、通知和交互工具。首条介绍、路线选择和创角前端属于开场内容。

## 先问

只问 2–4 个玩家能理解的问题：

- 这是状态展示、行动工具还是完整消息内应用？
- 玩家最常看或操作什么？
- 主要设备是电脑、手机还是两者？
- 视觉主题希望怎样贴合项目？

用户说“你定”时直接选择，不创建 UI 账本。

## 直接实现

轻型 UI 直接维护最终完整 `.html`：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <style>完整 CSS</style>
</head>
<body>
  完整消息内页面
  <script>完整 JavaScript</script>
</body>
</html>
```

只有用户明确要求复杂多页面或已有正式前端工程时，才临时拆分开发文件。最终交付不依赖同目录 CSS/JS，也不要求 `manifest`、mock、源码/制品双轨或 `ui-build`。

## 数据与生命周期

先确定：

```text
数据来自哪里
→ 当前消息如何读取
→ 哪些是持久状态、派生视图或本地交互状态
→ 何时刷新
→ 用户动作写到哪里
→ 空值、错误、加载和卸载怎样处理
```

MVU UI 通常等待 `Mvu`，读取当前楼层 `stat_data`；不要用固定示例值伪装运行状态。非 MVU UI 必须采用真实消息快照合同：模型生产 XML/文本块，正则捕获并注入 HTML，解析器处理完整/流式载荷，prompt 通道单独决定保留或删除。

消息 iframe 需要时探测当前窗口和 `window.parent`，并处理：

- 消息重新渲染；
- 编辑和 Swipe；
- 重载和聊天切换；
- `pagehide` 卸载；
- 重复初始化与重复监听。

按钮必须有真实宿主动作、成功反馈和失败回退。没有真实宿主证据时写 `runtime: not_run`。

## 玩家体验

- 可见标题、标签、空状态、错误和按钮使用自然中文；
- 窄屏、长中文、触控和滚动不破坏布局；
- 静态项目内容、派生视图和本地交互可以丰富页面，但不伪装成实时变量；
- 不创建脱离聊天消息的页面级常驻面板；
- UI 规模按用户实际目标判断，不按固定导航数、按钮数或代码行数阻断。

## 交付检查

确认完整 HTML、真实数据绑定、空/错状态、按钮行为、正则配对和宿主依赖。复杂问题按需加载 `st-host-capabilities`、`st-runtime-authoring` 或 `st-render-regex`。
