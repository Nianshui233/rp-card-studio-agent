# RP Interview Orchestration

只负责访谈控制，不替代当前阶段的创作 Skill。先读取 `references/stage-coverage.json` 中当前阶段的覆盖地图，再结合用户材料、历史回答和阶段 Skill 的内容形成**已解决 / 待确认 / 可默认 / 明确跳过**的决策集合。访谈问题集合只保留在当前对话，不另建访谈记录；真实决定及授权依据由 rp-project-continuation 更新共享 authority 阶段账本。必须遵守 orchestrator/stage-authorization.md。

## 决策闭环

每个触发的承重决策只能以下列状态之一关闭：

- `source_resolved`：用户材料或既有回答已明确决定；能指出具体依据，不靠猜测；
- `confirmed`：用户针对该项明确选择或校准；
- `delegated`：用户明确授权 Agent 对该项作决定；立即采用一致方案，不重复追问；
- `explicit_skip`：用户明确不做此能力/内容，或覆盖地图的 skip 条件成立；
- `tentative`：为了先产出草稿而采用的可逆临时假设。它不是确认，不能关闭承重项。

delegated 必须引用真实阶段授权，范围和阶段一致；“本阶段放权”内的选择自主完成，但不把它登记为 user_confirmed。proposed/unresolved 保留开放，不能以 Agent 自己的账本制造用户确认。

高影响创作决定（核心体验、人物自主性/底线、玩家控制权、重要后果、开场路线/写入行为等）不得静默记为 `delegated`。用户没答、含糊答或只答了复合问题中的一部分时，保留为待确认。

低风险、可逆、不会改变已确认体验的文案润色和实现细节可由 Agent 默认处理；在有可能影响体验时简短标明默认及可改处。具体 Schema、变量路径、API、正则写法和文件组织不推给用户；但**是否需要一项运行能力**不能被 Agent 私自吞掉。MVU、MVU_ZOD、EJS 以及用户要求的 Tavern Helper/界面交互能力，必须用普通语言说明用途、技术名称和取舍，让用户明确选择。

用户明确选择启用的能力具有约束力。不得以“安全”“复杂”“省事”或“建议最小化”为理由静默关闭、降级、改名或用静态假实现替代；确实存在宿主阻碍时，先报告阻碍、损失和可选替代路线，再由用户明确决定是否放弃。

## 创作归属模式与主控边界

定位阶段必须先关闭一个正式分流，默认推荐第一项：

1. **开放世界**：世界核心对外部主控保持中立，未来玩家可以创建一个或多个主控；
2. **固定主角**：作品围绕一个明确主角展开，主角身份、关系和共同经历可以成为这条路线的硬设定；
3. **开放世界＋可选主控预设**：世界核心保持中立，同时提供若干可主动启用、可关闭的固定主控路线。

访谈中始终区分：

- creator：正在使用 Agent 创作的人；
- 玩家：未来导入卡并游玩的人；
- 主控：当前聊天接入世界的外部角色；
- `<user>`：外部角色资料的预留接入口，不是默认主角，也不是唯一玩家。

开放世界模式下，世界、NPC、势力和场景必须在没有任何 `<user>` 或主控时也能运行。不得默认询问、补写或暗示玩家的姓名、身份、过去、能力、阵营、目标或与 NPC 的私人关系。NPC 可以有自己的生活、目标、固定关系和对陌生人/身份类型/行为的通常反应，但外部主控的朋友、恋人、仇人、亲属、旧识和共同经历默认未定义。

固定主控关系只能进入固定主角路线或独立、可选的主控预设。预设可以引用世界核心，世界核心不得反向依赖预设；必须保留“从零创建/不启用预设”的入口。多个主控的身份、知识、物品、经历、关系和状态必须有清楚作用域，切换 A→B 不得污染世界核心或泄漏 A 的资料。

## 运行能力的透明选择

开始展示能力选项时，至少分别说明：

1. **让状态跨消息持续记住并变化（MVU）**：时间、地点、任务、关系、物品和角色状态是否要保留到下一轮；
2. **检查变量结构并减少更新错误（MVU_ZOD）**：是否要校验类型、范围、必填字段和嵌套结构；它依赖 MVU，但不能被合并或悄悄省略；
3. **根据上下文动态改变 Prompt、世界书或页面（EJS）**：是否需要条件模板、动态内容或 STPT 输出；它不是 MVU；
4. **点击界面执行行动或调用酒馆能力（Tavern Helper 等）**：是否需要真正的消息内交互。

每项独立维护 `enabled`、`disabled`、`unresolved`。用户只回答“要 MVU”时只关闭 MVU；不自动打开或关闭 MVU_ZOD、EJS 或交互。用户明确启用后必须实现或明确报告无法实现，不能静默降级。只有 MVU 与 EJS 都启用且确有数据依赖时，才进一步判断 MVU→EJS bridge；bridge 不是隐藏的能力替代项。

## 前端个性化优先级

开场/创角页和持续消息 UI 是玩家直接使用的产品界面。主题气质、用户喜欢/排斥的参考风格、希望展示的内容、排版层级和交互感受属于高影响创作决定，**优先于 Agent 的通用审美默认，也优先于讨论实现细节**。没有现成设计简报时，先问这些用户偏好；用户明确授权“你自由设计”后，才可代定。

可以用少量具象的方向帮助用户表达（例如沉浸序章 vs 清爽创角向导、叙事档案 vs 紧凑 HUD），但这些只是灵感候选，不是默认答案。允许用户给作品/网页/UI 参考和明确禁忌。不要问 CSS、组件库、框架、断点、DOM、API 或 iframe；技术实现由对应前端 Skill 负责。技术能力是否启用另按上面的普通语言选项透明确认，不把“要不要 MVU/MVU_ZOD/EJS”藏在实现细节里。

图形化表达也属于体验选择：用“想不想把路线做成地图、阵营做成徽章、变化做成仪表”等具体建议帮助用户，而不是问 SVG、`viewBox` 或 `path`。仅在对应覆盖项触发且未被材料、回答或授权解决时询问；纯文字项目可以跳过。图形形式与点击动作分别确认，不用一个“高级前端”开关包住它们；SVG 本身不自动启用 MVU、MVU_ZOD、EJS 或酒馆助手。

## 提问批次

1. 每轮最多提出 **3 个独立决策点**；多于 3 个时按依赖和影响排序分轮。
2. 每项单独编号，使用玩家语言描述一个可回答的取舍；不要用一个“综合性问题”包住多个独立决定。
3. 对每项给出明确首选、为何符合已知材料、选择会改变什么。相邻问题可以共享背景说明，但用户应能分别回答每一项。
4. 不重复询问已由材料明确、已确认、已授权代定或明确跳过的内容。材料只暗示而未承诺时，按未知处理。
5. 用户回答后，逐项映射回答；只写入确定内容。能力选择必须逐项记录到当前对话：用户未回答的能力保持 `unresolved`，不能由“继续”、沉默或另一项选择推断为关闭。若答案有歧义，只追问会导致不同作品结果的那一处，然后立即推进已确定部分。
6. 不为了填满覆盖地图而提问。`trigger` 不成立或 `skip_when` 已满足时标记跳过/不适用，并继续创作。

## 后续需求与既有状态合同变更

后续阶段（尤其前端）出现“还想展示/操作 X”时，**前面已定的状态模型既不是不可修改的铁律，也不能被前端静默扩展**。先对新增需求做一次影响分类，再决定继续、派生、或回到拥有语义的阶段：

1. `existing_state`：已有 canonical 状态路径可直接提供；前端只读取并呈现，不复制一份。
2. `derived_view`：可由既有 canonical 状态和已确认规则确定性计算，且不需要独立保存、不改变模型后续决策；可以做只读派生视图。若规则涉及场景、权限、时序或角色语义，回到相应领域阶段把规则说清。
3. `transient_ui_state`：仅界面展开/选择/临时筛选等，不是游戏事实；由 UI 自己管理，不写入 MVU。
4. `new_persistent_state` / `new_mechanic`：会影响后续叙事、行动、权限、数值结果、模型可见上下文或跨消息/聊天记忆；停止把它当纯前端任务，返回覆盖地图 `reopen_routes` 指定的 owning stage。通常需要回到 `mvu` 重新定义唯一状态合同；若语义尚未成立，先回 `systems`、`scenes` 或 `character`。EJS 只在新增需求属于动态 Prompt/模板时处理，不拥有持久状态。
5. `unclear`：用玩家语言先问“这只是把已有信息显示出来，还是会改变游戏/后续叙事并需要记住？”；不要问用户选变量类型/API。若是能力选择，直接说明 MVU、MVU_ZOD、EJS 的用途和启用/不启用的实际影响，让用户选择能力，不让用户设计实现。

返回前置阶段时，只重开受影响的语义决定，不重跑整个项目、不推翻无关已确认内容。对新增持久状态，至少确认它对玩家代表什么、初值/范围或空态、由什么事件改变、谁有权改变、影响哪个玩法/叙事结果、玩家是否应看见、作用域与保存/旧聊天兼容。确认后由 `st-mvu-authoring` 修改唯一状态合同及 `[initvar]`/Schema/写入责任，再同步世界书提示、producer、开场初态、前端读写和验证样例；只有动态模板需要读取该状态时才另经 `st-mvu-ejs-bridge` 接入 EJS。禁止让 UI 或 EJS 建立影子状态源。

例如：已有“时间/地点/天气”字段就直接绑定；“可前往地点”若只是按已确认的场景规则计算且不需保存，可作为派生视图；若会随任务/权限变化并影响模型后续叙事，应先确认场景/玩法规则；“人物属性”若会跨消息变化并影响行动/叙事，是新持久状态，应回角色/系统阶段定语义，再回 `mvu` 定唯一变量合同，最后回状态栏显示。

实现前说明依赖影响与推荐路线。完成变更后重新运行包级检查，并对受影响的跨阶段链做回归；若旧聊天/旧制品会受影响，明确迁移或新聊天要求。没有明确语义时可先做不承诺新游戏事实的可逆视觉草稿，但不得假装该字段已有运行数据。

## 玩家中立性与主控切换完成门

定位、世界、角色、场景、叙事和开场阶段结束前，至少检查：

- 无 `<user>`、无当前主控时，世界、NPC、势力和场景仍能运行；
- 没有把 creator、玩家、主控和 `<user>` 偷换成同一个人；
- NPC 没有默认绑定外部主控的朋友、恋人、仇人、亲属或旧识关系；
- 用“主控 A 是 NPC 的朋友、主控 B 是 NPC 的仇人”的反例切换 A→B 后，当前关系跟随 B，A 的资料不泄漏；
- 固定关系只存在于已标记的固定主角路线或可选预设，未启用预设时不生效。

失败时回到拥有该语义的定位、世界、角色或场景阶段修复，不用前端、正则、EJS 或变量显示掩盖内容归属错误。

## 阶段结束门

阶段 Skill 完成实际内容后，检查当前阶段所有**已触发且承重**的决策：必须是 `source_resolved`、`confirmed`、`delegated` 或 `explicit_skip`。仍有 `tentative` 的承重项时：

- 继续就最重要的 1–3 项提问；或
- 若用户明确要先看草稿/暂不回答，则交付为可逆草稿，并简短指出它尚未定案的具体影响。

不得仅因为“已经问过一个大问题”“已经写了很多内容”或“Agent 能猜出合理答案”就宣布阶段完整。阶段摘要只报告已确定事项、Agent 受权代定事项、明确跳过项和尚未关闭的承重选择，不生成访谈记录文件。

阶段内容足够时只提交成果，progress=awaiting_handoff、review=pending，授权改 expired；阶段报告后不进入下一创作阶段；本次制作达到收尾条件时按 orchestrator/automatic-work.md 自动 QA/交付，创作仍待用户审阅，不额外访谈 QA 许可。用户否决使受影响决定重开并撤销相关验收，不能保留“全部完成/已接受”的错误状态。

## 边界

- 当前阶段主 Skill 负责创作事实、内容质量和技术/体验具体实现；本模块不生成角色、世界书、规则、页面或代码。
- 简单定向修改、事实明确的修复、用户明确授权“你直接决定”时，不强行启动访谈。
- 脑暴不是长问卷：先给可用的首选脊柱，再追问真正改变核心体验的决策。
- 访谈不是心理画像；不从沉默、简短回答或措辞推断偏好/授权。

## 制作与验证接入

前端阶段按 `shared/frontend/layout-preview.md` 主动给出当前方案的结构草图和关键交互状态，不仅问选项或等用户自己画。由当前前端主 Skill 提供布局投影，访谈控制器负责把问题落到看得见的结构并在修改后同步；不在此创建第二份 UI 需求或执行实现代码。已有明确决定/授权不重复求批，展示预览不自动关闭未答事项、接受阶段或授予下一阶段权限。

页面访谈按 `orchestrator/production-verification.md` 的 surfaces 与当前决定引用展开；不以大类 covered 代替具体字段、布局和操作。用户更正后旧摘要失效，必须同步所有受影响投影，不能只刷新摘要而保留旧取舍。
