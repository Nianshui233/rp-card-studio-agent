# SillyTavern Opening Frontend Authoring

只接受主 Agent 调度。这个 Skill 负责正式游玩前的入口、创角和主控资料交接；它不是通用表单生成器，也不是世界书写入器。

按需读取：

- 开场体验、入口媒介与页面家族：`references/opening-ui.md`
- 主控模式、创角资料与交接：`references/creation-flow.md`
- 字体、图标、SVG 图形与资源策略：`shared/frontend/ui-assets.md`；选用图形化表达时读取该参考中的实现与验收合同

不要在这里处理持续消息状态、每楼数据投影、背包、任务或长期消息控制中心；这些属于 `st-message-frontend-authoring`。但必须把开场产出的主控资料与后续状态读取合同对齐。

## 来源优先级：原始卡优先，样本只作技术参考

开场/创角前端不是通用表单生成器。改造旧卡时，先读取并盘点原始卡已有的页面、字段、分组、选项、交接文本和玩家流程；将每项标为保留、迁移、重写、删除或待确认，再开始实现。原始卡已有的语义不能被样本矩阵替换。

`assets/examples/`、外部样本卡和通用表单只能作为 `reference_only`：可以借鉴宿主 API、生命周期、错误回退和测试方法，但不得直接复制字段、步骤、默认值、提示文案、视觉媒介或状态语义。任何不在原始卡或用户明确决定中的新增字段，都先作为提案展示，不能因为样本已有就直接写入页面。

主控字段必须回答“这个项目为什么需要它、它影响什么体验或玩法、它交给哪个既有资料/状态路径”，否则不添加。不得用样本里的“当前目标/本次来意/关系”等通用字段逼用户填写，也不得让页面默认值替玩家创建目标、身份、关系或决定。

## 先确定体验，再决定页面

开场前端的设计起点是玩家将如何进入作品，而不是“需要一个表单”。开始实现前先用普通语言确认：

- 玩家第一眼应该感到什么、理解什么；
- 入口在作品里像什么：序章、档案、终端、登记台、地图、卷轴、现场界面或别的媒介；
- 玩家是先读、先选路线、先创建主控，还是直接进入某个现场；
- 哪些资料必须在进入前决定，哪些应留给游玩自然形成；
- 开场页是否只是一个入口，还是需要与角色创建、路线预设、说明、预览组成一个小型前端家族。

如果用户没有想法，给出 2–3 个看得懂的体验方案并明确首选；开始视觉实现前不要先问 CSS、框架、DOM、API、iframe、正则字段或剪贴板权限实现。

### 图形化表达是体验选择，不是技术问卷

当开场内容适合被“看见”而不只是被阅读时，必须把图形化表达作为设计选项纳入判断：例如世界地图、路线图、阵营徽章、档案印章、章节标记、设备面板或作品专属符号。用普通语言询问用户哪些内容希望做成地图、徽章、仪表、关系图或其他图形，哪些只需要文字；不要让用户回答 SVG、`viewBox`、`path` 等实现术语。

Agent 根据已经确认的体验和真实数据选择 HTML/CSS、内联 SVG 或其他已验证方式：

- 装饰图形只强化氛围，不冒充状态或事实；
- 语义图形必须对应作品已有内容，地图、路线、徽章和仪表不能凭空增加地点、关系或变量；
- 可交互图形要有文字/键盘/ARIA 等等价入口，不能只靠颜色或悬停；
- SVG 是可选的一等表达能力；采用时默认自包含、响应式并保留文字/CSS 回退，不默认依赖远程图标库；维护源码中的 SVG/JavaScript 正常编写，游玩时文本不得未经解析和校验变成执行代码；
- 不因为“有 SVG”就强行增加装饰，信息架构和作品语义优先；用户已选定的地图、徽章或交互不得因“安全”“省事”静默改成文字，回退只处理异常，不替代正式实现。

按已有回答、材料和授权跳过已解决项，每轮最多 3 个独立决策；纯文字项目不强问图形，已授权自由设计时由 Agent 选择。图形形式与点击动作分别确认，不把它们塞进一个“高级前端”问题。

技术能力仍然要向用户透明确认，但要用“能得到什么”来问，不能把实现决策偷换成安全降级。至少分别询问或确认：

1. **跨消息持久状态（MVU）**：时间、地点、任务、关系、物品或主控资料是否需要跨消息保存和变化；
2. **变量结构校验（mvu.zod）**：是否需要校验类型、范围、必填字段，减少 AI 把数字/对象/数组写错；
3. **动态模板（EJS）**：Prompt、世界书内容或页面输出是否需要根据当前上下文变化；
4. **界面交互/酒馆助手**：玩家是否需要点击界面执行选择、查看、行动或用户明确授权的资料维护。

MVU、mvu.zod、EJS 是三项不同能力。用户明确选择后必须保留该选择；执行 Agent 不得为了“安全”“简单”或省文件而静默关闭、改成静态假实现或把 EJS 混入 MVU。用户只需要选择功能，具体脚本、Schema、正则、载体和桥接由 Agent 实现并验证。

## 主控模式是内容合同，不是技术开关

除非用户明确选择固定主角，否则默认采用开放世界路线，并在交付中保留用户自己维护/导入主控资料的入口。三种模式必须明确区分：

- **开放世界**：世界、NPC、场景和事件不预设单一玩家身份；`<user>` 只是外部主控资料的预留接入口。
- **固定主控预设**：用户明确要一条固定主角剧情时，身份、过去和关系放进独立的可选预设，不污染开放世界核心。
- **开放世界 + 可选预设**：开放核心之外提供若干朋友、仇人、陌生人或其他入口，用户可选用、关闭或改用自己的主控。

“玩家”“user”“主控”“当前活动主控”不能在没有授权时互相替换。制作用户也不等于未来游玩者，未来游玩者也不等于某个固定角色。

开场页必须支持以下至少一种真实路线，并清楚说明当前路线：

- 直接以世界中立入口进入，不要求创建主控；
- 创建一份用户自己的主控资料，生成可复制、可手工维护的资料块；
- 选择一个独立的固定主控预设；
- 在有多个主控资料时只表示“当前选择的那一份”，不自动合并。

开场页不得因为存在“玩家称呼”字段，就把该角色写成世界事实或唯一主角；不得在 NPC 条目、世界书或 Greeting 中静默补写外部主控与 NPC 的朋友、恋人、仇人、旧识等关系。关系若未由当前主控资料或已发生剧情提供，显示为未定义/待建立。

## 接口

输入来自已经完成的内容和运行合同：

- `rp-experience-authoring`：世界入口、路线语义、可选固定预设、玩家可自定义资料和 Greeting 内容；
- `st-mvu-authoring`：若启用 MVU，主控资料如何由用户维护或导入后进入状态、当前活动主控如何被识别；
- `st-mvu-zod` 或项目实际 Zod 支援：若启用 mvu.zod，Schema、归一化和失败行为；
- `st-ejs-authoring`：若启用 EJS，页面/Prompt 的动态边界；EJS 不负责凭空创建主控或替代 MVU 持久化；
- `st-worldbook-regex` / `st-render-regex`：真实 marker、载体、显示路由和提示词/显示分工。

本 Skill 输出：

- 一个或多个完整、自包含、与作品体验匹配的开场/创角界面；
- 一份仅供当前对话或 QA 使用的来源核对结果：原始卡字段与新增字段的来源、语义和去留；该核对结果不进入玩家可见页面或最终 RP 内容；
- 需要时的入口、序章、路线选择、主控创建、预设选择、预览和交接页面；
- 真实 Greeting/Swipe 的人类可读指引；
- 可复制、可阅读、可手工编辑的用户主控资料或导入文本；
- 若用户选择图形化表达，实际自包含的地图、路线、徽章、仪表或主题 SVG/CSS 表面，并说明它读取的真实内容；
- 用户自己维护/导入 `<user>` 或等价主控条目的明确步骤；
- 剪贴板失败、页面重载、无脚本或未启用可选助手时的回退说明；
- 若用户明确授权独立 Tavern Helper 资料维护工具，另行交付其权限、确认、幂等和失败合同；开场页面本身仍不静默写入世界书。

## 硬边界：开场页不擅自写世界书、不直接发聊天

开场/创角前端是**作品入口、主控资料生成器和操作向导**，不是数据迁移器或聊天机器人。默认路线是：

- 不调用 `createWorldbookEntries`、`updateWorldbookWith`、`deleteWorldbookEntries`；
- 不创建、覆盖、启用或禁用用户的 `<user>` 条目；
- 不直接修改第 0 楼、Greeting Swipe、聊天 metadata 或 MVU；
- 不调用 `/send`、`/trigger`，不插入 user 楼，不自动发送开场资料给 AI；
- 不覆盖 SillyTavern 输入框；
- 不把“复制成功”或“资料已生成”说成“主控已登记”。

默认交接路线：

```text
用户在开场页创建/选择自己的主控
→ 页面生成可读的主控资料块
→ 用户复制；失败则手工选中复制
→ 用户自己打开或维护独立世界书中的 <user>/主控条目，或导入交付的主控资料文件
→ 用户确认当前要启用哪一份主控资料
→ 再按页面指引选择真实 Greeting 并开始游玩
```

除非用户明确授权一个**独立、可见、可撤销、可回滚的 Tavern Helper 资料维护工具**，任何页面都不得代替用户写入世界书。即使有这个可选工具，也不能直接向聊天发送主控资料，不能偷偷把多个主控合并成一个，也不能把写入成功冒充为剧情已经开始。

## 一次性生命周期

```text
展示作品入口与可选主控路线
→ 用户主动选择/填写或跳过
→ 页面本地校验与预览
→ 生成主控资料/交接文本
→ 用户复制或手工复制
→ 用户自己维护/导入目标 <user> 或主控条目
→ 用户明确选择当前活动主控（如有）
→ 用户手动选择真实 Greeting/Swipe
→ 进入正式游玩
→ 状态栏读取当前活动主控；没有主控也能显示世界状态
→ 页面使命结束
```

页面可以保存按聊天/角色隔离的临时草稿，但不得把“已复制”“已写入世界书”“已选择主控”“AI 已回复”混成一个状态。没有真实宿主证据时，不宣称资料已经被导入或激活。

## Greeting 与纯净开场标签

- 第一条开场白若承担开场前端入口，正文只放约定的纯净 marker，例如 `<opening_remarks>`；不得把解释文字、创角表单源码或状态栏正文混在该条开场白里。
- 正则只捕获该 marker 并替换为开场前端；真正的剧情开场白放在后续真实 Greeting/Swipe 中，并由用户按页面说明手动选择。
- 每条可选路线必须对应真实、可手动选择的 Greeting；不得依赖脚本临时重写第 0 楼、自动切 Swipe 或自动发送。
- 自定义主控、固定预设和世界中立入口都应说明各自会承接哪条 Greeting；缺失时停止生成最终指引并报告修包，不静默跳到别的路线。
- 页面可以生成“当前主控资料已准备好”的可读提示，但不能把主控资料直接贴进 AI 对话作为默认登记方式。

## 后续新增资料与状态归属

如果用户在开场访谈中新要求了字段，先区分它属于：页面临时草稿、用户主控资料、固定主控预设、已有 canonical 状态的展示，还是新的长期玩法状态。前端不得为了“看起来完整”自行扩展隐藏档案或 MVU 变量。

- 临时值只留在页面草稿；
- 用户主控资料由用户自己维护/导入，不能写成世界核心事实；
- 固定预设的身份和关系只进入该预设；
- 新的持久字段返回 owning stage 重新确认语义，再回 MVU/mvu.zod 定义路径、初值、更新权和兼容；
- 只有动态 Prompt/世界书/页面输出确实需要时才进入 EJS；不能用 EJS 代替状态持久化；
- 未确定的字段明确标记“未设定”，不得静默补全。

## 完成门槛

至少验证：

- 页面在窄屏和宽屏都能完成选定路线，或明确跳过主控创建；
- 第一条开场消息保持纯净 marker，正则与完整 HTML 配对；
- 开放世界、固定预设、自定义主控的实际指引不混淆；
- 输出中没有未授权的单一玩家身份、NPC 固定玩家关系或默认主控；
- 用户可以看到、编辑和复制自己的主控资料；剪贴板拒绝时仍可手工复制；
- 开场页本身没有世界书写入、自动发言、自动 Swipe 或 MVU 直写；若有独立授权助手，单独验证其权限和幂等；
- 用户导入/维护主控资料后，状态栏能读到当前活动主控；没有主控时仍能显示世界状态且不编造身份；
- 使用图形化表达时，图形与真实数据、文字回退、窄屏显示和键盘/可访问入口相互对应；未选择图形化表达时，不以“缺少 SVG”为问题；
- 用户选择启用的 MVU、mvu.zod、EJS 和交互能力都能在交付物中找到真实实现或明确阻断说明，不得静默降级；
- 没有真实宿主证据时只声明静态/浏览器级通过，不声明 SillyTavern runtime pass。
