# 创角、写入与开场交接

创角前端只收集正式开局确实需要的玩家资料与初始选择。它不为完整感要求玩家在不了解世界时填写整套履历，也不预填最终玩家人物。

## 字段分工

```text
稳定玩家档案
→ 写入并启用唯一、中文、默认空白的 <user> 条目

动态开局状态
→ 写入 st-runtime-authoring 定义的真实 MVU 或其他项目状态

页面临时状态
→ 仅用于未提交表单和预览，不作为成功结果
```

一个事实只能有一个权威来源。稳定档案和动态状态有意重复时必须说明哪个是权威、另一个如何派生或同步。

## 表单规则

- 正式字段默认空白；placeholder 只能举例，不能成为提交值；
- 快速预设默认不选，由玩家主动选择后仍可逐项编辑；
- 只要求会改变开场、长期称呼、权限或运行初态的字段；
- 对可留到 RP 中自然形成的资料明确标记可选；
- 不读取或猜测制作用户本人的身份作为玩家默认值；
- 校验错误贴近字段显示，并保留其他已填内容。

## 提交闭环

```text
收集
→ 预览
→ 校验
→ 锁定本次提交，防止重复点击
→ 写入稳定档案
→ 写入动态初态
→ 分别从同一真实存储面读回
→ 核对非默认值
→ 选择实际 greeting/开场
→ 成功后进入正式 RP
```

任一步失败都不能显示整体成功。能够安全回滚时回滚；不能回滚时明确指出已成功和未成功的部分，并提供重试或手动回退。不要清空玩家输入。

## 交接合同

不要求生成额外 handoff 文件，但实现必须能回答：

```yaml
selected_route: "实际选择的路线或开场"
user_profile_written: true
initial_state_written: true
profile_readback: "已验证"
state_readback: "已验证"
greeting_target: "实际目标"
runtime_ready: true
```

持续消息前端只能读取 `st-runtime-authoring` 定义的同一状态合同，不能依赖页面本地对象或另造初始化数据。

## 验收情境

至少执行：

1. 全空或缺失必填值；
2. 一个主动选择的非默认值；
3. 写入失败并保留输入；
4. 写入成功后从真实存储读回；
5. 重复点击不会重复创建状态或消息。

没有真实 SillyTavern 证据时记录 `runtime: not_run`。
