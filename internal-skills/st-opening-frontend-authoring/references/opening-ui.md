# 开场体验与入口前端

这个前端服务正式 RP 之前的一次性进入体验。它不是“项目介绍 + 通用表单”的固定模板，也不是默认创建一个唯一玩家。页面必须先表达作品的入口体验，再决定是否需要路线选择、主控创建、预设选择或其他页面。

## 设计起点：玩家正在进入什么

实现前先用普通语言确认：

- 玩家第一眼要感到什么、理解什么；
- 这个入口在作品世界里像什么：序章、档案、终端、登记台、地图、卷轴、控制台、现场记录或其他媒介；
- 玩家是先阅读、先选择路线、先创建自己的主控，还是直接进入现场；
- 哪些内容应当在入口展示，哪些要留给游玩发现；
- 入口是单页还是由多个小界面组成。

如果用户没有视觉概念，给出 2–3 个用日常语言描述的方案。例如：

- “像一份世界内的登记档案：先读一段背景，再填写或跳过自己的公开资料。”
- “像一台旧终端：先选择进入方式，再逐步建立一份可切换的主控资料。”
- “像故事序章：不先填表，先把玩家放进现场，主控资料之后由用户自己维护。”

每个方案说明第一眼看到什么、要做什么、会不会创建主控、最后如何交接；不要用“SPA、组件、Schema、iframe”等术语让用户猜。

## 主控路线

入口必须明确区分三类路线：

### 1. 开放世界

玩家可以不创建主控，也可以在页面里准备自己的资料。世界不预设玩家姓名、身份、过去或与 NPC 的私人关系。页面生成的资料只属于玩家自己维护的 `<user>`/主控条目，不是世界事实。

### 2. 固定主控预设

只有用户明确需要固定故事时才提供。预设可以包含固定姓名、过去、路线和 NPC 关系，但它是可选的独立入口。关闭它、改用另一个预设或换成自定义主控时，开放世界核心不变。

### 3. 自定义主控

玩家填写自己愿意公开的资料。允许“未设定”；页面不能为了完整感替玩家补写过去、性格、关系或行动。生成的内容供玩家复制后自己维护/导入，不自动发到聊天。

多个主控同时存在时，页面只说明“当前选择哪一份”，不合并资料、不把其中一份关系写回 NPC 本体。

## 页面旅程

不要求每个项目都经过相同步骤。根据作品体验选择实际需要的页面：

```text
作品入口/序章
→ 可选路线或入口选择
→ 可选主控预设/自定义主控
→ 可选资料预览与修改
→ 生成用户主控资料块
→ 复制或手工复制
→ 用户自己维护/导入 <user> 或主控条目
→ 用户手动选择真实 Greeting/Swipe
→ 正式游玩
```

轻型项目可以只有一段序章和一个复制区；固定主角项目可以没有自定义表单；开放世界也可以允许直接跳过主控资料。不要为了“步骤完整”强行加入表单。

## 纯净开场标签与 Greeting

- 若第一条开场白用于触发开场前端，正文只放 `<opening_remarks>` 或项目约定的等价纯净 marker；不能在同一条里混入开场文字、状态栏或创角资料。
- 正则只负责捕获该 marker 并替换渲染开场页；页面以外的剧情内容放在后续真实 Greeting/Swipe。
- 每个路线都必须映射到实际存在、用户能看懂的 Greeting/Swipe；页面指引用可见标题或首句描述，不只写内部索引。
- 页面不得自动改写第 0 楼、自动切 Swipe、自动发送资料或把主控资料贴到 AI 对话中。

## 载体与权限

开场页面可以由 Tavern Helper fenced HTML、ST-Prompt-Template `@@iframe` 或其他已验证宿主建立。纯 SillyTavern 只承诺静态展示，不声称其中 JavaScript 会执行。

开场页面默认不需要聊天写入、世界书写入或 MVU 写权限。它只输出可读资料和操作说明。若用户明确启用独立 Tavern Helper 资料维护工具，必须单独显示“将修改哪一个用户拥有的条目”、要求用户确认、支持失败回退，并且不能把它当成开场页面的隐式能力。

完整 `.html` 是维护源码；运行时必须有真实 marker 与显示正则。远程资源失败时仍保留可读介绍、完整资料文本和手工维护路径。

## 草稿与预览

- 页面草稿可以只存在内存；若跨刷新保存，按角色/聊天隔离并明确是草稿；
- 修改任一字段后，旧预览和旧复制状态立即失效；
- 复制按钮始终复制当前可见全文；
- 页面不把复制状态持久化成“已导入”“已激活”或“已开场”；
- 切换聊天、角色或主控时，不把旧草稿自动写入新目标；
- 预览应显示资料将被用户维护到哪里，但不伪装成已经进入世界书。

## 个性化设计访谈（实现前必经）

除非用户已给出完整设计简报或授权 Agent 自由设计，开始视觉实现前至少确认：

1. **第一印象**：希望玩家感到压迫、神秘、温柔、危险、庄重、荒凉，还是别的；
2. **作品媒介**：更像档案、终端、卷轴、地图、现场记录、书页，还是直接进入剧情；
3. **展示内容**：进入前必须知道什么，哪些内容不应剧透，主控资料哪些必填/可空；
4. **节奏与排版**：首屏先氛围还是先选择；一页、分步、自由探索或无表单；
5. **操作结果**：玩家完成后要得到什么——一份可复制的主控资料、一个路线选择、一个真实入口，还是几者组合。

问题要用用户能回答的体验语言，并给出首选建议；不要问实现方式。技术能力选择单独透明呈现：MVU、mvu.zod、EJS、酒馆助手交互分别解释能带来什么，不把它们揉成一个“高级前端”开关。
