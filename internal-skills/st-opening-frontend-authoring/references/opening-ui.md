# 开场介绍与路线前端

这个前端只服务正式 RP 之前的一次性进入流程。它将已经确定的项目介绍、玩法说明、路线选择和开场映射变成可操作页面，不重新创作叙事内容。

## 输入合同

从叙事与开场阶段取得：

- 项目标题、核心体验和必要游玩说明；
- 可选路线及其可观察差异与影响；
- 默认开场和备用开场的实际 Greeting/Swipe 标识；
- 动态路线的 canonical 玩家开局发言构建规则；
- 玩家在提交前必须知道的限制、风险和远程依赖；
- 无前端或前端失败时使用的短文本回退。

没有这些内容时返回 `narrative_opening` 补齐，不在页面实现中临时发明路线语义。

## 页面旅程

推荐顺序：

```text
简短项目入口
→ 路线/开场选择（如需要）
→ 创角或开局配置（如需要）
→ 汇总预览
→ 明确确认
→ 冻结当前聊天、草稿 revision、0楼 Swipe/revision 与输入框状态
→ 真实提交、保存与读回
→ 固定 Greeting：确认目标 Swipe/初态并退出
→ 动态自定义开局：走正常 user 发送链并验证 AI 楼
→ 退出开场页面职责
```

不是每个项目都需要所有页面。轻型项目可以在一个完整 HTML 中完成，不为了步骤感拆页。

## 路线选择

- 默认不替玩家选择路线；确有唯一推荐入口时可突出推荐，但仍由玩家主动确认；
- 每条路线说明玩家能观察到的体验差异，不用内部 ID、变量字段或实现术语；
- 固定路线必须映射到真实第 0 楼 Greeting/Swipe；动态路线必须映射到真实初态和 canonical 玩家开局发言；
- 路线不可用时显示原因和回退，不静默跳到另一条路线；
- 多次点击或页面重挂载不能创建重复状态、重复 user 消息或重复初始化。

## 载体

开场页面可以由 Tavern Helper fenced HTML、ST-Prompt-Template `@@iframe` 或其他已验证宿主建立。纯 SillyTavern 只承诺静态介绍内容，不能声称其中 JavaScript 会执行；需要路线提交、创角写入或 Greeting 切换时必须选择真实可交互载体。

### Tavern Helper fenced iframe

- 可使用 `getCurrentMessageId()`、裸 TH API 与自动事件清理；
- 切换当前第 0 楼 Swipe 会重渲染并可能立即销毁页面；
- 需要切 Swipe 后继续提交时，使用后台 TH Script/协调器保存事务并由新实例恢复。

### ST-Prompt-Template `@@iframe`

- 只在消息渲染且有 `msgId` 的路径建立；
- 不获得 TH 裸绑定函数；由 EJS render context 把 `message_id/swipe_id/chat identity/draft id` 写入页面数据；
- 若通过 `window.parent` 调用 TH/Core，必须做能力探测并主动清理事件；
- 当前是无 sandbox 的同源高权限 iframe，不把它描述成安全隔离页。

完整 `.html` 是维护源码；运行时还必须有真实 provider、marker/条目、正则或协调脚本。远程资源失败时保留可读文字和手动进入游戏的回退路径。

## 提交上下文与竞态

打开页面时建立草稿身份：

```text
chat UUID/稳定聊天身份
+ character/group identity
+ 0楼当前 swipe_id
+ 0楼内容 revision 或等价指纹
+ draft revision/hash
```

最终确认前和真正发送前至少各重校验一次。以下任一变化都取消旧提交并保留草稿：

- 玩家切换聊天或分支；
- 第 0 楼 Swipe/正文被修改；
- 草稿在确认期间变化；
- 输入框已有玩家文本且未完成仲裁；
- 页面卸载或协调器失效。

## 建议式访谈

重点问玩家进入正式游戏前必须理解什么、路线差异是否值得在开局前暴露、页面应多快让人进入 RP、最终玩家开局消息需要表达什么。每个问题先给推荐信息层级和交互路径，说明为什么符合核心体验，并指出会怎样影响首屏长度、创角负担、Greeting 映射和消息链。

标准模式至少用窄屏、无路线选择、路线不可用、切聊天或重复提交中的一个情境校准最终 HTML。
