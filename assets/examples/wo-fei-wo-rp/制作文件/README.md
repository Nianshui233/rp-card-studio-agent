# 《我，非我》：唯一完整制品样品

> 这是 `rp-card-studio-agent/assets/examples/` 当前唯一保留的完整制品样品。
>
> 它不是“某一种可选路线的演示”，也不是让 Agent 继续复制字段的样本矩阵模板；它以真实旧卡的 RP 语义为基础，展示完整的运行组件和工程组织；当前版本已完成离线构建、Schema fixture、Regex 回放与来源审计，真实酒馆导入/运行仍按 not_run 单独记录。

## 1. 为什么保留这个样品

这个样品来自实际项目《我，非我》的最终整改制品。**原始卡是语义金标准**，本样品只记录如何在不污染作品层的前提下完成运行化改造。它用于告诉后续 Agent：

- 旧卡改造首先继承原始卡的语义，而不是先套用通用表单或 HUD；
- 世界观、角色、系统、开场和前端必须先有当前项目自己的来源；
- MVU、Regex、ScriptFolder 和消息内页面属于运行层，不能反过来污染世界观和 RP 文案；
- 用户没有声明的身份、关系、目标、决定和承诺必须保持未定；
- 前端必须消费真实状态，不能用假数据填满空态；
- 样本里的字段、分组和页面结构只能解释“这个项目为什么这样做”，不能直接变成下一个项目的需求。

实际导入包只有角色卡、世界书、正则、酒馆助手脚本四个 JSON 和导入说明.txt。下面列出的其他文件都属于制作文件，不需要导入。

## 2.0 MVU 源码、构建与导入

`制作文件/项目记录/MVU源码合同.json` 将 canonical Schema、`制作文件/运行源码/MVU/` 注册/加载入口、01～04 实际变量正文、正则、角色卡、世界书和项目 fixture 绑定成同一工程。`制作文件/构建/MVU/` 保存当前编译结果与实际哈希，`导入包/我，非我.酒馆助手脚本.json` 使用精确构建正文；只有当前工程链，不另存备份路线。各变量源的解释集中在 `制作文件/AGENT_GUIDE.md`，不进入实际 Prompt 正文。离线构建/Schema fixture 通过不等于新制品已完成真实酒馆验收，当前 source contract runtime 为 not_run。

## 2.1 前端宿主载体是固定的

本样品的开场页和消息状态栏都不是普通浏览器 HTML，也不是任意 iframe。它们固定走 Tavern Helper / JS-Slash-Runner 的消息前端路线：

```text
消息正文中的 <pre> 前端代码块
→ isFrontend 识别
→ div.TH-render
→ Tavern Helper message iframe
→ TH-message--{message_id}--{index}
→ 高度协议与生命周期管理
```

因此 `导入包/我，非我.正则.json` 中的两个渲染条目必须保持：

- `markdownOnly: true`；
- `placement: [2]`；
- fenced `html` 代码块；
- `promptOnly: false`；
- `runOnEdit: false`；
- 与各自 marker 一一配对。

`制作文件/运行源码/前端/消息状态栏.html` 使用 Tavern Helper 注入的 `getCurrentMessageId`、`Mvu` 和 `waitGlobalInitialized` 读取当前消息楼状态；它不是独立网页打开后就能工作的页面。页面还在 `pagehide` 时清理监听。

`制作文件/配置/前端载体运行合同.json` 是这个载体事实的机器可读说明。它明确区分：

```text
Tavern Helper message iframe
Tavern Helper script iframe
ST-Prompt-Template @@iframe
```

本样品只使用第一种。不能因为另一个项目使用 EJS 或 `@@iframe`，就把本样品的载体替换成另一条路线。

## 3. 三层边界

### 作品层

作品层包括：

- 世界观和硬设定；
- 角色和 NPC 行为逻辑；
- 生存、感染、觉醒和判定语义；
- 开场环境与叙事边界；
- 玩家中立、未声明即未定等 RP 规则。

作品层必须能够脱离具体文件名、UID、构建脚本和 Agent 工作流独立成立。

### 运行层

运行层包括：

- MVU 状态结构；
- 初始化基线；
- JSON Patch 输出方言；
- `<UpdateVariable>` 与 `<StatusPlaceHolderImpl/>`；
- ScriptFolder、Regex、Schema 和消息前端读取适配。

这些是为了让宿主运行的机器协议。它们可以存在于世界书的运行合同区域，但不能伪装成世界观事实，也不能被混写进叙事规则。

### 维护层

维护层包括：

- 导入步骤；
- 构建和校验脚本；
- 阶段账本；
- 测试日志；
- 来源索引；
- 样品说明。

维护层可以解释“怎么制作”和“怎么验证”，但不能进入玩家实际阅读的 RP 作品内容。

## 4. 为什么主控表单是 10 步、47 个控件

不要把这个数字当成通用表单标准。

它来自《我，非我》原始卡已有的创角页字段档，字段直接服务于本世界的具体语义：

- 爆发前职业影响生存技能倾向；
- 爆发地点和生存经历影响来历；
- 身体和精神状态影响生存系统；
- 觉醒状态、路径、类别、等级、代价和反噬属于本世界的核心冲突；
- 武器、防护、物资和外观服务于末日生存；
- 关系、秘密、恐惧和背景属于玩家资料，不自动变成世界核心事实；
- 开局来意只有玩家明确填写时才成立。

如果另一个项目没有这些语义，不能照抄这些字段。应该先从那个项目的原始卡或用户决定重新推导字段。

### 可以自由发挥的部分

在不改变语义的前提下，可以自由调整：

- 排版、颜色、字体、间距和视觉表现；
- 表单是分步、折叠、档案或其他作品内媒介；
- 空态的具体文案；
- 同一语义的字段标签措辞；
- 页面动画和无障碍实现；
- 状态栏中同一真实字段的可视化方式。

### 必须定死的部分

以下内容不能因为“看起来更方便”而自由发挥：

- 未声明的主控身份、目标、关系和决定不能自动生成；
- 原始卡已经确认的世界硬设定不能被样品字段覆盖；
- MVU 只能有明确的状态根、字段、类型、范围和写入来源；
- 页面不能创建第二套持久状态；
- 入口页不能代替玩家发送消息或偷偷改写资料；
- 状态栏必须读取当前真实消息状态，不读取假数据；
- `schema` 为字符串或缺省时不能把有效 `stat_data` 判成无效；
- SVG 元素不能使用只读的 `className` 赋值方式；
- Regex、页面源码和 marker 必须逐字配对；
- 真实宿主没有验证时，不能声称已经导入验收通过。

## 5. 状态来源合同

每个状态写入都必须回答：

```text
这是什么事实？
它来自用户原话、材料事实，还是本轮正文中实际发生的事件？
它是否需要跨轮保留？
谁是唯一写者？
没有证据时应该保持什么空态？
```

允许的来源：

- 用户明确提供的主控资料；
- 用户明确的更正或目标声明；
- 原始材料中的确定事实；
- 本轮正文中玩家或世界实际发生、可指认的事件；
- 已确认的系统自然结算规则。

不允许直接落库的来源：

- Agent 觉得“合理”的目标；
- 样本矩阵里的默认字段或默认值；
- 为了让状态栏看起来完整而补出的数字；
- 旁白推测；
- 页面自己创建的临时状态；
- 文件已经生成或测试通过这一事实。

## 6. 前端为什么这样写

### 入口页

入口页是一次性作品入口和主控资料生成器，不是通用数据迁移器。它：

- 先展示《我，非我》的世界入口和传闻层；
- 保留原卡创角页的完整资料维度；
- 允许不创建主控直接开始；
- 生成可阅读、可复制、可手工编辑的资料块；
- 剪贴板失败时提供手动复制回退；
- 不自动发消息、不自动切换开场、不写入持久状态。

### 消息状态栏

状态栏是当前消息的只读视图，不是第二套游戏系统。它：

- 只读当前消息的真实状态；
- 没有主控时仍显示世界和现场；
- 让玩家看到精确数值，但明确这些数字不等于角色知道；
- 对 `schema` 为对象、字符串、缺省三种快照形状都能显示已有 `stat_data`；
- 在没有状态时显示玩家可理解的空态；
- 通过文字和无障碍属性为图形提供等价表达。

## 画布背景与黑边

消息内前端是在宿主消息的 fenced HTML/iframe 画布里显示的。截图中若看到内容两侧或底部出现一整块黑色，通常不是组件 `border`，而是 `body` 的不透明背景叠加内容容器的 `max-width`、居中 margin 或 padding：

```text
宿主消息背景
└─ iframe 文档画布（html/body）
   └─ 页面内容容器（max-width / padding）
```

本样品把 `html/body` 背景设为透明，让宿主消息背景透出；面板自己的深色背景仍由面板组件负责。保留 `max-width` 只为了阅读宽度，不应再制造黑色边缘。后续 Agent 必须在模拟父容器中检查宽屏、窄屏、短内容、长内容和底部滚动边缘，区分宿主背景、iframe 画布和内容 surface，不要把画布留白误判为 CSS border。

## 7. 参考样品的使用规则

使用本样品时：

1. 先读本 README 和对应运行合同；
2. 再读原始卡或当前项目的 canonical 源；
3. 只复制你确认需要的技术闭环；
4. 字段、页面步骤、作品文案和状态语义必须重新从当前项目推导；
5. 新增内容先标为提案，不要把样品内容自动记为用户决定；
6. 改完后用真实快照、空态、错误载荷、Swipe、编辑和重载回放；
7. 任何工具说明都留在运行/维护层，不回流到 RP-facing 制品。

本样品不代表所有项目都应该启用 MVU、MVU_ZOD、Tavern Helper 或消息前端；它只代表一个已经明确选择这些能力的完整项目应该如何把边界闭合。
